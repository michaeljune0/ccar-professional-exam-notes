시스템 프롬프트는 센 경고문이 아니라 "이럴 때 이걸 한다 + 왜" 를 담담하게 적는 곳. 역할은 한 문장, 재료(지시·맥락·예시·입력)는 XML 태그로 칸을 나눔 ✓ 확인

규칙 원문 ①②③④⑤⑥ (갈림길로 그린 규칙)
  1. ①

    센 표현 걷어내기 : Opus 4.5·4.6 은 이전 모델보다 시스템 프롬프트에 더 민감 → 과소 발동을 막으려 쓴 "CRITICAL: You MUST use this tool when…" 이 이제 과잉 발동을 부름. "Use this tool when…" 처럼 보통 말투로 ✓ 확인 [2.2①]

    "Default to using [tool]" → "Use [tool] when it would enhance your understanding of the problem." · "If in doubt, use [tool]" 은 과잉 발동 원인 → 지움 · 그래도 과하면 effort 를 낮춤 (Opus 4.6 기준) ✓ 확인

  2. ②

    반대로 안 불리면(과소) 모델부터 봄 : Opus 4.8 = 도구보다 추론 선호 → effort high·xhigh 가 도구 사용을 크게 늘림 + 언제·어떻게 쓰는지 명시 ✓ 확인 · Sonnet 5 = 기본은 도구를 더 잘 부르지만 thinking 을 끄면 덜 부름 → 시스템 프롬프트에 분명한 nudge ✓ 확인

    그 밖 모델 = 모든 현재 모델 공통 절 : 최신 모델은 정확한 지시 따르기로 학습돼, 특정 도구를 쓰라는 명시적 지시가 도움이 됨 ✓ 확인

    → "센 표현은 항상 나쁨" 이 아니라 **증상 방향 먼저**. 공식이 "dial back" 을 콕 집은 건 Opus 4.5·4.6 (과잉) ✓ 확인

  3. ③

    규칙 + 이유 : 왜 중요한지 설명하면 목표를 더 잘 알고, 설명에서 일반화함. 예 "NEVER use ellipses" < "TTS 엔진이 읽으니 말줄임표 쓰지 마(발음 못 함)" ✓ 확인

    황금률 : 맥락 없는 동료가 읽고 헷갈리면 Claude 도 헷갈림 ✓ 확인

  4. ④

    할 것을 적기 : "하지 마" 대신 "이렇게 해" · 원하는 출력 문체에 프롬프트 문체를 맞춤(프롬프트에서 마크다운을 빼면 출력 마크다운도 줆) ✓ 확인

  5. ⑤

    역할 한 문장 + XML 칸막이 : 시스템 프롬프트에 적은 역할 문장이 행동·어조를 사용 사례에 모아 줌. 한 문장도 차이 남 — 공식 예 "You are a helpful coding assistant specializing in Python." ✓ 확인

    지시·맥락·예시·입력이 섞이면 각자 태그로. 태그 이름은 일관·설명적으로, 계층이 있으면 중첩(<documents> 안에 <document index="n">) ✓ 확인

    칸 나누는 형식(XML 태그 vs 마크다운 머리)의 중요도는 모델이 좋아질수록 줄어듦 ✓ 확인

  6. ⑥

    알맞은 고도(right altitude) : 한쪽 끝 = if-else 식 로직을 프롬프트에 박음(깨지기 쉽고 관리 부담) · 다른 끝 = 모호한 고수준 지침(구체 신호 없음, 공유 맥락 가정). 가운데 = 행동을 이끌 만큼 구체적 + 강한 휴리스틱을 줄 만큼 유연 ✓ 확인

    시작은 가장 좋은 모델로 최소 프롬프트 → failure modes(실패 유형) 보고 지시·예시를 더함 ✓ 확인 → 예시는 ■ few-shot 예시

    문자 그대로 따르는 모델(Opus 4.8·Sonnet 5) : 한 항목의 지시를 다른 항목으로 조용히 넓히지 않고, 안 한 요청을 추론하지 않음 → 넓게 적용하려면 범위를 적음 ✓ 확인

함정

  • ≠"경고를 더 세게(대문자·반복) 써서 규칙을 강조" → Opus 4.5·4.6 은 더 민감해 과잉 발동이 심해짐. 걷어내는 게 처방 ✓ 확인
  • ≠"센 표현을 걷어내면 어느 모델이든 해결" → 과소 발동(Opus 4.8)이면 반대. effort 올리기 + 언제·어떻게 쓰는지 적기 ✓ 확인
  • ≠"금지 규칙을 시스템 프롬프트에 크게 적으면 지켜짐" → 안내일 뿐 강제 아님 → ◆ 안내(프롬프트) vs 강제(구성·코드) · ■ 최소 권한
  • ≠"도구가 엉뚱하게 불리니 모델을 바꿈" → 문체(①)나 도구 설명(■ 도구 설계)부터 업계 일반 공식은 모델 교체를 처방으로 들지 않음
  • ≠"역할 문장만 넣으면 형식도 맞춰짐" → 역할은 행동·어조를 모음. 형식은 예시(■ few-shot 예시)·스키마(■ structured outputs) 업계 일반 역할의 효과 문장은 ✓ 확인
  • ≠Skilljar API 강의(2025 제작 추정) 예 "You are a patient math tutor. Do not directly answer…" → 역할 한 문장은 docs 와 같음. "하지 마" 문장은 docs 가 "할 것을 적기" 를 권하는 쪽

ELI5

새로 온 똑똑한 직원에게 업무 쪽지를 써 주는 거예요.

  • 소리 지르듯 "무조건 해!" 라고 쓰면, 필요 없을 때도 해 버려요.
  • "이럴 때 해 주세요, 왜냐하면…" 이라고 쓰면 비슷한 일도 알아서 잘해요.
  • 쪽지는 칸을 나눠 써야 뭐가 지시고 뭐가 자료인지 안 헷갈려요.
  • 그런데 어떤 직원은 쪽지를 글자 그대로만 읽어서, 범위까지 적어 줘야 해요.

원리

모델은 시스템 프롬프트의 말투 세기까지 신호로 읽음

  • 옛 모델은 도구를 잘 안 불러서(undertrigger) "CRITICAL: You MUST…" 로 세게 밀었음.
  • Opus 4.5·4.6 은 이전 모델보다 시스템 프롬프트에 더 민감 → 같은 센 표현이 이제 과잉 발동(overtrigger). Claude 4.6 모델들은 더 적극적(proactive)이라 옛 모델에 필요했던 "더 부지런히" 지시에도 과잉 발동.
  • 그래서 처방 = 말투를 보통으로 ("Use this tool when…"), 막연한 기본값("If in doubt, use [tool]") 지우기, 그래도 과하면 effort 낮추기.

방향은 모델마다 다름

  • Opus 4.8 은 반대 : 도구보다 추론(reasoning)을 선호 → 도구를 더 쓰게 하려면 effort(high·xhigh) + 언제·어떻게 쓰는지 명시.
  • Sonnet 5 는 기본으로 도구를 더 잘 부르지만 thinking 을 끄면 덜 부름 → 시스템 프롬프트에 분명한 nudge.
  • 그러니 "센 표현을 빼라" 는 규칙이 아니라 증상(과잉/과소) → 그 모델 → 처방 순서.

이유가 일반화를 만든다

  • 규칙만 주면 그 문장에만 반응. 이유를 주면 목표를 알고 비슷한 경우로 넓힘 ("Claude is smart enough to generalize from the explanation.").
  • 단, Opus 4.8·Sonnet 5 는 지시의 적용 범위는 문자 그대로 읽음 — 한 항목의 지시를 다른 항목으로 조용히 넓히지 않음. 이유로 "뜻"은 넓어지지만, "어디에 적용하나"는 적어 줘야 함.

칸막이와 고도

  • 지시·맥락·예시·입력이 섞이면 모델이 어디까지가 지시인지 헷갈림 → XML 태그로 칸. 형식(XML vs 마크다운 머리) 자체의 중요도는 모델이 좋아질수록 줄어듦.
  • 알맞은 고도 = if-else 하드코딩(깨지기 쉬움)과 모호한 고수준 지침(신호 없음) 사이.
  • 역할 한 문장 = 행동·어조를 사용 사례에 모음. 형식까지 보장하진 않음.

뒤집히는 때

1. "센 표현을 걷어내라" 가 반대로 되는 때

  • 조건 : 지문의 모델이 Opus 4.8 이고 증상이 "검색 도구를 안 부른다".
  • 판단 : 과소 발동. Opus 4.8 은 도구보다 추론을 선호 → 문구를 더 누그러뜨리면 더 안 부름. 처방은 effort 를 high·xhigh 로 + 왜·어떻게 쓰는지 분명히 적기.
  • 전제 : 도구 목록이 작고 설명이 겹치지 않음(겹치면 ■ 도구 설계 쪽).
  • 등급 : ✓ 확인
  • 근거 : prompting-claude-opus-4-8 en-full 61줄 · prompting-best-practices en-full 489줄(Opus 4.5·4.6 한정 문장)

2. 같은 Sonnet 5 인데 thinking 을 끈 때

  • 조건 : Sonnet 5, 지연(latency) 때문에 thinking: {type: "disabled"}, 도구 호출에 의존하는 흐름.
  • 판단 : 기본 Sonnet 5 는 도구를 더 잘 부르지만, thinking 을 끄면 도구·검색을 덜 고려 → "보통 말투로 낮춰라" 가 아니라 "시스템 프롬프트에 분명한 nudge" 가 답.
  • 등급 : ✓ 확인
  • 근거 : prompting-claude-sonnet-5 en-full 65줄

3. 이유를 붙였는데도 범위가 안 넓어지는 때

  • 조건 : Opus 4.8·Sonnet 5 를 low effort 로 돌림. "첫 절 제목은 굵게" 라는 지시가 나머지 12개 절에는 안 먹힘.
  • 판단 : 이유 부족이 아니라 문자 그대로 읽기. "모든 절에 적용" 처럼 범위를 명시.
  • 등급 : ✓ 확인
  • 근거 : opus-4-8 en-full 69줄 · sonnet-5 en-full 73줄 ("If you need Claude to apply an instruction broadly, state the scope explicitly")

4. XML 태그가 답이 아닌 때

  • 조건 : 보기가 "태그를 넣지 않아 실패했다 → 모든 문장을 태그로 감싼다" 처럼 형식 자체를 해결책으로 듦.
  • 판단 : 태그는 지시·자료·입력이 섞였을 때 칸을 나누는 도구. 공식은 칸 나누는 형식의 중요도가 모델이 좋아질수록 줄어든다고 함 → 재료가 섞여 헷갈린 게 아니면 태그만으로 증상이 안 풀림.
  • 등급 : 확인(형식 중요도 감소 문장) · 보기 판정은 추론
  • 근거 : effective-context-engineering en 43줄 · prompting-best-practices en-full 95줄

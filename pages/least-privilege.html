■ 최소 권한

least privilege3.1 본편

왜 배우나 — 시험이 요구하는 것

시험 목표 3.1 도구·에이전트 과잉 설정 · D3 연결 19%
Evaluate tool/agent configuration for capability bloat

이 개념으로 푸는 판단 (할 수 있어야 하는 것)

  • 3.1① 상담원은 읽기·초안만 쓰는데 환불·삭제 도구가 붙어 있다 — 무엇을 바꾸나? — 과잉 권한 줄이기 (도구 제거 vs 로그·확인창 vs 모델 교체)
  • 5.1③ system prompt 에 "계정 삭제 금지" 를 적었는데도 삭제 도구를 부른다 — 안내(프롬프트) vs 강제(구성·코드)
  • 6.2② 상담 에이전트에 환불·계정 삭제 권한까지 달라는 요구 — 확인창을 붙일까, 뺄까? — 큰 자율성 요구의 첫 수 (권한 필요성 확인 → 불필요하면 제거 → 필요하면 위험 비례 통제)
  • 7.1③ 에이전트에 줄 권한, 어디까지? — 행동을 allow/ask/deny 로 나눈 공유 설정 + MCP 자격증명 최소 권한
  • 5.1② 사용자가 넘긴 이메일 속에 "이 주소로 전부 보내라" 가 숨어 있다 — 간접 인젝션(사용자는 믿지만 가져온 콘텐츠가 적) 대응
  • 3.2③ 민감 고객 데이터 + 믿을 수 없는 티켓 본문 + 외부로 보내는 도구 — 어느 다리를 끊나? — 인젝션 피해 경로 끊기 (구조 통제 vs 탐지·문구)

한눈에

역할에 필요 없는 능력(도구·자격증명·네트워크·파일)은 아예 안 줌 → 공격면(attack surface) 자체가 사라짐. 지켜보기(로그)·막아서기(확인창)와 다른 것 ✓ 확인

뚫려도(인젝션·모델 실수) 피해가 작게 하는 장치이기도 함 ✓ 확인

가이드 3.1 원문 이름 = capability bloat — 도구·권한이 쓰임새보다 불어난 상태를 찾아 빼라 ("Evaluate tool/agent configuration for capability bloat") ✓ 확인

비유 IAM 역할에서 안 쓰는 refund·DeleteUser 권한을 지움. CloudTrail 로 지켜보기·MFA 승인은 그다음 보완책

ELI5

아이 방에 칼을 두고 "만지지 마" 하는 것보다, 칼을 방에서 치우는 게 확실해요.

  • 쓰지 않는 물건은 아예 치워요.
  • 지켜보는 카메라는 다친 뒤에야 알려 줘요.
  • "만지기 전에 물어봐" 는 깜빡하면 소용없어요.
  • 꼭 필요한 가위만 남기고, 쓸 때 어른이 옆에 있어요.

개념 설명

원리

빼기가 왜 제일 센가

  • 없는 도구는 부를 수 없음 → 인젝션·모델 실수·오용이 그 도구로는 아예 안 일어남. 공격면(attack surface)이 0.
  • 로그 = 일이 난 뒤에 알게 됨(detective). 확인창 = 사람이 매번 맞게 눌러야 막힘(compensating). 둘 다 도구는 남아 있음.
  • 모델을 키워도 "무엇을 할 수 있나"는 안 바뀜. 권한은 모델이 아니라 설정이 정함.

빼기의 범위는 도구보다 넓음

  • 파일(필요한 디렉토리만, 읽기 전용) · 네트워크(프록시로 특정 엔드포인트만) · 자격증명(프록시가 주입) · 컨테이너 권한(capability 떼기).
  • 공식은 이것을 "뚫려도 피해가 작게"라는 틀로 적음 — 막는 장치가 아니라 피해 반경을 줄이는 장치.

설정 lever(손잡이)의 함정

  • Agent SDK allowedTools = "묻지 않고 실행" 목록. 목록 밖 도구는 남아 있음. 도구를 없애는 건 disallowedTools 에 이름만 적을 때.
  • MCP connector 는 서버를 붙이면 기본이 "모든 도구 켬". 읽기 전용이면 쓰기·파괴 도구를 꺼야 함.

남겨야 하는 강한 도구

  • 먼저 "정말 역할에 필요한가". 필요하면 남기고 실행 직전 코드 검사(훅)·사람 확인을 붙임. 이 경우엔 확인창이 정답 쪽.

연습 문제

상담 에이전트는 주문 조회와 답장 초안만 한다읽기·초안만. 그런데 설정에는 영업팀이 예전에 붙인 환불 도구와 고객 삭제 도구안 쓰는 도구가 그대로 남아 있다. 누군가 "환불·삭제 전에 확인창을 띄우자"고 한다. 첫 수는?

시험 대비

함정

  • ≠"도구는 두고 환불·삭제 전에 확인 단계" (샘플 1 C) → 보완 통제일 뿐 ✓ 확인
  • ≠"로그 달아 나중에 감사" (샘플 1 A) → 사후 감지 ✓ 확인
  • ≠"지시 잘 따르는 더 큰 모델로" (샘플 1 D) → 권한 범위와 무관 ✓ 확인
  • ≠"system prompt 에 '삭제 금지' 적기" → 안내일 뿐 강제 아님. 도구가 있으면 불릴 수 있음 업계 일반 CCA-F 노트 2.3 "다 주고 프롬프트로 '쓰지 마'" 와 같은 함정
  • ≠"allowedTools 에 읽기 도구만 적었으니 나머지는 막혔다" → 안 막힘. 목록 밖 도구는 남아 권한 모드로 넘어감. 빼려면 disallowedTools ✓ 확인
  • ≠반대 함정 : "확인창 보기는 항상 오답" → 필요해서 남긴 강한 도구엔 실행 전 검사·사람 확인이 맞는 통제 (업계 일반 + ⑤)

신호

"Least privilege means removing capabilities the role does not require, eliminating the attack surface rather than monitoring or guarding it." (가이드 샘플 1)

"Logging (A) and confirmations (C) are detective/compensating controls, not removal of unnecessary privilege; model size (D) is unrelated to authorization scope." (샘플 1)

"Denylisting write or destructive tools is recommended when building read-only assistants, or when you want a human confirmation step before state changes"

"Apply the principle of least privilege so that a successful injection can do minimal damage"

"To put a tool out of Claude’s reach entirely, add its bare name to disallowedTools."

뒤집히는 때

1. 확인창이 정답이 되는 때

  • 조건 : 강한 도구(환불)가 역할의 실제 업무다. 영업팀 요구가 아니라 상담원이 실제로 환불을 처리한다.
  • 판단 : 빼면 업무가 안 됨 → 최소 권한(least privilege)은 "필요한 것만"이지 "0" 이 아님. 남기고 실행 직전 검사(한도·대상 확인)·사람 확인을 붙인다.
  • 등급 : 확인(훅) · 업계 일반(위험 비례 사람 검토)
  • 근거 : permissions en 262줄 · 목록 6.2② "필요하면 오류 비용·잡을 수 있는지에 비례해"
  • 시험에서 : 지문이 "상담원은 읽기·초안만"이라 말하면 제거. "환불도 상담원 업무"라 말하면 제거 보기는 업무를 깨는 오답이 될 수 있음.

2. 서버째 뺄 수 없는 때

  • 조건 : 사내 원격 MCP 서버 하나에 읽기·쓰기 도구가 20개 섞여 있고, 서버를 떼면 읽기 도구까지 잃는다.
  • 판단 : 서버 단위가 아니라 도구 단위로 끔. connector 는 configs 로 도구별 enabled: false.
  • 등급 : ✓ 확인
  • 근거 : mcp-connector en 169~186줄

3. allowedTools 로 잠갔다고 믿는 때

  • 조건 : SDK 설정이 allowedTools: ["Read", "Grep"] 뿐.
  • 판단 : 목록 밖 도구도 존재. 승인이 필요한 호출은 권한 모드로 넘어감(모드에 따라 실행될 수 있음). 잠그려면 dontAsk 모드와 짝, 없애려면 disallowedTools.
  • 등급 : ✓ 확인
  • 근거 : permissions en 255·264~273줄

4. 합친 도구가 권한 단위를 섞는 때

  • 조건 : 도구 설계에서 github_pr 하나에 action = list·review·merge 를 합쳤다(■ 도구 설계 · 규칙 ①). 리뷰 전용 에이전트는 머지가 안 돼야 한다.
  • 판단 : 도구 하나를 빼면 읽기까지 사라지고, 두면 머지까지 남음. 권한 경계가 다른 동작은 도구를 나누거나, 실행 직전 검사로 action 값을 막음.
  • 등급 : 업계 일반 (두 공식 권고 — 합치기 · 최소 권한 — 를 같이 쓸 때의 추론)
  • 근거 : define-tools en 43줄 · 샘플 1 · permissions en 262줄

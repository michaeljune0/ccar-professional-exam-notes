한눈에

ELI5

매일 똑같은 도시락을 싸는 가게와, 손님마다 주문이 다른 식당을 떠올려 보세요.

  • 도시락 가게는 순서표를 붙여 두고 그대로 나눠 만들어요.
  • 식당은 주방장이 주문서를 보고 그때그때 누구에게 뭘 시킬지 정해요.
  • 매일 같은 도시락인데 주방장이 매번 새로 나누면 시간만 더 들어요.
  • 이 쪽은 "순서표로 될 일인가, 주방장이 필요한 일인가"를 가르는 곳이에요.

개념 설명

원리

static decomposition(정적 분해) — 코드가 미리 나눔

  • 워크플로 = LLM 과 도구를 미리 정한 코드 경로로 엮음. 잘 정의된 일엔 예측 가능성·일관성을 줌.
  • prompt chaining(체이닝) : 앞 호출의 출력이 다음 호출의 입력. 사이에 코드 검사(gate)를 넣을 수 있음. 호출마다 쉬운 일로 만들어 정확도를 얻고, 그 대신 지연(latency)을 씀.
  • 나눠 돌리기(sectioning) : 서로 독립인 하위작업을 병렬로 돌린 뒤 코드가 모음. 조각끼리 독립이어야 성립.
  • routing(라우팅) : 입력을 분류해 전문 경로로 보냄. 입력이 다양해 보여도 유형 목록이 정해져 있으면 여기서 끝남.

dynamic decomposition(동적 분해) — orchestrator(지휘자)가 입력을 보고 나눔

  • orchestrator-workers(지휘자-일꾼) : 중앙 LLM 이 입력을 보고 하위작업을 정하고, worker LLM 에 맡기고, 결과를 합침.
  • 나눠 돌리기와 모양이 같음. 차이는 하위작업이 미리 정해졌느냐(정적) 입력이 정하느냐(동적) 하나.
  • 여전히 공식 글에선 "워크플로" 칸에 들어감. 에이전트는 그다음 칸.

에이전트

  • 단계 수조차 예측할 수 없고 경로를 미리 정해 둘 수 없는 열린 문제. LLM 이 자기 과정과 도구 사용을 스스로 정함.
  • 대가 : 비용↑ · 오류 누적 → 샌드박스 시험 + 가드레일.

맨 앞에 서는 원칙

  • 가장 단순한 것부터. 검색(retrieval) + 예시를 붙인 단일 호출로 충분한 경우가 많음. 복잡도(쪼개기 단계를 더하는 것)는 필요할 때만 올림.

핵심 질문 두 개

  • 하위작업 목록을 입력을 보기 전에 적을 수 있나?
  • 적을 수 있다면, 조각끼리 서로의 출력이 필요한가(prompt chaining), 독립인가(나눠 돌리기)?

연습 문제

고객지원 티켓이 들어올 때마다 의도 분류 · 감정 · 요약 세 판정을 늘 똑같이늘 같은 목록 해야 한다. 세 판정은 서로의 결과를 쓰지 않는다서로 독립. 팀은 "하위작업이 여러 개니 orchestrator(지휘자) LLM 이 나누게 하자"고 한다. 어떻게 쪼갤까?

시험 대비

함정

  • ≠"하위작업이 여러 개니 orchestrator-workers" → 하위작업이 여러 개라는 것만으로는 동적 이유가 안 됨. 먼저 미리 아는지 물음. 미리 알면 정적 ✓ 확인
  • ≠미리 아는 일(예 : 매 티켓 똑같은 세 판정 = 의도 분류·감정·요약)을 orchestrator 에게 → orchestrator 호출이 더 들고 예측 가능성을 내줌 업계 일반 호출 수는 공식 숫자 없음
  • ≠"유연한 쪽이 항상 낫다" → 잘 정의된 일엔 워크플로가 예측 가능·일관. 에이전트 자율 = 비용↑ · 오류 누적 ✓ 확인
  • ≠"prompt chaining 으로 나누면 더 빠르고 싸다" → prompt chaining 은 지연을 내주고 정확도를 얻음 ✓ 확인
  • ≠"병렬로 나누면 무조건 이득" → 조각끼리 독립일 때만 ✓ 확인
  • ≠"입력마다 다르니 무조건 동적" → 유형이 몇 가지로 정해져 있고 분류가 정확하면 routing(정적)으로 충분 ✓ 확인 → ■ 워크플로 5패턴
  • ≠"orchestrator-workers = 멀티 에이전트" → 공식 글에선 워크플로 패턴 하나(중앙 LLM + worker LLM). 멀티 에이전트 비용 판단은 ◆ 단일 vs 멀티 에이전트 ✓ 확인

신호

"This workflow is ideal for situations where the task can be easily and cleanly decomposed into fixed subtasks."

"The main goal is to trade off latency for higher accuracy, by making each LLM call an easier task."

"subtasks aren't pre-defined, but determined by the orchestrator based on the specific input."

"Breaking a task into independent subtasks run in parallel."

"workflows offer predictability and consistency for well-defined tasks, whereas agents are the better option when flexibility and model-driven decision-making are needed at scale."

"Agents can be used for open-ended problems where it’s difficult or impossible to predict the required number of steps, and where you can’t hardcode a fixed path."

"always focus on implementing workflows where possible, and only resort to agents when they are truly required." (Skilljar)

더 깊이 : 뒤집히는 때 · 오답 재료 (설명)

뒤집히는 때

1. "입력마다 달라 보이는데" routing 으로 끝나는 때

  • 조건 : 고객 문의가 일반 질문 · 환불 · 기술 지원으로 들어옴. 문의마다 처리 경로가 다름.
  • 판단 : 경로가 다를 뿐 경로 목록은 정해져 있음(3개). 분류가 정확하면 routing = 정적. orchestrator-workers 는 하위작업 "목록 자체"가 입력마다 바뀔 때.
  • 등급 : ✓ 확인
  • 근거 : building-effective-agents en 76·80줄 (고객 문의 유형을 다른 프로세스·프롬프트·도구로 보내는 공식 예)

2. 고정 목록인데 병렬이 깨지는 때

  • 조건 : 티켓 한 건에 "환불 가능 판정"과 "답장 초안"을 나눠 병렬로 돌림.
  • 판단 : 답장 초안이 환불 판정 결과를 알아야 함 → 독립이 아님 → sectioning(나눠 돌리기)이 아니라 prompt chaining(판정 → 초안). 목록이 고정이라는 것만으로 병렬이 되진 않음.
  • 등급 : ✓ 확인 (독립 조건 · prompt chaining 정의) — 이 예시 자체는 새로 만든 것
  • 근거 : en 55·87줄

3. prompt chaining 이 지연 예산을 넘는 때

  • 조건 : 3단계 prompt chaining, 단계마다 약 1.2초 → 합 약 3.6초. 약속한 응답 지연이 2.5초.
  • 판단 : prompt chaining 은 지연을 내주고 정확도를 얻는 거래라 예산을 넘으면 단계 수를 줄이거나, 독립인 단계는 병렬로 돌리거나, 한 호출 안에서 thinking(사고)으로 처리. → ■ decomposition 단위 정하기 · ■ 지연 줄이기 lever
  • 등급 : 업계 일반 (단계당 시간은 가정 숫자 · 공식 숫자 없음). 거래 방향 자체는 확인.
  • 근거 : en 61줄 · prompting-best-practices en 404줄

4. 동적이 맞는데 멀티 에이전트까진 아닌 때

  • 조건 : 요청마다 고칠 파일 수가 다른 버그 수정.
  • 판단 : dynamic decomposition(orchestrator-workers)은 맞음. 하지만 코딩은 진짜 병렬 조각이 적어 작업 가치가 멀티 에이전트 비용(채팅 대비 약 15배)을 넘기 어려움 → 비용 판단은 ◆ 단일 vs 멀티 에이전트.
  • 등급 : ✓ 확인
  • 근거 : en 113줄 · multi-agent-research-system en 21줄

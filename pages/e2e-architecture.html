■ input → processing → output → feedback loop

end-to-end architecture · 입력 → 처리 → 출력 → 되먹임1.2 본편아래 설명 보기

카드

칸마다 맡는 일을 나눔. 입력 = 모델이 보기 전에 거름 · 처리 = 검색(retrieval)·도구·가드레일·사람 확인을 붙인 LLM(augmented LLM) · 출력 = 스키마로 받아 뒤쪽 코드가 추측 없이 씀 · feedback loop(되먹임) = 실패를 테스트 과제로 바꿔 프롬프트·설정 개선으로 되돌림 ✓ 확인

비유 알림은 오는데 사후 분석 → 런북 개선이 안 도는 팀. feedback loop 칸이 빠지면 같은 장애가 반복됨. "대시보드를 만들었으니 feedback loop 끝"이 속이는 습관

지문

자동차 보험 고객지원 Agent 가 같은 해지 수수료 오답을 3주째 반복한다몇 주째 반복. 고객 신고는 지원 큐에 로그로 쌓이기만 하고, 입력 선별과 JSON 출력은 잘 돈다. 팀은 "더 큰 모델로 바꾸자"고 한다. 어느 칸을 고칠까?

흐름

나머지 규칙

  1. ⑤

    칸 사이 약속은 스키마 : 입력 선별 판정 · 도구 입력 · 최종 출력 모두 스키마로 받으면 칸마다 뒤쪽 코드가 추측 안 함 ✓ 확인 (JSON outputs + strict tool use 는 같은 요청에서 같이 씀)

규칙 원문 ①②③④ (갈림길로 그린 규칙)
  1. ①

    입력 : 모델이 보기 전에 거름. 가벼운 모델(Haiku 4.5)로 사용자 입력 사전 선별 + 알려진 인젝션 패턴 필터, 판정은 구조화 출력으로 받아 앱이 분기 ✓ 확인 → ■ 프롬프트 인젝션 피해 경로 끊기 [1.2①]

    선별을 주 응답과 따로(병렬) 돌리면, 한 호출이 가드레일과 답을 둘 다 하는 것보다 나음 ✓ 확인

  2. ②

    처리 : 보강된 LLM(augmented LLM) = 검색·도구·메모리를 붙인 LLM ✓ 확인. 정적 지식은 검색(RAG) · 실시간 값은 임베딩 RAG 로 부족 → 도구로 조회 ✓ 확인 [1.2①]

    가드레일 = 환각(hallucination) 줄이기(인용·사실 확인) · 정책 교차 확인 · 권한 없는 약속 금지 · PII 제거 ✓ 확인

    사람 확인 지점 = 체크포인트나 막힐 때 사람에게 돌아옴 ✓ 확인

    루프는 앱이 쥠 : 응답의 stop_reason 으로 다음 단계를 정함 (1.2② 본편) ✓ 확인 (Skilljar)

  3. ③

    출력 : 구조화 출력 = JSON outputs(output_config.format) + strict tool use(strict: true). 항상 파싱되는 JSON · 필수 필드·타입 보장 · 스키마 위반 재시도 불필요 ✓ 확인 [1.2①]

    예외 : refusal(HTTP 200, 거절이 스키마보다 우선) · max_tokens(잘림 → 더 큰 값으로 재시도) · enum 대소문자는 보장 안 됨, 오류 없이 옴 → 대소문자 무시 비교 ✓ 확인

    같이 못 씀 : 인용(citations)과 JSON outputs 는 400 · 메시지 prefill 도 JSON outputs 와 호환 안 됨 ✓ 확인

    strict 도구는 요청당 20개까지 → 스키마가 깨지면 곤란한 도구만 strict ✓ 확인

  4. ④

    feedback loop : 성공 기준(success criteria) → 평가 → 개선이 한 바퀴 ✓ 확인. 실패(사용자 신고·지원 큐)를 테스트 과제로 바꿔야 regression 을 막음 · 실제 사용도 반영 ✓ 확인 [1.2①]

    출시 전·변경마다 = 자동 eval(변경·모델 업그레이드마다 도는 첫 방어선) · 출시 뒤 = 운영 감시(분포 변화·예상 못 한 실패) · 사용자 피드백 · 대화 기록 읽기 ✓ 확인 → ■ observability 세 신호 · ■ 성공 기준

함정

  • ≠"같은 오답이 몇 주째 → 더 큰 모델로" → feedback loop 칸이 빠진 것(로그만 쌓이고 평가 과제로 안 바뀜). 쌓인 실패를 테스트 과제로 ✓ 확인 · 모델 크기로 feedback loop 가 생기진 않음 업계 일반
  • ≠"출력은 자유 문장으로 받고 정규식으로 파싱" → 파싱 오류·필수 필드 누락, 뒤쪽 코드가 추측해야 함. 구조화 출력 ✓ 확인
  • ≠"assistant 메시지 prefill + stop sequence 로 JSON 만 받기" (Skilljar API 2025 강의) → 지금은 구조화 출력. prefill 은 Opus 4.6 미지원(2026-02-05) · Fable 5·Mythos 5 는 400(2026-06-09) · JSON outputs 와도 호환 안 됨 ✓ 확인
  • ≠"스키마를 걸었으니 오류 처리 필요 없음" → refusal · max_tokens 는 스키마와 안 맞을 수 있음 ✓ 확인
  • ≠"대시보드가 있으니 feedback loop 끝" → 운영 감시는 사후 대응(문제가 사용자에게 먼저 닿음). 평가 없이는 하나 고치면 다른 게 깨지는 사후 대응 루프 — 잡은 실패를 테스트로 바꿔야 루프 ✓ 확인
  • ≠"실시간 잔액도 RAG 로" → 도구 ✓ 확인
  • ≠"사용자 피드백만 모으면 됨" → 드물고 심각한 쪽으로 치우침, 왜 틀렸는지 거의 안 적음 ✓ 확인

ELI5

식당 주방을 네 칸으로 나누는 거예요.

  • 입구에서 상한 재료를 먼저 골라내요(입력).
  • 요리사는 레시피·도구·맛보기를 곁에 두고 요리해요(처리).
  • 접시 모양이 정해져 있어야 서빙하는 사람이 헷갈리지 않아요(출력).
  • 손님이 남긴 음식을 보고 레시피를 고쳐야 다음엔 안 남겨요(되먹임).

원리

입력 칸 — 모델이 보기 전에 거름

  • 가벼운 모델(Haiku 4.5)로 사용자 입력을 미리 분류 + 알려진 인젝션 패턴 필터. 판정은 구조화 출력으로 받아 앱이 분기.
  • 같은 선별을 도구 결과에도 적용(도구가 가져온 글도 믿을 수 없는 입력) → ■ 프롬프트 인젝션 피해 경로 끊기.
  • 선별을 주 응답과 따로 돌리는 편이 한 호출이 둘 다 하는 것보다 나음(병렬화 — 가드레일 예).

처리 칸 — 보강된 LLM

  • augmented LLM = 검색(retrieval) · 도구 · 메모리를 붙인 LLM. 모델이 검색어를 만들고 도구를 고르고 무엇을 기억할지 정함.
  • 정적 지식은 검색(RAG), 잔액·주문 같은 실시간 값은 임베딩 RAG 로 부족 → 도구.
  • 가드레일 : 환각(hallucination) 줄이기(인용·사실 확인) · 정책 교차 확인 · 권한 없는 약속 금지 · PII 제거.
  • 사람 확인 지점 : 에이전트는 체크포인트나 막힐 때 사람에게 돌아옴.
  • 루프는 앱이 쥠 : stop_reason 으로 다음 단계를 정함(1.2②). "You own the loop and the tools. Claude owns the reasoning." (Skilljar)

출력 칸 — 스키마

  • 구조화 출력 = JSON outputs(output_config.format, 답의 모양) + strict tool use(strict: true, 도구 입력의 모양). 제약 디코딩으로 스키마 준수 보장.
  • 없으면 : 파싱 오류 · 필수 필드 누락 · 타입 불일치 · 재시도 로직.
  • 예외 셋 : refusal(HTTP 200, 거절이 스키마보다 우선) · max_tokens(잘림) · enum 대소문자(오류 없이 다르게 옴).

feedback loop(되먹임) 칸 — 실패를 테스트로

  • 성공 기준(success criteria) → 평가 → 개선 사이클. 실패(사용자 신고·지원 큐)를 테스트 과제로 바꿔야 실제 사용을 반영하고 regression(회귀)을 막음.
  • 출시 전·변경마다 = 자동 eval(첫 방어선). 출시 뒤 = 운영(production) 감시(분포 변화·예상 못 한 실패) · 사용자 피드백 · 대화 기록 읽기. 한 겹이 모든 걸 못 잡음(스위스 치즈 — 구멍 난 겹을 여러 장 겹쳐 막음).
  • 운영 감시만 있으면 사후 대응 — 문제가 사용자에게 먼저 닿음.

핵심 질문 두 개

  • 칸 사이에 넘어가는 것(판정 · 도구 입력 · 최종 답)이 스키마로 정해져 있나?
  • 운영에서 잡힌 실패가 다음 평가 묶음으로 들어가는 길이 있나?

뒤집히는 때

1. 입력 선별이 지연(latency)을 늘리는 때

  • 조건 : 모든 채팅에 선별 호출을 앞에 붙였더니 첫 답이 늦어짐.
  • 판단 : 선별을 순서대로(앞에) 두지 말고 주 응답과 병렬로 → 선별이 "막아야 함"이면 주 응답을 버림. 공식도 분류기 추가는 추가 호출이라 지연을 늘릴 수 있다고 적음.
  • 등급 : 확인(병렬 가드레일 · 추가 호출 지연) · 버리는 운용은 업계 일반
  • 근거 : building-effective-agents en 99줄 · customer-support-chat en 1192줄

2. 스키마가 오히려 막는 때

  • 조건 : 정책 답변에 조항 인용을 반드시 붙여야 하고, 앱이 JSON 으로도 받고 싶음.
  • 판단 : 인용(citations) + JSON outputs 는 400. 인용이 핵심이면 인용 기능을 쓰고 JSON 은 포기, JSON 이 핵심이면 인용 필드를 스키마 안에 직접 둠(업계 일반).
  • 등급 : 확인(충돌) · 우회는 업계 일반
  • 근거 : structured-outputs en 253줄

3. 스키마를 걸었는데도 안 맞는 때

  • 조건 : 구조화 출력 켬. 하루 수만 건 중 일부가 파싱 실패.
  • 판단 : stop_reason 부터 봄. refusal = 거절이 스키마보다 우선(HTTP 200, 토큰 과금) · max_tokens = 잘림 → 더 큰 값으로 재시도. 정상 종료인데 값이 다르면 enum 대소문자 → 대소문자 무시 비교.
  • 등급 : ✓ 확인
  • 근거 : structured-outputs ko 171~201줄

4. feedback loop 를 사용자 피드백에만 기대는 때

  • 조건 : "싫어요" 버튼 수만 봄.
  • 판단 : 사용자 피드백은 드물고 스스로 고른 사람만 누르고, 심각한 쪽으로 치우치고, 왜 틀렸는지 거의 안 적음. 자동 eval · 운영 감시 · 대화 기록 읽기와 겹쳐야 함.
  • 등급 : ✓ 확인
  • 근거 : demystifying-evals en 298·306줄

5. strict 를 전부 켜려는 때

  • 조건 : 도구 26개에 전부 strict: true.
  • 판단 : strict 도구는 요청당 20개 상한 · 선택 파라미터 합계 24개 상한. 스키마가 깨지면 곤란한 도구만 strict, 나머지는 모델의 기본 준수에 맡김.
  • 등급 : ✓ 확인
  • 근거 : structured-outputs en 213·214·227줄

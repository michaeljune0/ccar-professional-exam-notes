대부분 한 지표로 안 끝남 → 여러 성공 기준(success criteria)으로 다차원 평가 ✓ 확인

비유 SLO 대시보드. 서비스 안쪽 지표(오류율·지연(latency))와 사업 지표(주문·이탈)를 따로 걸고, 가용성 하나로 "성공"이라 안 함

ELI5

새 직원을 뽑고 "잘하나?"를 볼 때 두 가지를 따로 봐요.

  • 하나는 맡긴 일을 제대로 하나예요. 주문을 맞게 받았나, 모를 땐 선배를 불렀나.
  • 다른 하나는 가게가 나아졌나예요. 손님이 덜 기다리나, 만족했나.
  • "손님 반응이 좋았어요" 같은 말로는 못 정해요. 숫자를 미리 정해 둬야 해요.
  • 숫자 하나만 보면 속아요. 여러 개를 같이 봐요.

개념 설명

원리

두 겹

  • 과제 지표 = Claude 가 맡은 과제 하나하나를 잘 하나. 대화 표본 검토 · LLM 채점으로 잰다. 어디가 깨졌는지를 알려 줌.
  • 사업 영향 지표 = 도입해서 사업이 달라졌나. 사람 없이 끝난 비율(deflection) · 만족도(CSAT) · 처리 시간(AHT) · 감정 유지. 넓힐지 말지를 정하는 데 씀.
  • 과제 지표가 좋아도 사업 지표가 안 오를 수 있고, 사업 지표만 보면 원인을 못 찾음 (업계 일반) → 두 겹을 같이 건다.

목표치는 만들기 전에

  • 공식 고객지원 가이드는 과제 정의 → 성공 기준(success criteria) 수립 → 구현 순서. 성공 기준은 지원 팀과 같이 정하고 측정 가능한 벤치마크를 붙인다.
  • 좋은 기준 4가지 = 구체적 · 측정 가능 · 달성 가능 · 관련성. "달성 가능"의 기준은 업계 벤치마크 · 이전 실험 · 현재 프런티어 모델 역량.
  • 모호한 것도 숫자로 바꾼다 (안전 = 10,000회 중 유해 플래그 0.1% 미만).

여러 차원

  • 대부분 한 지표로 안 끝남 → 정확도 + 무해성 + 응답 시간처럼 여러 기준을 한 목표에 묶는다.
  • 흔한 기준 목록에 지연(latency)·가격도 들어감 → 비용은 ■ per-request cost, 지연은 ■ 지연 줄이기 lever.

목표치의 성격

  • 좁은 사실 과제(프롬프트에 넣어 준 회사·상품 정보, 견적)는 100% 가 공식 목표.
  • 사람 판단에 좌우되는 결과(deflection 등)는 70~80%, 문의 복잡성에 따라 → 100% 가 아님.

프롬프트에 넣어 준 정보 · 견적의 정확도 목표 100% ✓ 확인 customer-support-chat ko 144·156줄

연습 문제

자동차 보험 챗봇 도입안에 "견적 금액 정확도 100%" 와 나란히 "문의 100% 를 사람 없이 끝낸다"100% 목표가 적혀 있다. 뒤쪽 숫자는 사람 개입 없이 챗봇이 처리한 문의 비율자동 해결률을 말한다. 이 뒤쪽 목표를 어떻게 고칠까?

시험 대비

함정

  • ≠"100% 자동 해결을 목표로" → deflection 공식 목표는 70~80%, 달성 가능해야 ✓ 확인
  • ≠반대로 "100% 목표는 늘 오답" → 프롬프트에 넣어 준 회사·상품 정보 · 견적 정확도는 공식이 100% ✓ 확인
  • ≠"deflection 만 올리면 성공" → 에스컬레이션 정확도를 같이 안 보면 사람에게 넘겨야 할 대화를 챗봇이 붙잡아도 deflection 숫자는 좋아 보임 업계 일반
  • ≠"고객 반응이 좋았다"로 확대 결정 → 측정 가능한 목표치가 없음 ✓ 확인
  • ≠과제 지표만 보고 사업 효과를 말함 / 사업 지표만 보고 어느 과제가 깨졌는지 모름 → 두 겹 다 업계 일반
  • ≠한국어판 "전환율" 을 value pillars 의 "전환" 으로 읽음 → deflection rate 임 ✓ 확인
  • ≠성공 기준 = "SMART 5가지(기한 포함)" → 공식은 4가지(Specific · Measurable · Achievable · Relevant) ✓ 확인

신호

"Here are criteria and benchmarks that can be used to evaluate the business impact of employing Claude for support:"

"Typically aim for 70-80% deflection rate, depending on the complexity of inquiries."

"Aim for a CSAT score of 4 out of 5 or higher."

"Aim for an escalation accuracy of 95% or higher."

"Most use cases need multidimensional evaluation along several success criteria."

"Your success metrics should not be unrealistic to current frontier model capabilities."

더 깊이 : 뒤집히는 때 · 오답 재료 (설명)

뒤집히는 때

1. deflection 이 올랐는데 실패인 때

  • 조건 : deflection 을 끌어올리려고 사람에게 넘기는 기준을 느슨하게 함.
  • 계산 : 월 2만 5천 건 중 사람이 꼭 봐야 할 문의가 16%(4,000건)라고 둠. 에스컬레이션 정확도 95% → 못 넘긴 대화 200건. 86% 로 떨어지면 560건 → 사람이 필요한 고객 360명이 더 챗봇에 묶임. deflection 숫자는 오히려 올라감.
  • 전제 : 에스컬레이션 정확도 = 넘겨야 할 대화 중 제대로 넘긴 비율로 봄 (공식은 "제대로 넘긴 대화 vs 넘겨야 했는데 안 넘긴 대화"를 추적하라고만 씀).
  • 등급 : 계산. 두 지표를 같이 걸라는 방향은 공식 다차원 원칙과 같음. "한쪽을 올리면 다른 쪽이 내려간다"는 문장 자체는 공식에 없음(업계 일반).
  • 근거 : customer-support-chat ko 160·172줄 · define-success en-full 96줄

2. 100% 목표가 맞는 때

  • 조건 : 지문이 "프롬프트에 넣어 준 회사 정보" · "견적 금액"처럼 좁은 사실 과제의 정확도를 물음.
  • 판단 : 공식 목표가 100%. "100% 는 비현실이니 오답"으로 외우면 여기서 틀림. 100% 가 오답인 건 자동 해결률·사람 판단에 좌우되는 결과 쪽.
  • 등급 : ✓ 확인
  • 근거 : customer-support-chat ko 144·156줄

3. 공식 목표치를 그대로 쓰면 안 되는 때

  • 조건 : 업무가 고객지원이 아님 (예 계약서 조항 추출).
  • 판단 : 70~80% · 4/5 · 95% 는 고객지원 예의 벤치마크. 다른 업무는 업계 벤치마크 · 이전 실험 · 현재 모델 역량으로 새로 정함 ("달성 가능").
  • 등급 : ✓ 확인 (원칙) · 다른 업무의 숫자는 공식 없음
  • 근거 : define-success ko 16줄

4. AHT 를 줄였는데 실패인 때

  • 조건 : 답을 짧게 끊어 평균 처리 시간을 낮춤.
  • 판단 : AHT 목표는 "사람 상담원보다 낮게"뿐. 끊어서 줄이면 CSAT · 감정 유지가 떨어질 수 있어 같이 봐야 함.
  • 등급 : 업계 일반 (두 지표는 공식 목록, 상충 설명은 없음)
  • 근거 : customer-support-chat ko 168·176·180줄

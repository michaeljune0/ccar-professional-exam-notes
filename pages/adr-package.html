이 개념으로 푸는 판단 (할 수 있어야 하는 것)

  • 6.4① 몇 달 뒤 팀이 "왜 RAG 로 했지?" 를 처음부터 다시 논쟁한다 — 인계 때 무엇이 빠졌나? (빈 목표) — 결정 기록(ADR)과 아키텍처 패키지의 목적
  • 6.4③ ADR 에 "100쪽 계약은 context rot 때문에 RAG" 라고 적었다 — 이 근거가 맞나? — ADR 근거를 공식 기준·평가 증거로 적기 (크기 기준부터 확인)

한눈에

결정마다 한 장씩 "무엇을 골랐나 · 왜(맥락·제약·증거) · 무엇을 버렸나(기각된 대안과 이유)" 를 남김. 목적 = 사람이 바뀌어도 정해진 trade-off(절충)가 다시 논쟁되지 않음 업계 일반 ADR 양식은 Anthropic 문서 없음, 양식 암기보다 목적

공식에서 가장 가까운 원칙 : 코드에서 못 읽는 것만 적음. 프로젝트 고유의 구조 결정은 넣고, 코드를 읽으면 알 수 있는 건 뺌 ✓ 확인 (Claude Code CLAUDE.md 규칙 — 사람 팀 문서로 넓힌 건 추론)

비유 "왜 EKS 대신 ECS 인가" 를 남긴 인프라 결정 기록. 없으면 새 팀원마다 같은 논쟁. "Slack 스레드에 다 있다" 가 속이는 습관

ELI5

이사 가면서 새 집주인에게 "왜 이 벽에 선반을 달았는지" 쪽지를 남기는 거예요.

  • 선반은 눈에 보여요. 그런데 "왜 여기에 달았는지"는 안 보여요.
  • 쪽지가 없으면 새 주인은 벽을 다시 재고, 같은 고민을 처음부터 해요.
  • 쪽지에는 "다른 벽은 습기가 차서 안 됐어요"처럼 버린 자리도 적어요.
  • 집이 바뀌면(벽을 새로 바르면) 쪽지도 새로 써요.

개념 설명

원리

ADR (architecture decision record) 한 장

  • 결정 · 맥락(문제·제약·위험·증거) · 기각된 대안과 이유. 양식(제목·상태·결과 칸)은 업계 일반이고 Anthropic 문서에 없음 → 시험은 양식보다 목적(재논쟁 방지)을 물을 것.
  • 코드는 "무엇"을 보여 주지만 "왜"와 "버린 안"은 안 보여 줌. 사람이 바뀌면 그게 사라짐 → 새 팀이 처음부터 다시 비교.

공식에서 가장 가까운 원칙 (Claude Code 가 읽는 문서, CLAUDE.md)

  • 넣을 것 = 프로젝트 고유의 구조 결정 · 흔한 함정. 뺄 것 = 코드를 읽으면 알 수 있는 것.
  • /doctor 는 구조 개요·디렉터리 배치처럼 코드로 알 수 있는 건 자르고, 함정·이유(rationale)는 남김.
  • 줄마다 "지우면 실수가 나나?" — 아니면 뺌. 길면 중요한 규칙이 묻힘.
  • 코드처럼 다룸 : 일이 틀어지면 검토 · 주기적으로 쳐냄 · git 에 넣어 팀이 기여 · 시간이 갈수록 쓸모가 쌓임.
  • 이 원칙들은 Claude 가 읽는 문서 기준. 사람 팀의 결정 기록에 그대로 옮긴 건 추론.

근거는 평가 증거

  • 공식 출발점 = 성공 기준(success criteria)을 정하고 평가를 설계. 평가가 있으면 숫자가 짐작을 대신함.
  • 그래서 ADR 의 "왜" 칸은 "좋아 보여서"가 아니라 평가셋 숫자(품질·지연(latency)·비용).
  • 근거 문장이 공식 기준과 어긋나면 기록이 있어도 틀린 결정이 굳음 (6.4③ : "context rot 이니 RAG" → 크기 먼저, ◆ RAG vs full context).

아키텍처 패키지

  • ADR 묶음 + 흐름 그림(입력→처리→출력→feedback loop(되먹임)) + 고른 패턴과 이유 + 모델 선택과 평가 근거 + 가드레일·규정 + 평가·모니터링 계획. 구성은 업계 일반(목록 6.4①).
  • 패턴 이름은 가이드 기준 3개 : workflow · agentic · augmented LLM.
  • ADR ≠ 패키지 전체. 구현 가이드·런북은 ■ 구현 가이드.

연습 문제

아키텍트가 떠나며 계약 검토 Agent 를 새 팀에 넘긴다. "왜 RAG 대신 full context(통째 넣기) + 캐싱인가" 는 코드를 읽어도 안 나온다코드에 없음. 아키텍트는 "근거는 슬랙 스레드에 다 있다채팅에 있음"고 한다. 이 결정의 근거를 어디에 어떻게 남길까?

시험 대비

함정

  • ≠"빠른 인계를 위해 코드·프롬프트만 넘기고 질문은 그때그때" → 코드엔 "무엇"만 있고 "왜"·기각 대안은 없음 → 새 팀이 처음부터 다시 비교 (업계 일반 · 가까운 공식 원칙 ✓ 확인 "코드로는 못 읽는 맥락")
  • ≠"결정 근거는 회의록·채팅에 다 있다" → 흩어져 새 팀이 못 찾음 업계 일반
  • ≠"ADR 하나에 다이어그램·구현 가이드·런북까지" → ADR = 결정 기록, 나머지는 패키지의 다른 문서 업계 일반 목록 영상 설명 교정
  • ≠"ADR 이 있으니 결정은 못 바꿈" → 전제가 바뀌면 새 ADR 로 대체 업계 일반
  • ≠"근거 = context rot 이니 RAG" → 공식 기준과 어긋난 근거. 크기 먼저 → ◆ RAG vs full context ✓ 확인
  • ≠"패턴은 workflow · agent 둘" → 가이드 기준 3개(augmented LLM 포함) ✓ 확인
  • ≠"결정마다 긴 설명·튜토리얼까지" → 긴 설명은 CLAUDE.md 에서 뺄 것 · 길면 중요한 규칙이 묻힘 ✓ 확인 (Claude 가 읽는 문서 기준)

더 깊이 : 뒤집히는 때 · 오답 재료 (설명)

뒤집히는 때

1. 기록한 결정이 뒤집혀야 맞는 때 — 전제(규모)가 바뀜

  • 조건 : ADR = "계약 1건(약 3만 토큰)씩 검토 → full context(통째 넣기) + 캐싱". 1년 뒤 요구가 "계약 800건 전체에서 같은 조항 찾기"로 바뀜.
  • 계산 : 800 × 3만 = 2,400만 토큰 → 1M 창도 한참 넘음 → 창에 안 들어가면 RAG 가 공식 기준.
  • 판단 : "ADR 이 있으니 못 바꿈"이 아니라 새 ADR 로 대체. 옛 ADR 은 지우지 않고 "대체됨" 표시 — 왜 처음엔 full context 였는지도 남아야 다음 사람이 헷갈리지 않음.
  • 등급 : 계산 (크기 기준 · 창 크기는 확인, 대체 절차는 업계 일반)
  • 근거 : contextual-retrieval en 11·19줄 · context-windows ko 23줄

2. 기록할 필요가 없는 때

  • 조건 : 코드만 보면 알 수 있는 결정(폴더 배치, 라이브러리 목록), 또는 쉽게 되돌리는 결정.
  • 판단 : 적으면 오히려 중요한 기록이 묻힘. Claude 문서 원칙 = 줄마다 "지우면 실수가 나나?".
  • 등급 : ✓ 확인 (Claude 문서 기준 — 사람 문서로 넓힌 건 추론)
  • 근거 : best-practices en 343·347줄 · memory en 844줄

3. 새 모델이 나왔는데 ADR 이 "Sonnet 으로 결정" 이라고 적혀 있을 때

  • 조건 : 모델 근거가 1년 전 평가셋 점수.
  • 판단 : 기록은 결론을 굳히는 게 아니라 "무엇이 달라졌나"를 묻게 함. 평가셋이 있으면 같은 셋을 새 모델로 돌려 며칠 안에 판단.
  • 등급 : ✓ 확인
  • 근거 : demystifying-evals en 50줄

4. 사람 문서 vs Claude 가 읽는 문서

  • 조건 : 같은 결정 기록을 사람 팀과 Claude Code(CLAUDE.md) 둘 다 봄.
  • 판단 : CLAUDE.md 는 매 세션 전부 읽혀 짧아야 하고, 긴 설명은 링크로 뺌. 사람용 ADR 은 더 길어도 됨 — 공식은 사람용 ADR 길이를 말하지 않음.
  • 등급 : 미해결 (사람 문서 기준 공식 문장 없음)
  • 근거 : best-practices en 343·349줄

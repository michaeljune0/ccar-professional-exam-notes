한눈에

보기마다 다른 최적화가 섞여 나오면 지문이 든 제약과 단서를 읽는다. 그리고 그 제약을 "가장 직접" 푸는 lever(조절 수단) 하나를 고른다. 필요한 것을 버리는 lever 는 탈락이다 (샘플 2)

  • 제약 : 비용 · 지연(latency) · 처리량
  • 단서 : 매번 같은 앞부분 · 마감 없음 · 첫 글자 기다림 · 장황

lever 본문은 각 카드에 있다. 여기는 단서와 lever 의 짝, 그리고 탈락 기준만 다룬다

비유 성능 튜닝과 같다. 병목(CPU·디스크·네트워크) 하나를 먼저 찾고, 거기에 맞는 lever 만 돌린다. 디스크 병목에 CPU 를 늘리면 돈만 쓴다

ELI5

막힌 수도관을 고치는 거예요. 어디가 막혔는지 보고 그 자리만 뚫어요.

  • 물이 늦게 나오면 꼭지 쪽을, 물값이 많이 나오면 새는 곳을 봐요.
  • 관을 잘라서 짧게 만들면 물은 빨리 오지만 필요한 방에 물이 안 가요.
  • 두 군데가 다 문제면 한 번에 둘 다 고치는 수리가 제일 좋아요.
  • 이 쪽은 "언제 다른 수리가 더 맞나"를 모아 둔 곳이에요.

개념 설명

원리

lever(조절 수단)마다 줄이는 것이 다르다

  • 캐싱 : 매번 같은 앞부분을 다시 읽지 않는다. 그래서 첫 토큰(TTFT)과 입력 비용이 같이 준다. 출력은 그대로다.
  • Batch : 급하지 않은 요청을 모아 입력·출력 모두 50% 할인받는다. 대신 끝나는 시각 약속이 없다.
  • 스트리밍 : 첫 글자가 먼저 보여 기다림이 짧게 느껴진다. 토큰 수와 총 시간은 그대로다 (업계 일반).
  • 출력 줄이기 : 생성 토큰이 줄어 전체 시간과 출력 비용이 같이 준다. 출력 단가가 입력의 5배라 효과가 크다.
  • effort : 한 모델 안에서 thinking(사고)·도구 호출·답의 토큰을 줄인다. 능력 일부를 내준다.
  • 라우팅 · 멀티 모델 : 쉬운 일은 싼 모델로 보낸다. 그러면 대부분 토큰이 낮은 요율로 처리된다.

"가장 직접" 의 뜻

  • 지문이 든 제약(예 : 지연(latency) + 비용)을 한 lever 가 다 풀면 그 lever 가 답이다. 한쪽만 풀면 약한 보기다.
  • 필요한 것을 버려서 얻는 절감(잘라내기 · 무작정 최소 모델)은 "직접" 이 아니다. 품질을 희생하는 trade-off(절충)라서 탈락이다.

핵심 질문 두 개

  • 이 지문이 말한 제약은 무엇인가(비용 · 지연 · 처리량 · 마감)?
  • 이 lever 는 그 제약을 전부 줄이나? 아니면 무엇을 잃나?

  1. ⑤

    측정 : eval 셋이 있으면 고정 과제 세트에서 아래 값을 기준선으로 본다. 그리고 lever 전후를 비교한다

    • 토큰 사용량
    • 작업당 비용
    • 오류율

    한 번에 여러 lever 를 켜면 어느 것이 효과인지 구분하지 못한다 업계 일반. 운영(production) 비용 추적은 ■ 비용 급증 추적 에 있다

    비용을 줄이는 공식 순서는 맞는 모델, 캐싱, 배치, 사용 패턴 감시다. 그 본문은 ■ per-request cost 에 있다

  2. ②

    "가장 직접" 은 지문이 든 제약을 한 lever 가 다 푸는가를 뜻한다. 지연과 비용이 둘 다 걸리면 캐싱이다(둘 다 줄인다). 스트리밍은 비용을 못 줄인다업계 일반. 배치는 지연을 늘린다 (샘플 2)

    여러 lever 가 다 맞으면 겹쳐 쓴다. 배치와 캐싱 할인은 곱해진다. 예는 설명 쪽 뒤집히는 때 1 에 있다

  3. ③

    탈락 기준은 둘이다

    • 필요한 것을 버리는 lever 다. 잘라내기(A)·과제 무시 최소 모델(B)·구조만 옮기기(D)가 여기에 든다 (샘플 2)
    • 지문에 없는 제약을 푸는 lever 다. 지연 문제에 배치를 쓰거나 비용 문제에 effort 를 올리는 것이 여기에 든다
  4. ④

    모델 쪽 순서 : 한 모델 안에서 effort 를 먼저 조정한다. 부족하면 모델을 바꾼다. 모델 교체나 다운은 eval 로 품질을 확인한 뒤에 한다

    난이도가 섞였으면 라우팅이나 멀티 모델을 쓴다

    • 라우팅 : 쉽고 흔한 것은 Haiku 급으로, 어렵고 드문 것은 큰 모델로 보낸다
    • 멀티 모델 : 실행자가 어려운 결정만 어드바이저로 올린다. 또는 orchestrator 가 대량 일을 싼 워커에 넘긴다

연습 문제

고객지원 Agent 는 요청마다 같은 환불·교환 정책 문서 8천 토큰을 맨 앞에 붙여같은 앞부분 보낸다. 상담원 화면의 첫 응답이 느리고 per-request cost(요청당 비용)도 줄이라지연·비용는 요구가 왔다. 팀원은 정책 문서를 앞 1,000 토큰만 남기고 자르자고 한다. 가장 직접 푸는 lever 는?

시험 대비

함정

  • ≠비용을 줄이려고 정책을 잘라내는 것, 과제를 무시하고 제일 작은 모델을 쓰는 것, 정책을 few-shot 블록으로 옮기는 것은 셋 다 오답이다 (샘플 2)
  • ≠지연과 비용이 둘 다 걸렸는데 "스트리밍" 을 고르는 것은 함정이다. 스트리밍은 체감만 바꾼다. 토큰 비용은 그대로다 업계 일반
  • ≠사람이 기다리는 일에 "배치로 50%" 를 고르는 것은 함정이다. 완료 시각 약속이 없다
  • ≠비용 문제에 "effort 올리기" 를 고르는 것은 함정이다. 토큰이 늘어 비용이 는다
  • ≠lever 를 한꺼번에 여러 개 켜는 것은 함정이다. 무엇이 먹혔는지 모른다. 근거 없는 조합이다 업계 일반
  • ≠캐싱 손익분기를 "요청 2~3회" 로 외우는 것은 함정이다. 5분 캐시는 읽기 1번부터, 1시간 캐시는 읽기 2번부터 이득이다
  • ≠"모델 교체는 항상 오답이다" 는 함정이다. effort 로도 모자라고 eval 로 품질을 확인했으면 맞는 답이다

신호

"Ordering stable content first and enabling prompt caching lets repeated prefixes be reused, reducing both time-to-first-token and per-request cost without discarding required context." (가이드 샘플 2)

"Truncation (A) loses needed policy; downsizing blindly (B) risks quality; relocating to few-shot (D) does not create a cacheable, reusable prefix." (가이드 샘플 2)

"Tuning effort is often a better lever than switching models."

뒤집히는 때

1. "lever 하나" 인데 둘을 겹치는 게 답인 때

  • 조건 : 매번 같은 앞부분 6천 토큰에 질문 300, 출력 500 이다. 밤새 처리하면 되는 일이다(마감 없음). 모델은 Sonnet 5 다.
  • 계산 (백만 토큰당 입력 $2 · 출력 $10 · 5분 쓰기 $2.50 · 읽기 $0.20, 배치 = 전부 × 0.5) :
    • 동기 · 캐시 없음 = 6,300 × $2 + 500 × $10 = $0.0126 + $0.005 = $0.0176
    • 동기 · 캐시 적중 = 6,000 × $0.20 + 300 × $2 + $0.005 = $0.0068
    • 배치만 = $0.0088
    • 미스면 쓰기 1.25배가 붙는다. 6,000 × $2.50 + $0.0006 + $0.005 = $0.0206
    • 배치 + 캐싱, 적중률 h : 0.5 × [h × $0.0068 + (1−h) × $0.0206]
    • h = 98% 면 약 $0.0035 다(배치만의 약 40%). h = 30% 면 약 $0.0082 다(배치만과 거의 같다).
  • 판단 : 제약이 "비용" 하나여도 단서 두 개(반복 앞부분 · 마감 없음)가 다 있으면 겹쳐 쓴다. 단 배치 안 캐시 적중은 보장이 없다(되는 만큼이다). 그래서 적중률이 낮으면 겹친 이득이 작다.
  • 전제 : 적중률 h 는 가정이다. 앞부분은 요청마다 같은 cache_control 블록이다. 가격은 2026-09-28 조회값이다.
  • 등급 : 계산 (배수·곱해짐은 확인)
  • 근거 : prompt-caching 표 · pricing · batch-vs-sync 카드(적중 보장 없음 · 30~98%)

2. "작은 모델로 내리면 싸다" 가 틀리는 때

  • 조건 : 앞부분 3천 토큰(매번 같다)에 질문 200, 출력 300 이다. Sonnet 5 에서 캐싱이 적중하고 있다. 비용을 더 줄이려 Haiku 4.5 로 내리자는 안이 나왔다.
  • 계산 :
    • Sonnet 5 캐시 적중 = 3,000 × $0.20 + 200 × $2 + 300 × $10 = $0.0006 + $0.0004 + $0.003 = $0.0040
    • Haiku 4.5 는 최소 캐시 길이 4,096 미만이라 캐싱이 안 된다. 3,200 × $1 + 300 × $5 = $0.0032 + $0.0015 = $0.0047
    • 단가가 절반인 모델로 내렸는데 요청당 약 18% 비싸다.
  • 전제 : 두 모델의 토큰 수가 같다고 봤다. 실제로 Sonnet 5 는 새 토크나이저라 같은 글을 약 30% 더 센다. 그러면 Sonnet 5 쪽이 약 $0.0052 가 되어 Haiku 가 약간 싸다. 결론은 이렇다. 단가표만 보고 "절반 값" 을 기대하면 틀린다. 캐싱 최소 길이와 토크나이저까지 넣어 계산해야 한다.
  • 등급 : 계산 (최소 길이·단가·토크나이저 30% 는 확인)
  • 근거 : prompt-caching · prompt-caching 표 · 릴리스 노트

3. 라우팅이 손해인 때

  • 조건 : 분류 쿼리다. 쿼리당 입력 1,500, 출력 200 이다. 지금은 전부 Opus 5.5($4/$20)로 처리한다. 라우터는 Haiku 4.5 한 번이다(입력 1,500 · 출력 10).
  • 계산 :
    • Opus 5.5 전부 = 1,500 × $4 + 200 × $20 = $0.010
    • Haiku 4.5 한 건 = 1,500 × $1 + 200 × $5 = $0.0025 · 라우터 = $0.00155
    • 쉬운 비율 90% 면 $0.00155 + 0.9 × $0.0025 + 0.1 × $0.010 = $0.0048 이다(약 52% 절감).
    • 쉬운 비율 30% 면 $0.0093 이다(약 7% 절감). 오분류 위험까지 지면 이득이 약하다.
    • 손익 : $0.00155 = s × $0.0075 이므로 s ≈ 21% 다. 쉬운 쿼리가 약 21% 미만이면 라우터 비용 때문에 더 비싸다.
  • 판단 : 난이도가 대부분 쉬울 때만 라우팅한다. 섞였어도 어려운 쪽이 많으면 effort 조정이 먼저다.
  • 전제 : 두 모델의 토큰 수가 같다고 봤다. 오분류 비용은 뺐다. 가격은 2026-09-28 조회값이다.
  • 등급 : 계산
  • 근거 : prompt-caching 표 · building-effective-agents · choosing-a-model

4. 스트리밍이 정답인 때

  • 조건 : 제약이 "사용자가 답이 늦게 뜬다고 느낌" 하나뿐이다. 비용 말은 없다.
  • 판단 : 스트리밍이 가장 직접이다. 캐싱은 앞부분이 매번 같을 때만 맞다. 출력 줄이기는 답 내용을 바꾼다. 지문이 "첫 글자까지" 인지 "다 받기까지" 인지 먼저 구분한다. 자세한 것은 ◆ TTFT vs 응답 완료 지연 에 있다.
  • 등급 : (스트리밍 = 체감) · 업계 일반 (총 시간 그대로)
  • 근거 : reduce-latency

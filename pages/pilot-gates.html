한눈에

단계와 단계 사이의 문(게이트). PoC(고른 사례로 "되나?") → 파일럿(pilot · 실제 트래픽 일부에서 미리 정한 선을 넘나?) → 확장(한 조각씩 넓힘). 문마다 들어가는 조건을 **들어가기 전에** 정함 업계 일반 단계 이름·게이트 구성은 Anthropic 문서 없음

공식에서 가장 가까운 것 : 프로토타입 단계를 지나 운영(production)에서 커지기 시작하면 eval 없이 짓는 방식이 무너짐 ✓ 확인 · 프로토타입 → 운영이면 비용이 일급 설계 제약 ✓ 확인 · 이긴 구성은 전환 전에 트래픽 일부에 shadow 로 ✓ 확인 (좁은 문맥 — 게이트로 넓힌 건 해석)

5단계 이름과 되돌아갈 곳은 ■ lifecycle 루프, 변경마다 eval 은 ■ 변경마다 eval 다시, 사업 지표 목록은 ■ impact metrics. 여기는 단계 **사이의 문** — 들어가는 조건 · 넓힐 근거 · 새 목적 판정

비유 카나리 배포 승격 조건 — 오류율·지연 선과 자동 중단 조건을 배포 전에 걸고, 1% → 10% → 50% 로 한 단씩. "스테이징에서 잘 돌았으니 전체 배포" 가 속이는 습관

새 놀이기구를 여는 순서예요.

  • 먼저 직원 몇 명이 타 봐요. "움직이긴 하네" 까지만 알 수 있어요.
  • 손님을 받기 전에 "몇 분 안에 끝나야 통과, 한 번이라도 멈추면 닫음, 결정은 누가" 를 먼저 정해요.
  • 그다음 손님 일부만 태워 보고, 정한 선을 넘는지 봐요.
  • 넘으면 줄 하나씩 늘려요. 한꺼번에 다 열지 않아요.
  • 놀이기구를 식당으로 바꾸면, 그건 새 가게라서 처음부터 다시 정해요.

개념 설명

원리

세 단계는 묻는 게 다름 (업계 일반 — 단계 정의는 공식 문서 없음)

  • PoC : 고른 사례로 "되나?" — 능력의 증거.
  • 파일럿 : 실제 트래픽 일부 · 좁힌 권한에서 "미리 정한 선을 넘나?" — 가설 검증.
  • 확장 : 한 조각씩 넓히며 "다른 입력에서도 유지되나?".
  • 공식 조각 : 프로토타입 단계를 지나 운영에서 커지기 시작하면 eval 없이 짓는 방식이 무너짐 (demystifying-evals en 38줄). 프로토타입 → 운영이면 비용이 일급 설계 제약 (optimizing-cost-intelligence en 1줄).

왜 기준을 먼저 (업계 일반)

  • 결과를 본 뒤에 기준을 정하면, 기준이 결과에 맞춰짐 → 사후에 판정할 수 없음.
  • 중단 규칙이 없으면 나쁜 일이 생겨도 "조금만 더" 가 됨.
  • 결정할 사람이 없으면 모두 의견만 내고 아무도 go/no-go 를 안 냄.

왜 데모는 측정이 아닌가

  • 고른 사례는 잘 되는 쪽으로 기울어 있음. 실제 트래픽은 분포가 다름.
  • 공식 조각 : 트래픽의 대표 표본으로 비교 (thinking-steering-and-cost en 87줄) · 운영 로그에서 실제 트래픽 비중대로 과제를 뽑음 (optimizing-cost-intelligence en 543줄) · 자동 eval 도 실사용 패턴과 어긋나면 거짓 확신 (demystifying-evals en 295줄).

왜 한 조각씩

  • 부서·문의 종류마다 입력이 다름 → 한 곳에서 성립한 가정이 다른 곳에서 깨질 수 있음 (업계 일반).
  • 공식 조각 : 이긴 구성은 전환 전에 트래픽 일부에 shadow 로, 전환 뒤에도 eval suite 를 계속 (optimizing-cost-intelligence en 546줄) · 사용량이 갑자기 늘면 가속 한도로 429 → 트래픽은 조금씩 (rate-limits en-full 92줄).

왜 전·후 + 대조군

  • "요청 수·지연·오류율" 은 돌아간다는 증거. 사업이 나아졌다는 증거는 목표 사업 지표의 전·후.
  • 전·후만 보면 그 사이의 다른 변화(성수기 · 인력 충원)와 못 가름 → 대조군(control). 공식 조각 : A/B 는 교란을 통제하고 실사용 결과를 측정 (demystifying-evals en 297줄) · 기준 모델·이전 판과 비교 (define-success en-full 35줄). 대조군을 확장 근거로 넓힌 건 해석.

핵심 질문 두 개

  • 이 단계에 들어가기 전에 "통과 · 중단 · 누가 정하나" 를 적어 뒀나?
  • 넓히자는 근거가 "돌아간다" 인가, "사업이 나아졌다(대조군과 함께)" 인가?

    권한 : 기본은 읽기 전용, 코드·시스템을 바꾸는 행동 전엔 사람 승인 ✓ 확인 (Claude Code 문맥 — 파일럿 권한으로 넓힌 건 해석) → ■ human-in-the-loop 게이트 위치

    반대 쪽 : 모델 벤치마크 세부 · 확정 SLA 문구 · on-call 순번은 뒤 게이트의 일 — 파일럿 전에 다 요구하지 않음 업계 일반 → SLA 는 ■ SLA 조항 쓰기

  3. ③

    고른 데모 ≠ 측정 : 고른 사례 몇 건의 정확도는 "되나" 의 증거일 뿐 → 대표 표본으로 기준선을 잰 뒤 약속 업계 일반 원리는 ✓ 확인 아래 [6.5] [6.3①]

    공식 조각 : 트래픽의 대표 표본을 돌려 비교 ✓ 확인 (thinking 조정 문맥) · 운영 로그에서 실제 트래픽 비중대로 과제를 뽑음 ✓ 확인 (비용 최적화 문맥) · 자동 eval 은 실사용 패턴과 어긋나면 거짓 확신 ✓ 확인 · 몇 번 해 보고 코너 케이스 한두 개 고치는 것도 사용자의 예상 밖 입력엔 모자람 ✓ 확인 (Skilljar) → "데모에서 잘 됨" 함정 본편 = ■ 변경마다 eval 다시

    파일럿 성공 = 가설 검증이지 운영 검증이 아님 → 넓히기 전에 먼저 물을 것 = "작은 규모에서 성립한 어떤 가정이 큰 규모에서 깨지나"(입력 분포 · 엣지 케이스 · 지원 부담 · 비용). 라이선스 · 교육 일정은 그 뒤 업계 일반

    공식 조각 : 운영 모니터링은 출시 뒤 분포 변화 · 예상 못 한 실패를 잡음 ✓ 확인 → ■ 검증 층

  4. ④

    넓히기는 한 조각씩 : 부서·문의 종류 하나 더 → 다른 입력 분포에서 정확도·지연이 유지되나 잰 뒤 다음 업계 일반 [6.5]

    공식 조각 : 이긴 구성은 전환 전에 트래픽 일부에 shadow 로 돌리고, 전환 뒤에도 eval suite 를 계속 ✓ 확인 (모델 구성 고르기 문맥) · 사용량이 갑자기 늘면 acceleration limit(가속 한도)으로 429 — 트래픽은 조금씩 올림 ✓ 확인 → ■ API 오류별 대응 · 옛 판·새 판 함께 트래픽 조금씩 → ■ 에이전트 상태·실패·배포

    되돌리기 어려운 결정(사람 검토 팀 해체 · 옛 시스템 폐기)은 단계적으로 줄이고, 지금 합의한 정지 선으로 되돌릴 길을 남김. "기준 통과했으니 예정대로 한 번에" 는 되돌리는 비용을 숨김 업계 일반

    비용은 운영 볼륨으로, 첫 청구서 전에 : 프로토타입 → 운영이면 비용이 일급 설계 제약 · 가장 좋은 모델이 규모에선 너무 비쌀 수 있음 ✓ 확인 · 지출 임계값 알림 ✓ 확인 → 전체 월 문의량으로 다시 셈 · 캐싱·모델 섞기·알림 설정(무엇을 언제 울릴지)을 넓히기 전에 말함 업계 일반 → ■ per-request cost · ■ 최적화 lever 하나 고르기

  5. ⑤

    넓힐 근거 = 목표 사업 지표의 전·후(같은 방법으로 측정) + 대조군(control) + 측정 소유자 업계 일반 [6.5] [1.6②]

    요청 수 · 지연 · 오류율 = 돌아간다는 증거뿐, 사업 결과가 아님 업계 일반 → 사업 지표 목록(AHT · deflection · CSAT)은 ■ impact metrics

    공식 조각 : A/B = 실제 사용자 결과(유지율 · 과제 완료율)를 재고 교란을 통제 ✓ 확인 · A/B 는 기준 모델·이전 판과 비교 ✓ 확인 → 대조군 없는 전·후 비교는 그 사이 다른 변화(성수기 · 인력)와 못 가름 (해석) → ■ 검증 층

    전 값만 있으면 바람일 뿐, 후 값만 있으면 근거 없는 주장 업계 일반 · 후 값에 운영 시간이 모자라면 측정 시점을 마일스톤으로 잡고 소유자·대조군 기록부터 업계 일반

  6. ⑥

    새 목적 = 새 use case : 서비스가 건강해도 목적이 바뀌면(배송 안내 → 환불 승인 여부 결정 · 문의 요약 → 상담원 순위 매기기) 반복이 아니라 새 use case → 결정권자 · 기준선 · 제약부터 다시 업계 일반 [6.5] [6.1①]

    전면 거절도, 기존 릴리스 절차로 밀어 넣기도 아님 — 다시 범위를 잡음 업계 일반 → ■ discovery 산출물 · 요구가 바뀐 증거 → discovery 는 ■ lifecycle 루프 · 규칙 ③

    게이트 순서 : eval 셋 + 합의된 trade-off(절충)는 handoff 계획 앞 · 되돌리기 절차 · 이름 있는 소유자는 handoff 앞 업계 일반 → ■ handoff 패키지 · 반복(iteration)은 설계로 돌아감, discovery 로는 요구가 바뀔 때만 (■ lifecycle 루프)

뒤집히는 때

1. 기준 없이 돌려도 되는 때 — 탐색 파일럿

  • 조건 : 무엇을 재야 할지부터 모름. 상담원 3명이 2주간 초안을 써 보며 "어디서 시간이 드나" 를 찾는 게 목적.
  • 판단 : 이건 파일럿이 아니라 PoC 쪽 탐색 — 기준 없이 돌려도 되지만, 결론은 "되나?" 와 "무엇을 잴까" 까지만. 넓힐 근거로는 못 씀. 그다음 파일럿은 여기서 찾은 지표로 기준을 먼저 정하고 시작.
  • 등급 : 업계 일반
  • 근거 : 공식 문장 없음. "eval 과제를 적어 보면 요구가 짓기에 충분히 구체적인지 드러남"(demystifying-evals en 277줄)과 같은 방향.

2. 전·후만으로 넓혀도 되는 때

  • 조건 : 반품 처리 시간이 22분 → 7분(약 68% 감소). 같은 기간 다른 센터는 21분 → 20분.
  • 판단 : 다른 센터가 사실상의 대조군 — 차이가 이렇게 크고 대조군 쪽이 거의 그대로면 "성수기 때문" 같은 다른 설명이 약함. 대조군을 따로 짜지 않았어도 비교 가능한 쪽이 있으면 근거가 됨. 둘 다 같은 방법으로 쟀는지는 확인.
  • 등급 : 계산 (15 ÷ 22 ≈ 68%) · 업계 일반 (판단)
  • 근거 : A/B 의 교란 통제(demystifying-evals en 297줄)를 넓힌 해석.

3. 한 번에 넓혀야 하는 때

  • 조건 : 규제 기한 때문에 모든 센터가 같은 날 새 환불 안내 문구로 바꿔야 함.
  • 판단 : 조각씩 넓힐 시간이 없으면, 대신 전환 전에 트래픽 일부에 shadow 로 돌려 보고(안내는 옛 방식, 새 방식 답은 비교만), 중단 규칙과 되돌릴 판을 미리 둠.
  • 등급 : 확인(shadow) · 업계 일반(적용)
  • 근거 : optimizing-cost-intelligence en 546줄

4. 데모 값으로 약속해도 되는 때?

  • 조건 : 고른 사례가 아니라, 지난달 운영 로그에서 비중대로 뽑은 문의 300건으로 "데모" 를 했고 정답 276건(92%).
  • 판단 : 이름이 데모여도 대표 표본이면 기준선. 가를 기준은 "데모냐" 가 아니라 "표본이 실제 트래픽 비중을 따랐나".
  • 등급 : ✓ 확인 (대표 표본 원리) · 계산 (276 ÷ 300)
  • 근거 : optimizing-cost-intelligence en 543줄 · thinking-steering-and-cost en 87줄

5. 새 목적인데 새 use case 까지는 아닌 때

  • 조건 : 반품 안내 Agent 가 교환 안내도 하게 함. 둘 다 "안내" 이고, 결정·통지는 여전히 상담원.
  • 판단 : 목적(안내)이 같고 결정 주체도 같으면 범위 확장 — 반복 안에서 eval 과제를 더하고 한 조각씩. 안내 → 결정 통지처럼 누가 결정하나 가 바뀌면 새 use case.
  • 등급 : 업계 일반
  • 근거 : 공식 문장 없음. 결정 앞 사람 승인은 ■ human-in-the-loop 게이트 위치.

  1. PoC · 파일럿 · 확장 게이트 구성 전체 : 공식 문장 못 찾음. 검색 = ccarp/raw/official-docs/en-*.md 에서 "pilot|roll out|rollout|gradual|phased|shadow|traffic slice|slice of" (스크래치 w3_grep.py) → 게이트 뜻 0건. 잡힌 것 = shadow 1(optimizing-cost en 546) · "ramp up your traffic gradually"(rate-limits en-full 92) · "piloting and scaling"(service-tiers en 4 — Standard 티어 설명일 뿐) · rainbow deployments(multi-agent-research-system en 74). 제외 = 받지 않은 공식 페이지 · ko 판.
  2. 중단 규칙 · go/no-go 소유자 · 한 부서씩 · 결과 문서 항목(전·후 + 대조군 + 소유자) · 새 목적 = 새 use case : 공식 문장 없음 → 업계 일반.

  4. 후보 절의 "운영 볼륨 = 파일럿의 10~100배" 는 공식 숫자 없음 → 카드엔 배수 없이 "전체 월 문의량으로 다시 셈" 만 남김.

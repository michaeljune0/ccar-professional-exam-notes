■ discovery 산출물

discovery outputs : 기준선 · 결정권자 · 요구 4범주 · 가정 목록 — "끝났다" 의 판정6.1 본편

왜 배우나 — 시험이 요구하는 것

시험 목표 6.1 요구 수집 · D6 사람·문서 14%
Conduct structured discovery and requirement gathering

이 개념으로 푸는 판단 (할 수 있어야 하는 것)

  • 6.1① "완벽한 계약 검토기를 만들어 달라" — 아키텍트의 첫 행동은? — 해법(모델·프롬프트·에이전트)보다 디스커버리 먼저
  • 6.1② 성공 기준을 어떻게 적나 — SMART 로? 숫자 하나로? — 성공 기준의 요건 (Anthropic 4가지 + 여러 차원)
  • 6.1③ 민감 데이터라며 BAA·GDPR·ZDR 을 한꺼번에 걸자고 한다 — 디스커버리에서 무엇을 사실로 확인하나? — 규정 약정을 데이터 사실(PHI 유무·거주지·보존)에서 끌어내기

한눈에

discovery 가 "끝났다" 는 회의 횟수가 아니라 산출물로 가름 — 지금 일의 기준선(baseline) · 그 기준선에 견주어 목표를 고른 결정권자(decision owner) 한 명 · 네 범주로 채운 요구 · 확인 안 된 말을 모은 가정 목록 업계 일반 산출물 목록은 공식 문서에 없음

공식에서 가장 가까운 원칙 : 목표는 기준선 대비로 적음("지금 기준선보다 5% 개선") ✓ 확인 · eval 은 초기에 제품팀이 성공이 무엇인지 적게 만듦 ✓ 확인. 묻는 법은 ■ discovery, 기준 문장 쓰는 법은 ■ 성공 기준

비유 이관 착수 체크리스트. 현재 처리량·지연(latency) 실측값 · 승인권자 1명 · 금지 사항 · 비용 상한 · 감사 증거 — 한 칸이라도 비면 착수 회의를 다시 잡음. "워크숍 했으니 요구 수집 끝" 이 속이는 습관

ELI5

집을 고치기 전에 "다 물어봤다" 를 체크리스트로 확인하는 거예요.

  • 지금 집을 줄자로 재 둬야, 나중에 얼마나 넓어졌는지 말할 수 있어요.
  • "넓게 해 주세요" 의 크기를 정하는 사람은 한 명이어야 해요.
  • "이 벽은 절대 헐지 마세요" 는 먼저 묻지 않으면 아무도 말 안 해요.
  • "수도관은 아마 여기 있을 거예요" 는 확인할 때까지 메모지에 따로 적어요.

개념 설명

원리

"끝났다" 는 시간이 아니라 산출물

  • 워크숍·회의 횟수는 discovery 가 끝났다는 증거가 아님. 설계가 기댈 네 가지(기준선 · 결정권자 · 요구 4범주 · 가정 목록)가 채워졌는지로 판정 (업계 일반).
  • 묻는 법 자체(인터뷰 · eval 과제로 구체성 검사)는 ■ discovery. 이 쪽은 "무엇이 손에 남아야 끝인가".

기준선이 없으면 목표가 뜻이 없음

  • "30% 단축" 은 무엇 대비인지가 있어야 약속이 됨. 공식 성공 기준 예도 "지금 기준선보다 5% 개선".
  • eval 이 생기면 AI 쪽 기준선(지연 · 토큰 · 과제당 비용 · 오류율)은 따라옴. 하지만 지금 사람이 하는 일의 기준선은 따로 재야 전·후 비교가 됨.

목표를 고르는 사람은 한 명

  • 목표에는 값 판단이 들어감(얼마나 빨라야 투자할 만한가) → 사업 쪽 소유자 몫. 승인자가 둘이면 두 목표로 설계가 갈림 (업계 일반).
  • 아키텍트 몫 = 그 목표를 이룰 수 있는지 가늠(공식 "달성 가능" — 업계 벤치마크 · 이전 실험 · AI 연구 · 전문가 지식)과 재는 법.

"하면 안 됨" 은 묻지 않으면 안 나옴

  • 사람은 원하는 것을 말하지, 금지 사항은 당연하다고 여겨 빠뜨림 (업계 일반). 공식 고객지원 가이드도 프롬프트에 dos and don'ts · 권한 없는 약속 금지를 따로 적으라고 함.
  • 금지 칸이 사람 승인 게이트 위치를 정함 → 비면 게이트를 못 놓음.

들은 말은 가정

  • "아마" 가 붙은 말을 요구로 적으면, 틀렸을 때 그 위에 선 설계 전체를 다시 짬. 가정으로 적고 소유자 · 푸는 기준을 달면 틀려도 한 줄만 고침 (업계 일반).

흐름

규칙 원문 ①②③④⑤ (갈림길로 그린 규칙)
  1. ①

    기준선(baseline) : 지금 일을 같은 잣대로 측정 — 예 "반품 문의 1건, 접수부터 환불 승인까지 걸린 분" · 운영 데이터 + 실제 사용자·데이터 소유자 인터뷰 업계 일반 [6.1①]

    공식 : 목표는 기준선 대비로 — "지금 기준선보다 5% 개선" 이 달성 가능한 목표의 예 ✓ 확인 · A/B 는 기준 모델·이전 판과 비교 ✓ 확인

    만들기 전에 재기 : 스킬도 스킬 없이 대표 과제로 돌려 빈 곳을 적고 기준선부터 측정 ✓ 확인 (Skills 문맥 — discovery 로 넓힌 건 해석)

    eval 이 생기면 지연·토큰·과제당 비용·오류율 기준선은 따라옴 ✓ 확인 — 단 그건 AI 쪽 기준선. 지금 사람이 하는 일의 기준선은 따로 측정 업계 일반

    스폰서 워크숍 하나로 "완료" 표시하면 미완 — 현장 상담원이 실제로 하는 일을 빗나감 업계 일반

  2. ②

    결정권자 한 명 : 이름이 정해진 결정권자 한 명이 기준선에 견주어 측정 가능한 목표를 고름. 아키텍트가 대신 정하거나 · 벤치마크 숫자로 채우거나 · 빈칸으로 둔 채 설계에 들어가지 않음. 승인자가 둘이면 한 명으로 정리 업계 일반 [6.1①] [6.3]

    목표 문장 모양(구체적·측정 가능·달성 가능·관련 · 여러 차원) → ■ 성공 기준

뒤집히는 때

1. 같은 "30% 단축" 이 전혀 다른 약속이 되는 때

  • 조건 : 목표는 "반품 처리 30% 단축", 기준선을 한 정의로 재지 않음.
  • 계산 : 정의 A "접수 → 상담원 첫 응답" 기준선 14분 → 30% 단축 = 9.8분(4.2분 줄임). 정의 B "접수 → 환불 승인" 기준선 2.5일(60시간) → 30% 단축 = 42시간(18시간 줄임). 같은 문장이 4분짜리 약속도, 18시간짜리 약속도 됨.
  • 전제 : 두 기준선 값은 예시 · 정의만 다르고 같은 반품 흐름.
  • 등급 : 계산 (기준선 대비 목표는 확인)
  • 근거 : define-success en-full 53줄
  • 판단 : 그래서 "기준선 있음" 은 숫자 하나가 아니라 "무엇부터 무엇까지" 정의까지 있어야 함.

2. 작은 변경이면 산출물을 다 채우지 않음

  • 조건 : 반품 안내 문구 한 줄 고치기처럼 한 문장으로 설명되는 변경.
  • 판단 : 네 산출물을 다 채우는 건 과함. 계획에도 부담이 있음 → 바로 함. "모든 요청에 산출물 전부" 는 반대 함정.
  • 등급 : ✓ 확인 (코딩 세션 문맥 — 설계 discovery 로 넓힌 건 해석)
  • 근거 : best-practices en 265줄 "If you could describe the diff in one sentence, skip the plan."

3. 요구자도 원하는 걸 모를 때

  • 조건 : 본부장이 "뭔가 AI 로 반품을 편하게" 라고만 하고, 무엇이 불편한지 본인도 못 짚음.
  • 판단 : 질문만 계속하면 빈 답만 모임. 작게 먼저 돌려 보고 결과물을 보여 주는 것이 곧 질문 → 그 반응으로 기준선·목표·금지 칸을 채움.
  • 등급 : ✓ 확인 (코딩 세션 문맥 — 넓힌 건 해석)
  • 근거 : best-practices en 821줄 "Sometimes a vague prompt is exactly right because you want to see how Claude interprets the problem before constraining it."

4. 지금 하는 사람이 없는 새 업무

  • 조건 : 야간(22시~8시) 반품 문의는 지금 아무도 응대하지 않음 — 잴 "현재 프로세스" 가 없음.
  • 판단 : 기준선 = 지금 고객이 겪는 값(아침까지 기다리는 시간 · 그 사이 이탈률). "기준선 없음" 이 "재지 않아도 됨" 은 아님.
  • 등급 : 추론
  • 근거 : define-success en-full 53줄(기준선 대비 목표)에서 한 걸음

  2. 공식 "기준선" 문장은 AI 쪽 기준선(모델 성능 · 스킬 없이 잰 성능 · eval 의 지연·비용)이다. "지금 사람이 하는 일의 기준선" 을 discovery 산출물로 적으라는 문장은 없음 — 이 카드의 해석.
  3. 후보 절 공식 근거 7줄은 모두 원문에서 그 줄에 있음을 확인했다(define-success en-full 53 · demystifying-evals 277·44 · customer-support-chat en-full 89·360 · safe-trustworthy-agents 17 · agent-skills best-practices 705). 추가로 찾아 쓴 줄 = define-success en-full 15·35·45·88 · customer-support-chat en-full 160·352.

  5. Skilljar 는 이번에 보지 않음 — ccarp/raw/skilljar 검색(위 검색어) 결과 discovery 산출물 주제 없음 (제외 = 받지 않은 과정·강의).

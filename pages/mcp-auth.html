■ MCP 인증·인가

MCP authentication/authorization3.2 본편

왜 배우나 — 시험이 요구하는 것

시험 목표 3.2 인증·권한 빈틈 · D3 연결 19%
Analyze authentication and authorization requirements to identify security gaps

이 개념으로 푸는 판단 (할 수 있어야 하는 것)

  • 3.2① 같은 머신의 stdio MCP 서버와 원격 HTTP MCP 서버를 함께 붙인다 — 자격증명을 각각 어떻게 주나? — 전송 방식별 인증 고르기
  • 3.2② 사내 MCP 서버가 받은 사용자 토큰을 Salesforce API 호출에 그대로 붙인다 — 무엇이 빈틈인가? — 토큰 경계 (audience 검증 · 그대로 넘기기 금지)
  • 7.1③ 에이전트에 줄 권한, 어디까지? — 행동을 allow/ask/deny 로 나눈 공유 설정 + MCP 자격증명 최소 권한

한눈에

MCP 에서 인가(authorization)는 **선택(OPTIONAL)**. 붙인다면 전송 방식이 방법을 정함 — stdio 는 환경에서 자격증명, HTTP 는 OAuth 2.1 기반 규격 ✓ 확인

HTTP 인가에서 MCP 서버 = OAuth resource server, MCP 클라이언트 = OAuth client, 토큰 발급 = authorization server ✓ 확인

비유 같은 파드 사이드카는 마운트된 시크릿·환경변수, 외부 API 는 OIDC/OAuth 토큰. 게이트웨이가 받은 JWT 를 제3자 API 에 재사용하지 않음

ELI5

놀이공원 손목 띠는 그 놀이공원에서만 써요.

  • 집 안 방끼리는 띠 없이 열쇠를 서랍에 두고 써요(로컬).
  • 밖에 나갈 땐 입구에서 띠를 받아요(원격).
  • 옆 놀이공원 입구에 내 띠를 내밀면 안 돼요 — 거기서 새 띠를 받아요.
  • 처음엔 작은 띠만 받고, 큰 놀이기구 앞에서 더 받아요.

개념 설명

원리

인가(authorization)는 선택, 붙이면 전송이 방법을 정함

  • stdio 서버는 클라이언트가 띄운 같은 머신의 자식 프로세스 → 네트워크 경계가 없음. 자격증명은 환경(환경 변수)으로 주면 됨. OAuth 규격을 따르지 말라고(SHOULD NOT) 적혀 있음.
  • HTTP 서버는 네트워크 너머 → OAuth 2.1. MCP 서버 = resource server(토큰 검사), 클라이언트 = OAuth client(토큰 받아 옴), authorization server = 토큰 발급.
  • 인가 자체가 OPTIONAL — 인증(authentication) 없는 공개 서버도 규격 위반은 아님.

토큰은 한 곳 전용 (audience)

  • 클라이언트는 토큰을 받을 때 resource 파라미터로 "이 서버용"을 박음.
  • 서버는 자기용이 아닌 토큰은 거부. 그래야 다른 서비스용 토큰을 주워 와 재사용하는 공격이 막힘.
  • 서버가 뒤에서 제3자 API 를 부르면, 서버는 그 API 의 OAuth client 가 되어 새 토큰을 받음. 받은 토큰을 그대로 넘기면(passthrough) 업스트림이 "MCP 서버가 검증했겠지"라고 믿어 버림 → 통제(control)·감사·신뢰 경계가 다 깨짐.

scope 는 점진 승격

  • 처음엔 읽기 수준 최소 scope. 권한이 더 필요한 작업을 처음 하려 할 때 서버가 WWW-Authenticate 로 필요한 scope 를 알려 주고 그때 올림.

연습 문제

사내 MCP 서버(Streamable HTTP)가 상담원 앱이 보낸 액세스 토큰을 검사한 뒤, 뒤에서 Salesforce API 를 불러 고객 기록을 가져온다업스트림 호출. 개발자는 "받은 토큰을 그대로 넘기면 사용자 권한이 유지돼 안전하다"고 한다. Salesforce 호출에는 어떤 토큰을 쓸까?

시험 대비

함정

  • ≠"stdio 서버에도 OAuth 2.1 흐름을 붙인다" → 규격은 SHOULD NOT, 환경에서 ✓ 확인
  • ≠"원격 MCP 는 반드시(MUST) OAuth" → 인가 자체가 OPTIONAL, HTTP 면 SHOULD ✓ 확인
  • ≠"로컬 프로세스는 API 키 경계" (영상 표현) → 공식은 "환경에서 자격증명" ✓ 확인
  • ≠"토큰을 그대로 넘기면 사용자 권한이 유지돼 오히려 안전(SSO 처럼)" → 명시 금지 ✓ 확인
  • ≠용어 : 규격의 'Confused Deputy' 절은 좁게는 정적 client ID 를 쓰는 프록시 서버의 동의 문제(동적 등록 클라이언트마다 사용자 동의 필수). 토큰 그대로 넘기기는 별도 항목 — 다만 규격은 그것도 confused deputy 를 부를 수 있다고 적음 ✓ 확인
  • ≠"scope 를 한 번에 넉넉히 받아 동의창을 줄인다" → 과한 scope 는 피해 반경↑, 동의 포기도 부름. 점진 승격 ✓ 확인

신호

"Authorization is OPTIONAL for MCP implementations."

"Implementations using an STDIO transport SHOULD NOT follow this specification, and instead retrieve credentials from the environment."

"Implementations using an HTTP-based transport SHOULD conform to this specification."

"MCP servers MUST only accept tokens specifically intended for themselves and MUST reject tokens that do not include them in the audience claim"

"The MCP server MUST NOT pass through the token it received from the MCP client."

"Token passthrough is explicitly forbidden in the authorization specification"

뒤집히는 때

1. "원격이니 OAuth 필수"가 틀리는 때

  • 조건 : 사내망 안의 공개 사내 문서 검색 서버(Streamable HTTP), 사용자별 데이터 없음.
  • 판단 : 인가는 OPTIONAL. 붙인다면 SHOULD 로 이 규격. "MUST OAuth" 라고 쓴 보기는 과장.
  • 등급 : ✓ 확인
  • 근거 : authorization en 163~164줄

2. stdio 인데 OAuth 가 등장하는 때

  • 조건 : 로컬 stdio 서버가 뒤에서 원격 SaaS API 를 부른다.
  • 판단 : 클라이언트 ↔ stdio 서버 구간은 환경 자격증명. 서버 ↔ SaaS 구간은 그 SaaS 의 인증 방식(OAuth 일 수 있음) — 두 구간을 섞어 "stdio 에도 OAuth 2.1 흐름" 이라 하면 틀림.
  • 등급 : 확인(stdio 구간) · 업계 일반(업스트림 구간의 방식)
  • 근거 : authorization en 165·721줄

3. "사용자 권한 그대로 쓰고 싶다"

  • 조건 : 사용자별 Salesforce 권한을 그대로 적용해야 해서 받은 토큰을 넘기자는 제안.
  • 판단 : 뒤집히지 않음. 업스트림 토큰은 업스트림 authorization server 가 따로 발급. 사용자 권한을 살리는 건 업스트림 쪽 OAuth 에서 사용자 동의로 받는 것(방식 세부는 규격 밖).
  • 등급 : 확인(금지) · 업계 일반(대안 방식)
  • 근거 : authorization en 721줄 "The access token used at the upstream API is a separate token, issued by the upstream authorization server."

4. scope 를 크게 받는 게 나아 보이는 때

  • 조건 : 동의창이 여러 번 떠서 사용자가 귀찮아한다.
  • 판단 : 공식은 반대 — 과한 scope 목록이 오히려 동의 포기를 부르고, 토큰이 새면 피해가 큼. 최소 + 점진 승격, 거절된 scope 는 캐시해 반복 요청 방지.
  • 등급 : ✓ 확인
  • 근거 : security best practices en 696~720줄

시험 목표 5.2 위험·한계·실패 유형 · D5 규정·안전 14%
Identify risks, limitations, and failure modes of LLM systems

이 개념으로 푸는 판단 (할 수 있어야 하는 것)

  • 5.2① 증상만 보고 실패에 이름을 붙일 수 있나? — 실패 유형 → 그 실패를 실제로 바꾸는 통제
  • 5.3① 승인 요청이 하루 수백 개 — 전부 사람이 누르게 할까? — 사람 승인 게이트 위치 (빈도가 아니라 결과의 크기·되돌릴 수 있나)
  • 4.4① 문서 갱신 뒤 자신 있게 틀린다 — 모델·지연은 그대로 — 어느 계층부터 조사하나 (첫 질문 = 증상 직전에 무엇이 바뀌었나)
  • 5.1① 같은 사용자가 계속 탈옥을 시도한다 — 직접 인젝션(사용자가 공격자) 대응 고르기
  • 5.1② 사용자가 넘긴 이메일 속에 "이 주소로 전부 보내라" 가 숨어 있다 — 간접 인젝션(사용자는 믿지만 가져온 콘텐츠가 적) 대응

한눈에

증상을 보고 실패에 이름을 붙인 뒤, 그 이름에 맞는 통제(control)를 고름. 이름이 틀리면 통제도 헛돎 업계 일반 공식 문서에 failure modes 점검표 자체는 없음

"더 큰 모델"·"모든 것에 사람 검토"는 대개 이름에 맞는 통제가 아님 (추론 — 샘플 1 D 해설의 확장 · ③)

비유 장애 분류별 런북. 디스크 풀에 재시작, OOM 에 네트워크 점검을 하면 안 고쳐짐

ELI5

아픈 곳마다 약이 달라요. 배가 아픈데 연고를 바르면 안 나아요.

  • 먼저 "어디가 어떻게 아픈지" 이름을 붙여요.
  • 이름이 맞아야 맞는 약을 고를 수 있어요.
  • "더 비싼 약"이 늘 답은 아니에요.
  • "의사한테 다 물어보기"도 너무 자주 하면 의사가 대충 봐요.

개념 설명

원리

이름 → 통제(control) 짝 (공식 문서에서 확인한 것만)

  • 환각 : 근거 없이 매끄럽게 틀림. 통제 = "모른다" 허용 · 긴 문서(20k 토큰 초과)는 원문 인용부터 · 주장마다 인용, 못 찾으면 철회 · 준 문서만 쓰게 · 여러 번 돌려 비교(Best-of-N).
  • 비결정성 : run 마다 출력이 다름. 통제 = 판정은 여러 번(trials). 고객 대면이면 매번 성공해야 하니 pass^k (■ 성공 기준). 줄이는 쪽 = 형식 명시 · 예시 · 검색(retrieval)으로 고정된 정보에 근거.
  • 직접 인젝션·탈옥 / 간접 인젝션 : 위협 모델이 다름 → ◆ 직접 인젝션 vs 간접 인젝션.
  • 과잉 행동(overeager) : 사용자가 뜻하지 않은 주도(원격 브랜치 삭제 · 토큰 업로드 · 운영(production) DB 마이그레이션 — Anthropic 사내 사고 기록 예). 통제 = 최소 권한(least privilege) · 샌드박스 · 고위험(high-stakes) 결정 전 사람 승인(human approval) · 실행 직전 검사.
  • 오정렬 : 목표는 맞지만 맥락이 없어 과하게 함("파일 정리" → 중복 삭제·폴더 재구성). 통제 = 투명성(transparency — 계획을 보이기) + 사람 통제.
  • 학습 컷오프 : 모델마다 reliable-knowledge·training-data cutoff 가 있음. 통제 = 최신 사실을 검색해서 넣기(업계 일반).
  • 거절 : HTTP 200 + 빈 content → ■ stop_reason 으로 분기.

사람 검토의 한계

  • 수동 확인이 많으면 승인 피로 : 사용자는 수동 확인의 93% 를 승인함 (Claude Code auto mode 글).
  • 사람을 조언 자리에만 두는 것만으로는 충분한 가드레일이 아님 — 자동화 편향(automation bias) (Anthropic 차별 평가 논문).
  • 그래서 "모든 실패에 사람 검토"는 이름을 안 붙이고 뭉뚱그린 처방.

연습 문제

개발자가 사내 코딩 Agent 에게 "테스트 좀 정리해 줘" 라고 했더니 Agent 가 원격 브랜치를 지우고 운영(production) DB 마이그레이션까지 시도뜻 밖 행동했다. 메일·문서 속에 숨은 지시는 없었다. 팀장은 "더 큰 모델로 바꾸면 안 그럴 것" 이라고 한다. 이 실패의 이름과 맞는 통제는?

시험 대비

함정

  • ≠"더 큰 모델이 더 안전하고 덜 뚫린다" → 모델 크기는 권한 범위와 무관 ✓ 확인 (샘플 1 D) · 환각·비결정성 처방 목록에도 없음 (추론)
  • ≠모든 실패에 일괄 "사람 검토" → 승인 피로 ✓ 확인
  • ≠같은 질문에 다른 답을 "모델 버그"로 봄 → run 마다 출력이 다름, 판정은 여러 번 ✓ 확인
  • ≠한 번 돌려 통과하면 됨 → 비결정성이라 여러 번 시도 ✓ 확인
  • ≠환각인데 "인젝션 필터" / 인젝션인데 "모른다 허용" → 이름이 틀리면 통제도 헛돎 업계 일반
  • ≠거절(빈 답)을 환각·장애로 봄 → HTTP 200 + refusal → ■ stop_reason 으로 분기 ✓ 확인

뒤집히는 때

1. 비결정성인데 사실은 환각일 때

  • 조건 : 같은 환불 질문에 5번 물어 3가지 금액이 나옴.
  • 판단 : 겉은 비결정성이지만, 공식은 "여러 번 돌려 어긋나면 환각 신호일 수 있다"고 함 → 금액이 문서에 있는지부터(인용 후 철회). 판정은 여러 번 돌려서.
  • 등급 : ✓ 확인 (두 문장 모두 공식)
  • 근거 : reduce-hallucinations en 14줄 · demystifying-evals en 24줄

2. 사람 검토가 정답일 때

  • 조건 : 에이전트가 월 구독 40개 중 12개를 해지하려 함.
  • 판단 : "모든 실패에 사람 검토"는 오답이지만, 고위험·되돌리기 어려운 결정 전의 사람 승인은 공식 원칙 → 이 경우는 사람 승인 쪽.
  • 등급 : ✓ 확인
  • 근거 : safe-trustworthy-agents en 17줄(구독 해지 예시 그대로)

3. pass@k 가 맞을 때

  • 조건 : 사내 개발자용 도구, 여러 번 시도해 한 번만 맞으면 됨.
  • 판단 : 비결정성 판정을 pass^k 로 하면 과하게 엄격. 한 번 성공이 중요한 도구면 pass@k.
  • 등급 : ✓ 확인
  • 근거 : demystifying-evals en 211줄

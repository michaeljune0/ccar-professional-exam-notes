함정

  • ≠과제 무시하고 제일 작은 모델로 → 오답 (샘플 2 B) ✓ 확인
  • ≠"스트리밍을 켜면 전체 처리 시간이 준다" → 체감만 업계 일반
  • ≠"effort 낮추면 답이 짧아진다" → thinking 양만 줄어듦, 길이는 프롬프트로 ✓ 확인
  • ≠캐시 쓰는 대화 중간에 요청 수준(top-level) effort 값을 바꿈 → 캐시 무효화. 워크로드 단위로 바꾸거나 메시지별 effort(베타) ✓ 확인
  • ≠"모델 교체는 항상 오답" → 아님. 공식 지연 문서는 모델 선택을 첫 방법으로 듦. eval 로 품질을 확인하면 맞는 답 ✓ 확인
  • ≠fast mode 를 배치에 → 안 됨, 동기 지연용 ✓ 확인

ELI5

식당에서 음식이 늦게 나온다고 할 때를 생각해 보세요.

  • 물과 반찬을 먼저 내주면 덜 기다린 것처럼 느껴져요.
  • 매번 쓰는 재료를 미리 손질해 두면 첫 접시가 빨리 나와요.
  • 양을 줄이거나 조리를 간단히 하면 다 나오는 시간이 줄어요.
  • 요리사를 바꾸는 건 맛이 그대로인지 먼저 맛본 뒤에 해요.

원리

지연(latency)은 두 가지

  • 첫 글자까지(TTFT) : 요청 보내고 첫 토큰이 나올 때까지. 입력 처리 시간이 큰 몫을 차지.
  • 다 받기까지 : TTFT + 출력 토큰을 다 생성하는 시간. 출력이 길수록 김.
  • 공식 : 처리·생성할 토큰이 적을수록 응답이 빠름.

lever(손잡이)마다 건드리는 곳

  • 스트리밍 : 생성은 그대로, 오는 대로 보여 줌 → 체감만 줄임.
  • 캐싱 : 매번 같은 앞부분 처리를 건너뜀 → TTFT · 입력 비용을 줄임. 출력 시간은 안 건드림.
  • 출력 길이 : 생성할 토큰 수 자체를 줄임 → 전체 시간.
  • effort : 한 모델 안에서 thinking(사고)·도구 호출·텍스트 토큰 양을 줄임 → 전체 시간 · 비용. 대신 지능이 조금 내려감.
  • 모델 : 더 빠른 모델(Haiku 4.5) 또는 fast mode(같은 Opus, 출력 속도 최대 2.5배, 비쌈).

왜 "모델부터"가 약한 답인가

  • 공식 지연 문서는 모델 선택을 가장 직접적인 방법 중 하나로 든다. 그러니 모델 교체 자체가 틀린 건 아님.
  • 다만 "effort 조정이 모델 교체보다 나은 경우가 많다"는 것도 공식이고, 과제 무시한 축소는 품질 위험(샘플 2).
  • 그래서 시험 답의 모양 = "증상을 가르고, 품질을 지키는 가장 싼 lever 부터, 모델 교체는 eval 로 확인하고".

핵심 질문 두 개

  • 느린 게 첫 글자인가, 다 받기까지인가?
  • 이 lever 를 돌리면 품질이 떨어지나 — 떨어진다면 eval 로 확인했나?

품질 여유가 있고 지연·비용을 줄여야 함 effort 낮추기 (모델 교체보다 먼저) ✓ 확인 choosing-a-model en 8줄 "Tuning effort is often a better lever than switching models." · effort en 157줄
effort 를 낮췄는데 답 길이가 그대로 (Opus 5) 길이는 프롬프트로 ✓ 확인 effort en 53줄 "Effort controls thinking volume, not visible response length"
지연 요구가 엄격 · 단순 대량 작업 빠른 모델(Haiku 4.5)로 시작, 기능 격차 있을 때만 올림 ✓ 확인 choosing-a-model ko 18~30줄
모델을 바꾸려 함 실제 프롬프트·데이터로 정확도·품질·엣지 케이스 비교 뒤 ✓ 확인 choosing-a-model ko 69~79줄
품질을 못 내려놓고 출력 속도가 문제 fast mode (Opus 5.5 · 5 · 4.8, 비싼 요금) ✓ 확인 choosing-a-model ko 6줄
배치 작업의 지연 fast mode 불가 (동기 지연용) ✓ 확인 batch-processing ko 63줄

뒤집히는 때

1. 스트리밍이 답이 아닌 때

  • 조건 : 사람이 보는 화면이 없음. 분류 결과를 다음 단계 코드가 통째로 받아 큐에 넣음.
  • 판단 : 스트리밍은 "보이는" 반응성을 올리는 것이라 기다리는 쪽이 코드면 얻는 게 없음. 전체 시간을 줄이는 lever(출력 길이 · effort · 모델)로.
  • 전제 : 부분 결과를 먼저 쓸 수 있는 흐름이 아님.
  • 등급 : 업계 일반 (공식은 "perceived responsiveness"·"users can see the model's output"까지만 말함)
  • 근거 : reduce-latency en 41~43줄
  • 곁가지 : 긴 출력은 SDK 가 HTTP 타임아웃을 피하려고 스트리밍을 요구함 → 이때 스트리밍은 체감이 아니라 연결 유지용 (streaming ko 9줄 · errors ko 76줄, 본편 4.5③).

2. 캐싱을 켰는데 첫 글자가 안 빨라지는 때

  • 조건 : 입력이 900 토큰 정도로 짧은 채팅, Haiku 4.5.
  • 계산 : Haiku 4.5 최소 캐시 길이 4,096 > 900 → 캐시가 아예 안 만들어짐. 그리고 입력이 짧으면 TTFT 에서 입력 처리 몫이 작아 캐싱으로 줄일 것도 적음.
  • 처방 : 출력 길이 · effort · 스트리밍 쪽.
  • 등급 : 확인(최소 길이) · 업계 일반(입력이 짧으면 캐싱 이득 작음)
  • 근거 : ■ 프롬프트 캐싱 · 규칙 ② · prompt-caching ko 183줄

3. fast mode 로 얼마나 줄어드나

  • 조건 : 품질 때문에 Opus 를 못 내려놓음. 한 응답 12초 중 입력 처리·대기 2초, 출력 생성 10초라 치자.
  • 계산 : fast mode 는 출력 속도 최대 2.5배 → 출력 10초 ÷ 2.5 = 4초 → 전체 약 6초 (최대치 기준, 입력 몫 2초는 그대로라고 가정).
  • 전제 : "최대" 2.5배라 실제는 덜 줄 수 있음 · 요금은 프리미엄 · 리서치 프리뷰 · 배치 불가.
  • 등급 : 계산 (2.5배는 확인)
  • 근거 : choosing-a-model ko 6줄 · 릴리스 노트 en 17줄 · batch-processing ko 63줄

4. 모델 교체가 맞는 답인 때

  • 조건 : 지연 요구가 엄격한 대량·단순 작업. effort 를 낮춰도 목표 미달. 실제 데이터 eval 에서 작은 모델이 품질을 지킴.
  • 판단 : 모델 교체(또는 처음부터 Haiku 4.5)가 정답. "모델 교체 = 오답"으로 외우면 여기서 틀림.
  • 등급 : ✓ 확인
  • 근거 : choosing-a-model ko 18~30·69~79줄 · reduce-latency ko 20줄

5. 모델만 바꿨는데 지연·품질이 같이 달라진 때 (시험 뒤 변경)

  • 조건 : effort 를 명시하지 않은 채 Opus 5 → Opus 5.5 로 옮김.
  • 판단 : Opus 5.5 기본 effort 는 medium(Opus 5 는 high) → 한 단계 낮게 돎. 지연·비용이 줄고 품질이 변할 수 있음 → effort 를 명시하고 eval 로 스윕.
  • 등급 : ✓ 확인 · 시험 뒤 변경(2026-09-22). 시험은 "대부분 모델 기본 high"로 물을 가능성(추론).
  • 근거 : effort ko 9·47·156줄 · 릴리스 노트 en 15줄

오답 재료

오답 왜 끌리나 왜 틀리나 등급 근거
"과제와 상관없이 가장 작은 모델로" 작은 모델이 빠르고 쌈 품질 위험. 과제 적합도를 eval 로 봐야 ✓ 확인 가이드 샘플 2 해설 "downsizing blindly (B) risks quality"
"정책 문서를 잘라 입력을 줄인다" 토큰이 줄면 빨라짐(공식) 필요한 내용을 잃음. 반복 앞부분은 캐싱 ✓ 확인 가이드 샘플 2 해설 "Truncation (A) loses needed policy"
"스트리밍을 켜면 전체 처리 시간이 준다" 빨리 뜨니 빨라진 것 같음 체감만. 생성 토큰 수는 같음 업계 일반 reduce-latency en 41줄 ("perceived")
"effort 를 낮추면 답이 짧아진다" 적게 쓰라는 설정 같음 thinking 양만 줄어듦(Opus 5). 길이는 프롬프트로 ✓ 확인 effort en 53줄
"모델 교체는 항상 오답" effort 먼저라는 말을 과하게 외움 공식 지연 문서의 첫 방법이 모델 선택. eval 로 확인하면 맞는 답 ✓ 확인 reduce-latency ko 20줄 · choosing-a-model ko 69~79줄
"캐싱은 비용만 줄이고 지연엔 무관" 할인 얘기만 들음 TTFT 도 줄임 ✓ 확인 가이드 샘플 2 해설 · prompt-caching ko 314·402줄
"지연 줄이려고 대화 도중 effort 를 요청마다 바꾼다" 요청마다 최적값 요청 수준 effort 변경은 캐시를 무효화 → 오히려 느려질 수 있음 ✓ 확인 effort ko 152·160줄
"fast mode 를 배치에 걸어 배치를 빠르게" 빠른 모드니까 배치에선 speed 미지원 ✓ 확인 batch-processing ko 63줄

미해결

  1. lever 순서표(카드 ⑥)는 공식 한 문서에 없음 — 지연 문서(모델 · 길이 · 스트리밍), 캐싱 문서, effort 문서를 합쳐 만든 순서라 업계 일반.
  2. fast mode 가 TTFT 도 줄이는지 : 받은 원문은 "출력 속도(output speed)"만 말함 (choosing-a-model ko 6줄). fast-mode 문서는 받지 않았음.
  3. temperature 를 낮추면 "때때로" 더 짧은 답 (reduce-latency ko 35줄) — 지연 lever 로 물을지 불확실, 카드엔 안 넣음.
  4. 공식 지연 문서(reduce-latency)는 캐싱·effort 를 지연 방법으로 들지 않음. 캐싱의 지연 효과는 샘플 2 해설·캐싱 문서, effort 는 effort·모델 선택 문서가 근거.

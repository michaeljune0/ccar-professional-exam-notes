한눈에

에이전트 성능을 아는 방법 6층 = 자동 eval · 운영(production) 모니터링 · A/B · 사용자 피드백 · transcript 직접 읽기 · 체계적 사람 평가. 어느 한 층도 전부 못 잡음 → 겹쳐 씀. 한 층에서 샌 실패를 다른 층이 잡음(스위스 치즈 모델)

층마다 시점이 다름 : 자동 eval = 출시 전·CI · 운영 모니터링 = 출시 뒤 · A/B = 트래픽이 충분할 때 큰 변경 · 피드백·transcript = 늘 · 사람 평가 = grader(채점기) 보정·주관적 출력

비유 배포 파이프라인. CI 테스트 → 카나리 → 운영 모니터링. CI 가 초록이어도 카나리를 보고, 카나리 몇 분 보고 전체 배포하지 않음

ELI5

구멍 난 치즈 여러 장을 겹쳐 놓는 거예요.

  • 한 장만 있으면 구멍으로 벌레가 빠져나가요.
  • 여러 장을 겹치면 구멍 자리가 달라서 벌레가 걸려요.
  • 치즈마다 잘 막는 곳과 늦게 막는 곳이 달라요.
  • 이 쪽은 "언제 어느 치즈를 먼저 대나"를 모아 둔 곳이에요.

개념 설명

원리

층 6개 = 무엇으로 아는가가 다 다름

  • 자동 eval : 실사용자 없이 코드로 과제를 돌려 채점. 빠르고 재현되고 커밋마다 돌릴 수 있음. 대신 과제가 실사용과 어긋나면 "통과"가 거짓 확신이 됨.
  • 운영 모니터링 : 실제 시스템의 지표·오류. 진짜 사용자 행동을 봄. 대신 문제가 사용자에게 먼저 닿은 뒤에야 알게 됨(사후 대응) · 채점할 정답이 없음.
  • A/B : 실사용 트래픽을 나눠 두 판을 비교. 유지율·과제 완료율 같은 진짜 결과를 재고 교란을 통제(control)함. 대신 유의성(우연이 아니라고 볼 만큼 표본이 쌓임)까지 수일~수주 · 트래픽이 충분해야 함 · 이미 배포한 변경만 시험 · 왜 움직였는지는 transcript 를 읽어야 알 수 있음.
  • 사용자 피드백 : 엄지 아래·버그 신고. 예상 못 한 문제를 실제 예시와 함께 줌. 대신 드물고, 내고 싶은 사람만 내고, 심한 문제 쪽으로 쏠리고, 이유를 잘 안 적음.
  • transcript 직접 읽기 : 사람이 대화를 읽음. failure modes(실패 유형) 감각·미묘한 품질을 잡음. 대신 규모를 못 키우고(사람 수만큼만) 정성 신호뿐.
  • 체계적 사람 평가 : 훈련된 평가자 여럿이 구조화해 채점. 최고 품질 판정 · LLM-as-judge(LLM 채점기)를 맞추는 기준. 대신 비싸고 느려 자주 못 돌림.

왜 겹치나

  • 층마다 구멍(못 보는 것)이 다름 → 한 층에서 샌 실패를 다른 층이 잡음. 스위스 치즈 모델.
  • 시점도 다름 : 출시 전엔 자동 eval · 사람 평가뿐, 출시 뒤에 운영(production) 모니터링 · 피드백이 생기고, 트래픽이 쌓여야 A/B 가 됨.
  • 가장 잘하는 팀의 기본 조합 = 자동 eval(빠른 반복) + 운영 모니터링(실제 결과) + 주기적 사람 검토(보정).

A/B 라는 말이 공식 문서 두 편에 세 뜻으로 나옴

  • demystifying-evals 표 : 실사용 트래픽으로 두 판 비교(이 카드의 A/B).
  • 같은 글 사람 grader(채점기) 표 : 방법 목록에 A/B testing 이 들어 있음 → 사람의 선택으로 채점하는 방식으로도 분류.
  • define-success : "기준 모델이나 이전 판과 성능 비교" 라는 넓은 뜻의 정량 방법. → 지문이 A/B 를 어느 뜻으로 쓰는지 먼저 봄.

핵심 질문 두 개

  • 지금 출시 전인가 뒤인가, 트래픽은 충분한가?
  • 이 층이 못 보는 것(구멍)을 어느 층이 막고 있나?

연습 문제

하루 2만 건 문의를 받는 고객지원 챗봇에 새 응답 흐름을 A/B 로 걸었다. 시작 3시간 만에몇 시간치 새 쪽의 과제 완료율이 4%p 높게 나오자 팀장은 트래픽도 충분하니 바로 전체 배포하자고 한다. 지금 판단은?

시험 대비

함정

  • ≠"오프라인 eval 통과했으니 A/B·운영 확인은 불필요" → 자동 eval 은 실사용 패턴과 어긋나면 거짓 확신
  • ≠"A/B 가 있으니 오프라인 eval 은 생략" → A/B 는 배포한 변경만 시험 · 수일~수주. 자동 eval 은 커밋마다 · 사용자 영향 없음
  • ≠"몇 시간치 A/B 가 좋으니 전체 배포" → 몇 시간치로는 유의성까지 못 감
  • ≠"새 버전이 더 나은지 카나리로 확인" → 카나리 = 일부에 내보내고 오류를 봄업계 일반 공식 문서에 카나리 없음. "두 변형 중 어느 쪽이 실사용에서 나은가" 는 변형끼리 실사용 결과를 비교 · 교란 통제 = A/B
  • ≠"사용자 불만(엄지 아래)을 주 탐지 수단으로" → 드물고 쏠림 · 사용자가 문제를 잡게 두면 사용자가 피해를 봄
  • ≠"운영 대시보드가 멀쩡하니 품질도 OK" → 운영 모니터링은 사후 대응 — 사용자가 먼저 겪음 · 채점할 정답이 없음
  • ≠"중요하니 변경마다 체계적 사람 평가" → 비싸고 느려 자주 못 돌림. grader 보정·주관적 출력에만
  • ≠"한 층만 제대로 하면 된다" → 어느 한 층도 전부 못 잡음

"Like the Swiss Cheese Model from safety engineering, no single evaluation layer catches every issue."

뒤집히는 때

1. 트래픽이 적은 사내 도구 — A/B 가 사실상 안 되는 때

  • 조건 : 하루 60건 쓰는 사내 도구. 새 프롬프트가 과제 완료율을 70% → 73% 로 올렸는지 보고 싶음.
  • 계산 : 두 비율 비교 표본식(양측 유의수준 5%, 검정력 80%) → 한 쪽당 약 3,550건. (1.96 + 0.84)² × (0.70×0.30 + 0.73×0.27) ÷ 0.03² ≈ 3,550. 하루 60건을 반반 나누면 한 쪽 30건 → 약 118일.
  • 비교 : 하루 2만 건 고객 챗봇이면 한 쪽 1만 건 → 표본은 하루 안에 참. 그래도 공식은 "수일~수주" (요일 효과 등 — 업계 일반).
  • 판단 : 적은 트래픽이면 A/B 대신 자동 eval + transcript 표본 읽기 + 피드백 분류.
  • 등급 : 업계 일반 (표본식은 통계 일반 지식, Anthropic 문서엔 표본 크기 세부 없음). "sufficient traffic" 조건 자체는 확인.
  • 근거 : demystifying-evals

2. 작은 변경인데 A/B 부터?

  • 조건 : 시스템 프롬프트의 말투 문장 하나만 바꿈.
  • 판단 : 공식은 A/B 를 "significant changes" 용으로 둠. 작은 변경은 자동 eval 로 먼저 보고, 효과가 작아 자동 eval 에서도 안 보이면 과제 셋을 키움(성숙한 에이전트는 작은 효과를 보려면 더 큰 eval).
  • 등급 : (A/B 대상 = 큰 변경 · 성숙하면 더 큰 eval) + 업계 일반("작은 변경은 A/B 안 함"이라는 직접 문장은 없음)
  • 근거 :

3. 오프라인 eval 은 올랐는데 운영 지표는 그대로

  • 조건 : 오프라인 eval +5%p, 출시 2주 뒤 과제 완료율 변화 없음.
  • 판단 : 자동 eval 이 실사용 패턴과 어긋났을 가능성(거짓 확신). transcript 표본을 읽고, 운영에서 본 실패를 eval 과제로 되돌림(■ 운영 → eval feedback loop).
  • 등급 : (자동 eval 약점 · 운영 모니터링 강점)
  • 근거 :

4. 법률 검토 에이전트 — 사람 평가를 아껴 쓰라는 규칙이 약해지는 때

  • 조건 : 답이 주관적이고 도메인 전문가만 맞고 틀림을 가릴 수 있음.
  • 판단 : 사람 평가는 "LLM-as-judge 보정·주관적 출력"에 쓰는 층 → 이 경우가 바로 그 자리. 그래도 매 변경마다가 아니라, 사람 판정으로 LLM-as-judge 를 맞춘 뒤 grader 로 규모를 키움(■ LLM-as-judge 설계).

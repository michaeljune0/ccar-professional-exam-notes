■ rate limit

rate limits : RPM · ITPM · OTPM · 429 · 헤더3.4 본편아래 설명 보기

카드

Messages API rate limit(속도 제한) = 모델 클래스별 분당 요청(RPM) · 분당 입력 토큰(ITPM) · 분당 출력 토큰(OTPM). 하나라도 넘으면 429 + 어느 한도인지 + retry-after(몇 초 기다릴지) ✓ 확인

조직 단위 · 사용량 티어(Start · Build · Scale · Custom)로 정해짐 · 보장된 최소가 아니라 허용 최대치 ✓ 확인

비유 API 게이트웨이 스로틀링. 토큰 버킷 · X-RateLimit-Remaining·Retry-After 헤더 · CDN 적중은 오리진 한도를 안 먹음

원리

세 한도 (모델 클래스별)

  • RPM(분당 요청) · ITPM(분당 입력 토큰) · OTPM(분당 출력 토큰). 하나라도 넘으면 429 + 어느 한도인지 + retry-after.
  • 조직 단위. 사용량 티어(Start · Build · Scale · Custom)로 정해지고, 쓰다 보면 올라감. 한도는 최대치일 뿐 보장이 아님.

토큰 버킷

  • 고정 간격으로 리셋되는 게 아니라 계속 채워짐 → 분당 한도가 초 단위로 걸릴 수 있음. 짧은 폭주가 한도 안에서도 429 를 냄.

무엇을 세나

  • ITPM : 캐시 안 된 입력 + 캐시 쓰기. 대부분 모델에서 캐시 읽기는 안 셈 → 캐싱이 한도를 사실상 넓힘 (■ 프롬프트 캐싱 · 규칙 ④).
  • OTPM : 실제 생성한 출력만. max_tokens 값은 안 셈.
  • 한도는 모델마다 따로 → 다른 모델은 각자 한도까지 동시에 씀.

429 의 두 얼굴

  • rate limit 429 : retry-after 있음 → 기다렸다 재시도.
  • 지출 상한 429 : retry-after 없음 · error_code: enforced_spend_limit_reached → 다음 달 1일 00:00 UTC 까지 재시도해도 실패.
  • 내가 건 지출 한도는 400. API 과부하는 529(내 한도 문제 아님).

재시도

  • 공식 SDK 가 연결 오류 · 429 · 5xx 를 지수 백오프로 기본 2번 자동 재시도하고 retry-after 를 따름.

뒤집히는 때

1. 캐싱이 ITPM 을 얼마나 넓히나 (새 숫자)

  • 조건 : ITPM 한도 50만(가정), 요청당 입력 6,000 토큰 중 5,000 이 매번 캐시 읽기.
  • 계산 : 캐싱 없으면 요청당 6,000 → 분당 약 83 요청. 캐시 적중이면 ITPM 에 1,000 만 셈 → 분당 500 요청 (6배).
  • 전제 : 대부분 모델 기준(각주 4 예외 아님) · 캐시 쓰기 요청(ITPM 에 셈)은 드묾 · RPM · OTPM 은 안 막힘.
  • 등급 : 계산 (셈 규칙은 확인)
  • 근거 : rate-limits ko 72~82줄

2. 캐싱이 안 듣는 때 — OTPM 이 먼저 막힘

  • 조건 : OTPM 한도 8만(가정), 응답이 평균 800 토큰.
  • 계산 : 80,000 ÷ 800 = 분당 100 요청이 상한. 입력 캐싱을 아무리 해도 출력은 그대로라 이 벽은 안 움직임.
  • 처방 : 출력 줄이기(■ 지연 줄이기 lever · 규칙 ③) · 상향 요청 · 쉬운 요청을 다른 모델(따로 된 한도)로. max_tokens 를 줄이는 건 OTPM 셈과 무관(실제 생성분만 셈).
  • 등급 : 계산 (OTPM 규칙은 확인)
  • 근거 : rate-limits ko 86·88줄

3. 분당 한도 안인데 429 가 나는 때

  • 조건 : RPM 120, 매 분 정각에 요청 40개를 한꺼번에 보냄.
  • 계산 : 분당 40 < 120 인데도, 공식 예처럼 분당 한도가 초 단위로 적용되면 120 RPM ≈ 초당 2 → 한 순간 40개는 넘침.
  • 처방 : 요청을 1분에 고르게 퍼뜨림 · 큐 · retry-after 따르기.
  • 전제 : 초 단위 환산은 문서 예시(60 RPM → 초당 1)와 같은 비례라고 가정.
  • 등급 : 계산 (폭주 규칙은 확인)
  • 근거 : rate-limits en 14줄 · ko 16줄

4. 재시도가 답이 아닌 때 — 지출 상한

  • 조건 : Start 티어(월 $500) 조직이 월 중순에 상한 도달, 429 가 계속.
  • 판단 : retry-after 없음 + enforced_spend_limit_reached → 다음 달 1일 00:00 UTC(한국 시각 09:00)까지 SDK 자동 재시도도 전부 실패. 재시도 로직을 늘리는 건 헛수고, 상향 요청(Rate limits 페이지) 또는 지원팀.
  • 등급 : ✓ 확인 (UTC→KST 환산은 계산)
  • 근거 : rate-limits ko 23~49·137줄

5. 한도 상향이 맞는 때

  • 조건 : 캐싱 적중률이 이미 높고(Usage 차트의 캐시 비율), 요청이 고르게 흐르는데도 캐시 안 된 입력·출력이 한도에 붙어 있음.
  • 판단 : 그때는 상향 요청이 정답. "상향 요청은 항상 오답"도 틀림.
  • 등급 : ✓ 확인
  • 근거 : rate-limits ko 123~137줄

오답 재료

오답 왜 끌리나 왜 틀리나 등급 근거
"캐시된 입력도 ITPM 을 똑같이 먹으니 캐싱은 rate limit(속도 제한)엔 소용없다 — 한도 상향만" 많은 제공자는 TPM 에 전부 셈 대부분 Claude 모델은 캐시 안 된 입력만 ITPM 에 셈 ✓ 확인 rate-limits en 72줄
"429 면 무조건 지수 백오프로 재시도" SDK 가 그렇게 함 지출 상한 429 는 재시도해도 계속 실패 ✓ 확인 rate-limits en 47줄
"max_tokens 를 크게 잡으면 OTPM 을 미리 차지한다" 예약처럼 느껴짐 실제 생성된 토큰만 셈 ✓ 확인 rate-limits en 86줄
"분당 한도 안이면 429 가 안 난다" 분당 숫자만 봄 토큰 버킷 · 짧은 폭주로 걸림 ✓ 확인 rate-limits en 14·16줄
"529 가 나니 한도 상향을 요청" 둘 다 '너무 많다' 류 529 는 API 과부하, 내 한도와 무관 ✓ 확인 errors en 15줄
"한도는 이만큼 처리를 보장한다" 숫자가 계약처럼 보임 최대치일 뿐 보장된 최소 아님 ✓ 확인 rate-limits ko 17줄
"워크스페이스 한도를 합쳐 조직 한도보다 크게 잡으면 더 쓸 수 있다" 합이 크니까 조직 한도는 항상 적용 ✓ 확인 rate-limits ko 152줄

미해결

  1. 티어별 RPM · ITPM · OTPM 숫자 : rate-limits 원문의 한도 표가 받은 파일(ko·en)에 빠져 있음 (defuddle 이 표를 못 옮김, 검색어 "<table>"·"| Model" 0건). 숫자는 이 카드에 안 넣음.
  2. 각주 4("이 제한은 cache_read_input_tokens 를 ITPM 사용량에 포함")가 붙은 모델이 어느 것인지 같은 이유로 확인 못 함 — 캐싱 카드의 "대부분 모델"과 같은 수준으로만 씀.
  3. 티어 통합(Start · Build · Scale, 2026-06-26)은 시험 가이드(2026-07) 직전 변경 — 시험이 옛 티어 이름(1~4)으로 물을 가능성(추론).

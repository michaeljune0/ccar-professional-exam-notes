■ human-in-the-loop 게이트 위치

human approval gates : 되돌릴 수 있나 · 피해 범위 · 승인 피로 93%5.3 본편아래 설명 보기

카드

사람 승인(human approval)은 행동 개수가 아니라 결과 크기에 건다. 되돌릴 수 없고 파괴적이거나 피해 범위(blast radius)가 남에게 미치는 행동 앞에만 사람 → 나머지는 자동, 사람은 언제든 멈추고 방향을 바꿈 ✓ 확인

행동마다 승인시키면 승인 피로(approval fatigue) — 사람이 뭘 승인하는지 안 봄. Claude Code 수동 권한 프롬프트는 실제로 93% 승인됨 (2026-09-28 조회) ✓ 확인

비유 변경 관리. 표준 변경은 사전 승인 목록으로 자동, 프로덕션 DB 삭제만 CAB 승인. 모든 배포에 승인을 걸면 아무도 안 읽고 도장만 찍음

지문

개발자가 코딩 Agent 에게 "오래된 브랜치 정리해 줘" 라고 했다. Agent 는 브랜치를 지우는 명령상태 바꿈을 만들었고, 대상은 팀이 같이 쓰는 원격 브랜치 40개공유 자원다. 팀은 "모든 행동에 확인창을 띄우자" 와 "권한 확인을 전부 끄자" 사이에서 고민한다. 이 행동은 어떻게 다뤄야 할까?

흐름

나머지 규칙

  1. ⑤

    막혔을 때 : 거부는 도구 결과로 돌아가 에이전트가 더 안전한 길을 찾음(우회 금지). 연속 3번 또는 총 20번 거부면 멈추고 사람에게. 헤드리스(claude -p)는 물을 사람이 없어 프로세스 종료 ✓ 확인 (2026-09-28 조회) [5.3①] [7.3②]

규칙 원문 ①②③④⑥ (갈림길로 그린 규칙)

    검토 우회·남에게 영향main 직행 push · 프로덕션 배포 · 에이전트가 안 만든 공유 자원·작업 수정
  2. ②

    나머지는 자동 : 상태 못 바꾸는 도구(읽기·검색·코드 탐색) = 허용 목록 · 프로젝트 안 파일 편집 = 분류기 없이(버전 관리로 검토) · 진짜 손해 가능성 있는 행동만 마지막 단계(분류기)로 ✓ 확인. 사람은 언제든 멈추고 방향을 바꿈 ✓ 확인 → 자율성 단계는 ■ 가장 작은 맞는 형태 [5.3①] [7.3②]

  3. ③

    승인 피로 : 행동마다 승인하면 사람이 주의를 잃음. 수동 확인 93% 승인 ✓ 확인. 선택지 셋 = 샌드박스(안전하지만 유지보수 큼, 네트워크·호스트 접근이 필요하면 격리가 깨짐) · 전부 건너뛰기(--dangerously-skip-permissions, 유지보수 0·보호 0) · 수동 확인(중간) → auto mode = 수동 승인 자리를 모델 분류기가 대신함 ✓ 확인 [5.3①] [5.2①]

  4. ④

    분류기의 한계 : 실제 과잉 행동(overeager)을 17% 놓침 (2026-09-28 조회). 위험은 알아보는데 "그 동의가 이 행동의 피해 범위까지 덮나"를 틀림 → 전부 건너뛰기 대비로는 큰 개선, 모든 행동을 신중히 승인하던 사람 대비로는 후퇴일 수 있음. 고위험 인프라의 신중한 사람 검토를 대신하지 않음 ✓ 확인 [5.3①]

  5. ⑥

    동의 범위 : 사용자가 말한 것만 승인된 것. 에이전트가 스스로 고른 건 사용자가 말하기 전까진 미승인. "브랜치 정리해 줘" ≠ 원격 브랜치 일괄 삭제 허락 · "고칠 수 있어?" = 질문이지 지시 아님 · 한 번 승인은 패턴이 아님 ✓ 확인

함정

  • ≠"모든 행동에 사람 승인이 가장 안전" → 승인 피로, 93% 승인 ✓ 확인
  • ≠"승인이 귀찮으니 권한 확인 전부 끔" → 보호 0, 대부분 상황에서 위험 ✓ 확인
  • ≠"분류기(auto mode)가 있으니 고위험 인프라도 사람 없이" → 대신 못 함 ✓ 확인
  • ≠"비슷한 걸 전에 승인했으니 이번도 OK" → 한 번 승인은 패턴이 아님. 그 동의가 이 행동의 피해 범위를 덮는지 봐야 ✓ 확인
  • ≠"필요 없는 환불·삭제 도구를 두고 확인창" (샘플 1 C) → 먼저 빼기 → ■ 최소 권한 ✓ 확인
  • ≠"두 번째 Claude 를 검토자로" → 목록 5.3① 의 매력적인 오답. 단 공식 auto mode 는 실제로 모델 분류기가 승인을 대신함 → 일상 작업이면 맞는 방식, 고위험이면 사람 (업계 일반 + ④)
  • ≠"강제 대기 시간 추가" → 판단 기준(되돌릴 수 있나·피해 범위)을 안 바꿈 업계 일반
  • ≠"AUP 의 Human-in-the-loop = 이 게이트" → AUP 쪽 이름은 고위험 용도에서 자격 전문가가 내용·결정을 전파 전에 검토하라는 요구. 이 카드는 되돌리기 어려운 행동 앞 승인 위치 → ■ AUP 고위험 용도 ✓ 확인

  • 미끄럼틀 탈 때마다 허락을 받게 하면 선생님이 지쳐서 그냥 "응" 해요.

원리

승인은 공짜가 아님

  • 승인의 비용 = 사람의 주의력. 게이트가 많을수록 한 건당 주의가 줄어듦 → 승인 피로. 수동 권한 프롬프트 93% 승인.
  • 그래서 게이트를 늘리면 보호가 늘지 않고 오히려 떨어질 수 있음. 도장만 찍는 승인은 보호가 아님.

어디에 거나 = 틀렸을 때의 비용

  • 되돌릴 수 있나 : 프로젝트 안 편집은 버전 관리로 되돌림 → 자동. force-push·대량 삭제는 못 되돌림 → 막음.
  • 피해 범위 : 내 것만인가, 공유 자원·남의 작업인가. 남에게 미치면 되돌릴 수 있어도 막음(검토 우회·남에게 영향 묶음).
  • 신뢰 경계 : 데이터가 밖으로 나가거나 밖의 코드를 들여오면 막음. 기본으로 믿는 건 지금 작업 중인 git repo 뿐.

층으로 거름 (auto mode)

  • 1층 허용 목록(상태 못 바꾸는 도구) → 2층 프로젝트 안 편집 → 3층 분류기(진짜 손해 가능성) → 사람(반복 거부·고위험(high-stakes) 인프라).
  • 위협 4가지 = 과잉 행동(overeager) · 정직한 실수(피해 범위 오판) · 프롬프트 인젝션 · 목표가 어긋난 모델. 막는 법은 모두 "그 행동을 막기".
  • 주 표적 = 과잉 행동. 악의 없이 도우려다 사용자가 허락한 선을 넘음 → 겉보기엔 합리적인 문제 해결이라 잡기 어려움.

분류기의 약점

  • 위험을 알아보는 것과 "사용자 동의가 이 행동까지 덮나"를 판정하는 건 다른 일. 놓친 것 대부분이 후자.
  • 그래서 고위험 인프라는 신중한 사람 검토를 남김.

핵심 질문 두 개

  • 이 행동이 틀렸을 때 되돌릴 수 있나?
  • 틀렸을 때 누가(나만 / 남까지) 다치나?

뒤집히는 때

1. 되돌릴 수 있는데도 막아야 하는 때

  • 조건 : 백업으로 되돌릴 수 있는 변경이지만, 대상이 팀 공용 스테이징 큐·다른 사람이 만든 예약 작업.
  • 판단 : 기준은 "되돌림" 하나가 아님. 기본 차단 묶음에 "에이전트가 안 만든 공유 자원·작업 수정" 이 따로 있음 → 되돌릴 수 있어도 남에게 영향이면 막음.
  • 등급 : ✓ 확인
  • 근거 : claude-code-auto-mode en 77줄

2. 되돌릴 수 없어도 사람 없이 가는 때

  • 조건 : 사용자가 "로컬 브랜치 exp-47 지워 줘" 처럼 대상을 명시.
  • 판단 : 사용자가 말한 것이 승인의 범위. 이름까지 댄 삭제는 에이전트가 고른 행동이 아님 → 동의가 이 행동을 덮음. 반대로 "오래된 브랜치 정리" 는 원격 일괄 삭제를 덮지 않음.
  • 등급 : 확인(원칙) · 분류기가 실제로 어디까지 통과시키는지는 미해결 4
  • 근거 : en 38·64줄

3. 하루 800건 행동 — 분류기 vs 사람, 숫자로

  • 조건 : 하루 행동 800건 중 진짜 위험한 과잉 행동이 6건이라고 가정.
  • 계산 : 분류기(전체 파이프라인) 놓침 17% → 6 × 0.17 ≈ 1건/일 통과. 오탐 0.4% → 794 × 0.004 ≈ 3건/일 잘못 막힘, 각각 재시도 1번 비용.
  • 비교 : 전부 건너뛰기면 6건 전부 통과 → 분류기가 크게 나음. 모든 건을 신중히 보는 사람이면 이론상 0건 → 분류기가 후퇴. 그런데 실제 수동은 93% 승인이라 "신중한 사람" 전제가 무너짐.
  • 등급 : 계산. 17%·0.4% 는 글의 평가 데이터 값(실제 과잉 행동 n=52, 실제 트래픽 n=10,000)이라 다른 트래픽에 그대로 맞는다는 보장 없음.
  • 근거 : en 3·93~104·154줄

4. 무인 파이프라인(헤드리스)

  • 조건 : CI 에서 claude -p 로 돌림.
  • 판단 : 물을 사람이 없어서 거부가 쌓이면 프로세스 종료. 사람 게이트가 필요한 행동(프로덕션 배포 등)은 그 파이프라인에 두지 말고 승인 단계를 따로.
  • 등급 : 종료 동작은 확인 · 처방은 업계 일반
  • 근거 : en 152줄

미해결

  1. 목록 문구 "빈도가 아니라 결과 크기" 의 '빈도' 는 원문에 없는 말. 원문 기준은 되돌릴 수 없음 · 파괴 · 피해 범위 · 동의 범위 (claude-code-auto-mode en 38·64·74~77줄).
  2. 목록의 문제 상황 "간호사용 triage 초안 vs 환자에게 가는 알림" 과 "환자에게 가는 알림" 예시는 받아 둔 원문에서 못 찾음(검색어 patient·nurse·triage, en-claude-code-auto-mode · en-safe-trustworthy-agents — 걸린 1건은 보안 이슈 triage, safe-trustworthy-agents en 5줄).
  3. 목록의 매력적인 오답 "두 번째 Claude 인스턴스를 검토자로" 는 공식 auto mode(모델 분류기가 사람 승인자 대신, en 19줄 "acting as a substitute for a human approver")와 부딪힘. 고위험·일상 중 어느 문맥인지로 갈림.
  4. 명시 지시된 비가역 행동을 분류기가 실제로 통과시키는지 : 원칙(en 64줄)만 있고 사례 없음.
  5. 93% · 17% · 0.4% · 3/20 은 날짜 표기 없는 엔지니어링 글 값(분류기 = Sonnet 4.6 시점). 릴리스 노트엔 2026-05-28 "Auto mode 를 더 많은 사용자로 확대" 1줄만 있음(en-release-notes 250줄) → 수치가 이후 바뀌었는지 모름.
  6. 목록이 대비한 "샌드박싱 글 '권한 프롬프트 84% 감소'" 는 원문 파일이 없어 확인 안 함. HITL/HOTL 용어는 받은 원문 어디에도 없음(업계 용어).

흐름

나머지 규칙

  1. ③

    새 컨텍스트 : 방금 쓴 코드에 치우치지 않게 다른 세션(Writer/Reviewer) 또는 서브에이전트가 리뷰 ✓ 확인. 리뷰어는 diff 와 넘겨받은 기준만 보고 변경을 만든 추론(reasoning)은 못 봄 → 결과를 제 기준으로 평가. 리뷰 지시 = 점검할 작업 · 대조할 계획 · 무엇이 finding 인지 ✓ 확인

규칙 원문 ①②④⑤⑥ (갈림길로 그린 규칙)
  1. ①

    찾기 = 커버리지 : 리뷰 프롬프트의 "only report high-severity issues" · "be conservative" · "don't nitpick" 을 Opus 4.8 은 이전 모델보다 더 충실히 따를 수 있음 → 조사는 똑같이 하고도 기준 아래 발견은 보고 안 함 → 정밀도는 오르고 재현율은 떨어짐 ✓ 확인

    처방 = 전부 보고(불확실·저심각도까지) + 발견마다 신뢰도·추정 심각도 → 뒤 필터가 순위. 두 번째 단계가 실제로 없어도 도움, 있으면 "찾기의 일은 커버리지" 라고 명시 ✓ 확인 (Opus 4.8 프롬프트 가이드) [7.2③]

  2. ②

    한 번에 거를 거면 '중요한' 같은 두루뭉술한 말 대신 판정선을 구체적으로 : "잘못된 동작 · 테스트 실패 · 오해 부르는 결과는 전부, 순수 스타일·네이밍만 생략" ✓ 확인. 고친 프롬프트는 eval·테스트 케이스 일부로 돌려 재현율·F1 이 실제로 올랐는지 봄 ✓ 확인

  3. ④

    리뷰어는 찾으라면 찾음 : 멀쩡해도 무언가 보고 → 전부 쫓으면 과설계(추상화 층 · 방어 코드 · 일어날 수 없는 경우의 테스트). 정확성·명시된 요구에 영향 주는 공백만 표시, 나머지는 선택 ✓ 확인

  4. ⑤

    관리형 Code Review 가 이 구조 그대로 : 여러 에이전트가 종류별로 병렬 찾기 → 검증 단계가 실제 코드 동작과 대조해 거짓 양성을 거름 → 중복 제거 → 심각도 순위(🔴 Important = 머지 전 고칠 버그 · 🟡 Nit) → 인라인 코멘트 ✓ 확인

    기본은 정확성(프로덕션을 깨는 버그) 중심, 스타일·테스트 커버리지 아님 · PR 을 승인·차단하지 않음(check run 은 늘 neutral — 게이트는 내 CI 가 check run 출력을 읽어서) ✓ 확인

    조정 = REVIEW.md(리뷰 전용 : 심각도 재정의 · nit 개수 상한 · 건너뛸 경로 · 저장소 고유 검사 · 검증 기준 · 재리뷰 때 nit 억제). CLAUDE.md 위반은 nit 로 ✓ 확인

    로컬 /code-review effort : low·medium = 확신 높은 것만(거짓 양성↓) · high~max = 커버리지↑ ✓ 확인 (2026-09-28 조회)

  5. ⑥

    넓히기 : Owner 가 조직에 한 번 켜고 저장소를 골라 넣음, 나중에 추가 · 저장소별 on/off. 트리거 = PR 생성 1회 / 매 push / Manual(@claude review) — 매 push 가 가장 비쌈, 트래픽 큰 저장소는 Manual ✓ 확인. 리뷰당 평균 $15~25, 월 지출 상한 설정 가능 ✓ 확인 (2026-09-28 조회)

    가치 높은 흐름 몇 개로 시범 → 측정 → 확대 업계 일반 공식은 저장소 선택·추가·트리거 lever 만, 시범 개수 없음

CCA-F

봄 (4.6 다중 인스턴스·다중 패스 리뷰 — 만든 쪽에게 채점을 안 맡김 · 4.1 명시적 기준으로 거짓 양성 줄이기 — '보수적으로' 같은 말은 기준이 아님) — 여기선 팀이 리뷰봇을 운영하며 "지적이 많다" 불만에 어디서 거르나(찾기 vs 뒤 단계), 어떻게 넓히나(저장소 · 트리거 · 비용)로 묻나

함정

  • ≠"지적이 많다 → 찾기 프롬프트를 '고심각도만'으로" → 재현율이 떨어짐. 거르기는 뒤 단계에서 ✓ 확인
  • ≠"'중요한 것만' 보고" → 두루뭉술한 말. 판정선을 구체적으로 ✓ 확인
  • ≠"코드를 쓴 세션에 '스스로 다시 검토해'" → 방금 쓴 코드에 치우침. 새 컨텍스트 ✓ 확인
  • ≠"리뷰어 지적은 전부 고친다" → 과설계. 정확성·명시된 요구만 ✓ 확인
  • ≠"Code Review 로 머지를 막는다" → 승인·차단 안 함. 게이트는 내 CI 가 check run 출력을 읽어서 ✓ 확인
  • ≠"새 모델로 바꿨더니 지적이 줄었다 → 모델 퇴보" → 옛 모델용 '보수적' 지시를 더 충실히 따른 하네스 효과일 가능성 ✓ 확인
  • ≠"전사에 한 번에 켠다" → 저장소를 골라 넣고 추가 (업계 일반 + 비용 ✓ 확인)

신호

"Report every issue you find, including ones you are uncertain about or consider low-severity."

"Tell the reviewer to flag only gaps that affect correctness or the stated requirements, and treat the rest as optional."

"a verification step checks candidates against actual code behavior to filter out false positives."

ELI5

물고기를 잡을 때 촘촘한 그물로 다 건진 다음, 배 위에서 골라내는 거예요.

  • 그물코를 처음부터 크게 하면 작은 물고기는 빠져나가요.
  • 그러면 "요즘 고기가 없네" 하고 착각해요.
  • 고르는 일은 배 위에서, 다른 사람이 하면 더 공정해요.
  • 바다 전체에 한꺼번에 그물을 던지기 전에, 몇 군데서 먼저 해 봐요.

원리

찾기와 거르기는 다른 일

  • 찾기의 목표 = 커버리지(재현율). 거르기의 목표 = 정밀도. 한 프롬프트에 둘을 섞으면 모델이 거르기 기준을 찾기에 적용함.
  • Opus 4.8 은 지시를 글자 그대로 따르는 쪽(prompting-claude-opus-4-8 en 55줄) → "고심각도만" · "보수적으로" 가 있으면 버그를 찾아 놓고도 기준 아래라 판단한 건 보고 안 함. 조사 깊이는 같은데 보고만 줄어 → 정밀도는 오르고 재현율이 떨어짐. 모델이 약해진 게 아니라 하네스 효과.
  • 처방 : 찾기는 전부 보고 + 발견마다 신뢰도·추정 심각도 → 뒤 단계(검증 · 중복 제거 · 순위)가 거름. 뒤 단계가 없으면 판정선을 구체적으로.

새 컨텍스트

  • 코드를 만든 세션은 "왜 그렇게 짰나" 를 들고 있어 자기 코드에 치우침. 새 세션·서브에이전트는 diff 와 넘겨받은 기준만 보고 제 기준으로 평가.

"전부 보고" vs "정확성만 표시" — 충돌 아님

  • 찾기 단계(뒤에 필터가 있음) → 전부 보고.
  • 리뷰 결과를 바로 구현자가 받아 고침(필터 없음) → 정확성·명시 요구에 영향 주는 공백만 표시, 나머지는 선택. 안 그러면 과설계.
  • 즉 "보고 기준" 은 그 출력을 다음에 누가 받나 로 정함. (두 공식 문장을 이어 읽은 해석 — 업계 일반)

관리형 Code Review = 위 구조의 제품판

  • 종류별 에이전트 병렬 찾기 → 실제 코드 동작과 대조하는 검증 → 중복 제거 → 심각도 순위 → 인라인 코멘트. 승인·차단은 안 함(사람 몫).
  • 기본은 정확성. REVIEW.md 로 심각도·nit 상한·건너뛸 경로·검증 기준을 저장소마다 조정.

넓히기

  • Owner 가 저장소를 골라 넣고 나중에 추가 · 저장소별 on/off · 트리거 3가지(1회 / 매 push / Manual). 비용은 리뷰 수에 비례 → 트리거와 저장소 수가 비용 lever(손잡이).

뒤집히는 때

1. "전부 보고" 가 오히려 틀릴 때

  • 조건 : 거르기 단계가 없고, 리뷰 결과가 PR 코멘트로 곧장 작성자에게 감.
  • 판단 : 뒤 필터가 없으면 전부 보고 = 코멘트 홍수. 공식도 "두 번째 단계 없이도 쓸 수 있다" 고 했지만, 한 번에 거를 거면 판정선을 구체적으로 주라는 게 같은 글의 다음 문장. 관리형 Code Review 를 쓰면 필터가 제품 안에 있으니 REVIEW.md 로 nit 상한(예 "많아야 5개, 나머지는 개수만")을 걺.
  • 등급 : ✓ 확인
  • 근거 : prompting-claude-opus-4-8 en 138·140줄 · code-review en 389줄

2. 모델을 올렸더니 지적이 줄었음

  • 조건 : 리뷰 봇을 새 모델로 바꾼 뒤 주당 지적 수가 크게 줄었고, 팀은 "새 모델이 버그를 덜 찾는다" 고 봄.
  • 판단 : 옛 모델에 맞춘 "보수적으로" · "고심각도만" 을 새 모델이 더 충실히 따른 하네스 효과일 가능성. 먼저 그 문구를 걷어내고 전부 보고 + 뒤 필터로 바꾼 뒤, 같은 eval 부분집합으로 재현율을 다시 측정. 모델 되돌리기가 첫 수가 아님.
  • 등급 : ✓ 확인
  • 근거 : prompting-claude-opus-4-8 en 130·142줄

3. 한꺼번에 켜면 얼마나 드나 — 시범이 이기는 계산

  • 조건 : 시범 = 저장소 3개 · 저장소당 월 PR 60건 · "PR 생성 1회" 트리거. 전사 = 저장소 25개 · 같은 PR 수 · "매 push" 트리거 · PR 당 평균 push 4회.
  • 계산 : 시범 = 3 × 60 = 180 리뷰 × $15~25 = 월 $2,700~4,500. 전사 = 25 × 60 × 4 = 6,000 리뷰 × $15~25 = 월 $90,000~150,000 (약 33배).
  • 전제 : 리뷰당 비용을 공식 평균 $15~25 로 고정(실제는 PR 크기·복잡도·검증할 이슈 수에 비례, push 뒤 리뷰는 더 작을 수 있음) · 저장소별 PR 수 동일 · 가격 = 2026-09-28 조회값.
  • 판단 : 저장소를 골라 넣고 트리거를 싸게 시작 → 저장소별 평균 리뷰 비용 칸·주간 비용 차트로 측정 → 추가. 월 지출 상한도 걸 수 있음.
  • 등급 : 계산 (비용·lever 는 확인, "시범 → 확대" 순서는 업계 일반)
  • 근거 : code-review en 272·296·302~308·469~473·503줄

4. 같은 세션 리뷰가 괜찮을 때?

  • 조건 : 한 줄 수정 뒤 "방금 고친 거 한번 봐" 를 같은 세션에서.
  • 판단 : 공식은 새 컨텍스트가 더 낫다(improves)고 했지 같은 세션 확인을 금지하진 않음. 오래 무인으로 돈 작업일수록 독립 검사가 중요하다는 게 공식 방향 → 작고 지켜본 변경이면 같은 세션 확인도 설 자리가 있음, 무인·큰 변경이면 새 컨텍스트.
  • 등급 : 업계 일반 (공식 두 문장 "improves" · "The longer Claude works unattended, the more an independent check matters" 을 이어 읽은 해석)
  • 근거 : best-practices en 700·777줄 · Skilljar cci 486938 ("The less you watched, the more you verify.")

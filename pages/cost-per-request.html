  1. ①

    식 : 건당 = 캐시 안 된 입력 × 입력가 + 캐시 쓰기 × 1.25배(5분)·2배(1시간) + 캐시 읽기 × 0.1배 + 출력 × 출력가 ✓ 확인 [1.6③]

    공식 계산 예 (Opus 5, Managed Agents 1시간 세션) : 입력 5만 $0.25 + 출력 1.5만 $0.375 + 런타임 $0.08 = $0.705 → 입력 중 4만을 캐시 읽기로 $0.525 ✓ 확인

    이 예에서 출력은 토큰 수가 입력의 3분의 1 인데 값은 더 큼 ($0.375 > $0.25) → 출력 단가 5배의 뜻 (계산)

  2. ②

    단가 (백만 토큰당, 2026-09-28 조회) ✓ 확인 [1.6③]

  3. ③

    줄이는 공식 순서 = 맞는 모델 → 캐싱 → 배치(급하지 않은 작업) → 사용 패턴 감시 ✓ 확인 [1.6③] [4.5②]

    • 맞는 모델 : 간단 = Haiku · 대부분 프로덕션 = Sonnet · 가장 복잡한 추론(reasoning) = Opus ✓ 확인. 낮출 땐 eval 로 품질 확인 뒤 낮춤 ✓ 확인. 한 모델 안에선 effort 로 지능 ↔ 비용 맞바꿈 (■ 지연 줄이기 lever) ✓ 확인. 과제 무시하고 제일 작은 모델은 오답 (샘플 2 B) ✓ 확인
    • 캐싱 : 반복되는 컨텍스트 비용 줄이기. 긴 고정 앞부분을 캐싱하면 입력 대부분이 0.1배로. 5분 캐시는 읽기 1번부터 이득. 규칙 본문 = ■ 프롬프트 캐싱 ✓ 확인
    • 배치 : 입력·출력 모두 50%. 캐싱 할인과 함께 적용됨. 규칙 본문 = ◆ Batch API vs 동기 호출 ✓ 확인
    • 출력이 대부분이고 몇 분 안에 답해야 하면 : "짧게 답해" + max_tokens 로 출력 줄이기 (■ 지연 줄이기 lever) ✓ 확인
    • 감시 : 토큰 소비를 추적해 최적화 기회 찾기. 응답 usage 에 input_tokens · output_tokens · cache_read_input_tokens · cache_creation_input_tokens ✓ 확인
  4. ④

    숨은 입력 : tools 정의(이름·설명·스키마) · tool_use·tool_result 블록 · 도구가 있으면 자동으로 붙는 도구 시스템 프롬프트(모델별 수백 토큰, 예 Sonnet 5 354) · 웹 검색 = 1,000회당 $10 + 결과는 이후 턴까지 입력 토큰 ✓ 확인 [1.6③]

    곱해지는 것 ✓ 확인 [1.6③] [2.1①]

    • 미국 전용 추론 inference_geo: "us" = 모든 토큰 1.1배 (4.6 이후 모델)
    • fast mode = 비싼 요금 (Opus 5.5 $8/$40), 배치와 같이 못 씀
    • 1M 창 전체가 표준 단가 (900k 요청도 9k 요청과 같은 토큰당 요율)

함정

  • ≠"과제와 상관없이 제일 작은 모델로" → 품질 위험 (샘플 2 B) ✓ 확인
  • ≠"정책을 잘라 입력을 줄임" → 필요한 정책을 잃음 (샘플 2 A) ✓ 확인
  • ≠긴 출력 일에 캐싱만 → 할인은 입력가에만 붙는 배수라 출력 토큰이 청구서 대부분이면 캐싱해도 총비용이 조금만 줄어듦 ✓ 확인
  • ≠"몇 분 안에 답해야 하는데 배치로 50%" → 배치엔 분 단위 약속이 없음 (◆ Batch API vs 동기 호출) ✓ 확인
  • ≠새 모델로 옮기며 단가만 비교 → 토큰 수가 약 30% 느는 걸 놓침 ✓ 확인. 예 Sonnet 4.6 $3/$15 → Sonnet 5 $2/$10 은 단가 33% 싸지만 토큰 1.3배면 약 13% 만 쌈 (계산)
  • ≠도구 정의·검색 결과를 빼고 입력을 셈 → 전부 입력 토큰 ✓ 확인
  • ≠"200k 넘는 긴 요청은 할증" → 4.6 이후는 1M 창 전체가 표준 단가 ✓ 확인 (옛 규칙 : 2026-02-05 릴리스 노트엔 200k 초과 할증 있었음)
  • ≠"Managed Agents 세션도 배치로 50%" → 배치 모드 없음 ✓ 확인

ELI5

택배 요금이랑 비슷해요.

  • 보내는 상자(입력)보다 받는 상자(출력)가 다섯 배 비싸요.
  • 매번 똑같이 넣는 포장재는 창고에 맡기면 10분의 1 값이에요.
  • 급하지 않으면 느린 배송으로 반값이에요.
  • 그러니 영수증에서 제일 큰 줄부터 줄여요.

원리

값의 뼈대

  • 요청 1건 = 입력 토큰 × 입력가 + 출력 토큰 × 출력가. 한 달 = 건당 × 건수.
  • 출력가 = 입력가의 5배 (Haiku 4.5 $1/$5 · Sonnet 5 $2/$10 · Opus 5.5 $4/$20 · Opus 5 $5/$25, 백만 토큰당).
  • 그래서 "입력이 많은 일"과 "출력이 많은 일"은 줄이는 수단이 다름.

수단별로 깎이는 곳

  • 캐싱 = 입력가에만 거는 배수. 쓰기 1.25배(5분) · 2배(1시간), 읽기 0.1배. 출력은 그대로.
  • 배치 = 입력·출력 모두 50%. 대신 끝나는 시각을 약속 안 함. 캐싱 할인과 함께 적용됨.
  • 모델 = 단가 자체를 바꿈. Opus 5.5 → Haiku 4.5 는 입력·출력 모두 4분의 1. 대신 품질이 흔들릴 수 있어 eval 로 확인.
  • effort = 한 모델 안에서 출력 토큰(thinking(사고)·도구 호출·답)을 줄임.

곱해지는 것 · 숨은 것

  • 새 토크나이저 : 같은 글이 약 30% 더 많은 토큰 → 단가표가 같아도 청구가 늘 수 있음.
  • 미국 전용 추론 1.1배 · fast mode 는 Opus 5.5 에서 2배 단가($8/$40).
  • 도구 정의 · 도구 시스템 프롬프트 · tool_result · 웹 검색 결과는 전부 입력 토큰. 웹 검색은 1,000회당 $10 따로.
  • 1M 창은 전 구간 같은 단가 → 긴 요청이라 할증 붙는 일은 없음(4.6 이후).

공식 줄이는 순서

  • 맞는 모델 → 캐싱 → 배치(급하지 않은 일) → 사용 패턴 감시.
  • 이 순서는 목록일 뿐 지문 조건이 먼저 : 청구서의 큰 줄이 입력인가 출력인가, 몇 분 안에 답해야 하는가.

뒤집히는 때

1. 입력이 대부분인 일 — 캐싱이 제일 큼

  • 조건 : 고정 앞부분 6천 토큰 + 질문 200 토큰, 답 300 토큰, Haiku 4.5, 월 30만 건.
  • 계산 : 캐싱 없음 = 6,200 × $1 + 300 × $5 (백만 토큰당) = 건당 $0.0077 → 월 $2,310. 캐시 적중 = 6,000 × $0.10 + 200 × $1 + 300 × $5 = 건당 $0.0023 → 월 $690. 약 70% 절감.
  • 그다음 : 캐싱 뒤엔 출력이 건당 값의 약 65% → 다음 lever(손잡이)는 출력 쪽(길이 · effort).
  • 전제 : 월 30만 건이 고르게 와서(분당 약 7건) 5분 안에 늘 다음 호출이 있음 · 캐시 쓰기 값은 무시할 만큼 드묾 · 가격 = 2026-09-28 조회값.
  • 등급 : 계산 (배수·단가는 확인)
  • 근거 : prompt-caching ko 39줄 표 · pricing ko 83·85줄

2. 출력이 대부분인 일 — 캐싱은 거의 안 먹힘

  • 조건 : 보고서 생성, 입력 3천(그중 고정 2,500) · 출력 5천, Sonnet 5.
  • 계산 : 캐싱 없음 = 3,000 × $2 + 5,000 × $10 = 건당 $0.056. 캐싱 = 2,500 × $0.20 + 500 × $2 + 5,000 × $10 = $0.0515 → 약 8% 절감. 배치 = $0.028 → 50%. 출력을 2,500 으로 줄이면 $0.031 → 약 45%.
  • 판단 : 마감이 없으면 배치, 있으면 출력 길이 · 모델 쪽. "캐싱부터"가 순서상 앞이라도 이 일에선 효과가 작음.
  • 등급 : 계산
  • 근거 : prompt-caching ko 39줄 표 · pricing ko 123줄

3. 모델 교체가 캐싱보다 큰 때

  • 조건 : 같은 보고서(입력 3천 · 출력 5천)를 Opus 5.5 로 돌리다 eval 상 품질 여유가 큼.
  • 계산 : Opus 5.5 = (3,000 × $4 + 5,000 × $20) × 1.3 = 건당 약 $0.146. Haiku 4.5 = 3,000 × $1 + 5,000 × $5 = $0.028. 약 5.2배 차이. 캐싱은 입력 쪽만 줄여 이만큼은 못 줄임.
  • 전제 : 같은 글이 Opus 5.5(새 토크나이저)에서 1.3배 토큰, Haiku 4.5 는 옛 토크나이저(pricing 15줄이 "Claude 4.7 이후"만 새 토크나이저라고 해서 그렇게 봄 — 추론).
  • 판단 : 공식 순서 1번이 "맞는 모델"인 이유. 단 eval 로 품질을 확인한 경우만 — 무작정 낮추기는 샘플 2 B 오답.
  • 등급 : 계산 · 조건부(eval 전제)
  • 근거 : prompt-caching ko 39줄 표 · pricing en 15·346줄 · 가이드 샘플 2 해설

4. 새 모델이 단가만큼 안 싼 때

  • 조건 : Sonnet 4.6($3/$15) → Sonnet 5($2/$10) 로 옮김.
  • 계산 : 단가 × 2/3, 같은 글 토큰 × 약 1.3 → 청구 × 약 0.87. 33% 가 아니라 약 13% 절감.
  • 등급 : 계산. 30% 는 "approximately" · 내용 따라 다름 → 실제는 token counting API 로 잼.
  • 근거 : 릴리스 노트 en 168·211줄 · prompt-caching ko 39줄 표

미해결

  1. pricing 모델 단가표(ko·en 9줄)는 defuddle 판에서 칸이 밀려 Sonnet 5 입력·출력 칸이 비어 있음 → 단가는 같은 표인 prompt-caching ko 39줄과 릴리스 노트 en 96·168줄로 대조함.
  2. 시험 시점의 단가 : 가이드가 어느 모델 가격을 전제했는지 모름 → 시험은 배수(출력 5배 · 읽기 0.1배 · 배치 50%)와 역할(빠르고 싼 ↔ 능력 높은)로 물을 가능성 (추론).
  3. 공식 "줄이는 순서"는 번호 목록 4줄뿐 — 우선순위인지 나열인지 공식 문장 없음. 뒤집히는 때 2·3 처럼 지문 조건이 순서를 바꿀 수 있음 (계산).
  4. 목록 1.6③ 의 "가격 숫자는 바뀌니 역할로 판단한다"는 공식 문장 없음 (업계 일반).
  5. Haiku 4.5 가 옛 토크나이저인지 공식 명시 없음 — "Claude 4.7 이후 = 새 토크나이저"에서 미룬 것 (뒤집히는 때 3 전제).

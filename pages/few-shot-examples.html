    3~5개가 최선. Claude 에게 예시의 관련성·다양성을 평가시키거나 처음 세트를 바탕으로 더 만들게 해도 됨 ✓ 확인

  3. ③

    경계 사례 목록 금지 : 모든 규칙을 말하려고 경계 사례를 줄줄이(laundry list) 넣지 말고, 기대 행동을 잘 보여 주는 서로 다르고 대표적인 예시를 고름 — 예시는 "천 마디 말보다 나은 그림" ✓ 확인

  4. ④

    좋은 예 > 나쁜 예·금지 지시 : 간결함 같은 문체는 적절한 간결함을 보여 주는 좋은 예가 나쁜 예나 "하지 마" 지시보다 효과적 (Sonnet 5 문서) ✓ 확인

함정

  • ≠"모든 예외 경우를 규칙 목록으로 길게 나열" → 비권장. 대표 예시 몇 개 ✓ 확인
  • ≠"같은 모범 답 하나를 여러 번 반복" → 다양성 조건 위반, 의도 안 한 패턴을 따라 함 (반복 자체를 콕 집은 공식 문장은 없음 — 다양성 조건에서 추론)
  • ≠"예시를 지시 문장 사이에 그냥 섞음" → 태그로 구분 ✓ 확인
  • ≠"예시는 많을수록 좋다(수십 개)" → 공식은 3~5개가 최선. 그 이상이 나쁘다는 문장은 없음 업계 일반 컨텍스트는 한정 자원이라 늘 비용이 듦
  • ≠"정책 문서를 few-shot 블록으로 옮겨 비용·지연(latency) 줄이기" → 캐시되는 재사용 앞부분이 안 생김 (공식 샘플 2 오답 D) ✓ 확인
  • ≠"JSON 모양을 예시만으로 보장" → 예시는 방향. 보장은 structured outputs → ■ structured outputs ✓ 확인
  • ≠목록 영상 요령 "권장 7단계 순서(명확→이유→예시→XML→역할→형식→체이닝)대로" → 공식은 소개 순서일 뿐 규칙 아님. 가까운 원칙 = 최소 프롬프트부터 (목록 영상 요령 — 공식 근거 없음)

ELI5

그림 그리는 법을 말로 설명하는 대신, 잘 그린 그림 몇 장을 보여 주는 거예요.

  • 말로 "예쁘게 그려" 하면 사람마다 다르게 그려요.
  • 잘 그린 그림 서너 장을 보여 주면 비슷하게 그려요.
  • 그런데 보여 준 그림이 다 빨간색이면, 빨간 게 규칙인 줄 알아요.
  • 그래서 서로 다른 그림을 골라서, "이건 보기예요" 하고 따로 담아 줘요.

원리

예시가 지시보다 센 이유

  • 형식·어조·구조는 말로 정확히 설명하기 어려움. 예시는 "보여 주기" 라 모델이 바로 따라 함 — 공식은 예시를 출력 형식·어조·구조를 잡는 가장 확실한 방법 중 하나로 봄.
  • 추상적인 지침보다 원하는 출력의 예시가 더 효과적.

예시의 부작용 = 우연한 공통점도 배움

  • 예시끼리 공통점(길이·주제·첫 단어)이 있으면 모델은 그것도 규칙으로 읽음. 그래서 "다양성" 조건 — 경계 사례를 넣고 의도 안 한 패턴을 따라 하지 않게 충분히 다르게.
  • 예시가 지시와 섞이면 어디까지가 예시인지 헷갈림 → <example>/<examples> 태그.

규칙 목록 vs 대표 예시

  • 모든 경계 사례를 규칙 문장으로 나열하면 프롬프트가 길어지고 깨지기 쉬움 → 서로 다르고 대표적인(canonical) 예시 몇 개로 기대 행동을 그림처럼.
  • 컨텍스트는 한정 자원이라 예시도 "작지만 쓸모 있는 정보가 많은(high-signal)" 쪽으로.

언제 넣나

  • 처음부터 예시를 잔뜩 넣지 않음. 가장 좋은 모델로 최소 프롬프트를 시험 → failure modes(실패 유형)가 형식·어조면 예시, 판단 기준이면 지시.
  • 모양을 보장해야 하면 예시가 아니라 스키마(■ structured outputs).

뒤집히는 때

1. 예시를 넣었더니 더 한쪽으로 쏠린 때

  • 조건 : 티켓 요약 예시 3개가 전부 환불 건이고 전부 두 문장. 이후 배송 문의 요약도 두 문장 + 환불 말투로 나옴.
  • 판단 : 예시가 모자란 게 아니라 다양성 부족. 개수를 늘리기보다 주제·길이·경계 사례가 다른 예시로 바꿈.
  • 등급 : 확인(원리) · 사례는 새로 만든 것
  • 근거 : en-full 86줄 "vary enough that Claude doesn't pick up unintended patterns"

2. "예시가 비싸서 뺀다" 가 틀리는 때

  • 조건 : 예시 4개 × 약 600토큰 = 2,400토큰. 하루 3만 요청 · Haiku 4.5 (입력 $1, 캐시 읽기 $0.10 / 백만 토큰).
  • 계산 : 캐시 없이 = 2,400 × 30,000 = 7,200만 토큰/일 → $72/일. 예시를 고정 앞부분에 두고 캐시 적중 = 0.1배 → $7.20/일(+ 5분마다 쓰기 1.25배).
  • 전제 : 예시가 요청마다 똑같고 바뀌는 입력 앞에 있음 · 캐시 대상 앞부분(tools + system + 예시)이 Haiku 4.5 최소 캐시 길이 4,096토큰 이상(예시 2,400 만으로는 미달 — 시스템 프롬프트·도구 정의와 합쳐 넘어야 함) · 호출 간격이 5분보다 짧음 · 가격 = 2026-09-28 조회값.
  • 판단 : 예시 비용이 문제면 빼기 전에 앞부분 고정 + 캐싱. 단 "정책을 예시 블록으로 옮기면 캐시된다" 는 반대로 오답(샘플 2 D) — 캐싱은 위치가 아니라 요청마다 똑같은 앞부분에서 생김.
  • 등급 : 계산 (배수·가격·최소 길이는 확인)
  • 근거 : ko-pricing-2026-09-28 9·85·87줄 · ko-prompt-caching 183줄(Haiku 4.5 최소 4,096) · ■ 프롬프트 캐싱 · 규칙 ①② · sample-questions-p6-7 66줄

3. 예시로 안 되는 때 (모양 보장)

  • 조건 : 예시 5개로 JSON 모양을 보여 줬는데 하루 몇 건씩 파싱 실패. 뒤쪽 시스템이 재시도를 못 함.
  • 판단 : 예시는 방향. 보장은 structured outputs(제약 디코딩) → ■ structured outputs. 예시는 필드 값의 문체·기준을 잡는 데 계속 씀.
  • 등급 : ✓ 확인
  • 근거 : structured-outputs en 10~21줄

4. 예시보다 지시가 먼저인 때

  • 조건 : 첫 프롬프트, failure modes 를 아직 모름.
  • 판단 : 가장 좋은 모델로 최소 프롬프트부터. 실패가 형식·어조면 예시, 그 밖이면 지시. 처음부터 예시를 쌓는 건 순서가 거꾸로.
  • 등급 : ✓ 확인
  • 근거 : effective-context-engineering en 45줄

미해결

  1. 예시 수 상한 : 3~5개 "최선" 문장만 있고, 그 이상일 때 품질이 떨어지는지 공식 문장 없음.
  2. 문자 그대로 따르는 모델(Opus 4.8·Sonnet 5)에서 예시가 일반화되는 폭 : 모델 문서는 "지시" 의 범위만 말함 — 예시 문맥 문장 없음(상황 변수의 해당 줄은 추론).
  3. 목록 영어 신호 3개("Include 3–5 examples for best results." · "we recommend working to curate a set of diverse, canonical examples…" · "It's best to start by testing a minimal prompt…")는 원문에서 모두 찾음. 단 마지막 문장의 원문 따옴표는 곧은 ' 가 아니라 ’(effective-context-engineering en 45줄).

함정

  • ≠"체이닝으로 나누면 더 빠르고 싸다" → 지연을 내주고 정확도를 얻음 ✓ 확인
  • ≠"단계가 여러 개면 무조건 체이닝" → 한 요청 안에서 대부분 처리. 체이닝은 중간 검사·구조 강제일 때 ✓ 확인
  • ≠"thinking 켜 놓고 프롬프트에 단계 계획을 길게" → 일반 지시가 나을 때가 많음 ✓ 확인
  • ≠"추론을 보려고 '생각 과정을 답에 써라'" → thinking 블록을 읽음. 새 모델은 거절될 수 있음 ✓ 확인
  • ≠"thinking 블록이 빈 칸 → thinking 안 함" → display 기본 "omitted". 추론은 signature 에 담겨 있음, 그대로 돌려줌 ✓ 확인
  • ≠"thinking 없는 턴이 있음 → 설정 오류" → adaptive 는 단순한 요청엔 thinking 을 건너뜀, 정상 ✓ 확인
  • ≠Skilljar(2025 제작) "thinking 없이 먼저, 프롬프트를 다듬어도 정확도가 모자라면 켠다" → 평가로 정한다는 원칙은 맞지만, 지금은 새 모델 다수가 기본 켜짐이고 못 끄는 모델도 있음 (Skilljar)

ELI5

어려운 수학 숙제를 푸는 두 가지 방법이에요.

  • 혼자 연습장에 끄적이며 한 번에 풀 수도 있어요.
  • 한 단계 풀 때마다 선생님께 보여 드리고 다음으로 넘어갈 수도 있어요.
  • 한 번에 푸는 게 보통 더 빨라요.
  • 중간에 누가 꼭 봐야 하면 단계마다 보여 드려야 해요.
  • 이 쪽은 "언제 나눠야 하나"를 모아 둔 곳이에요.

원리

thinking (한 요청 안)

  • 모델이 답하기 전에 thinking 블록에서 문제를 다시 말하고, 방법을 시도하고, 중간 결과를 확인하고, 안 되는 길은 버림 → 답은 text 블록에.
  • adaptive 모드면 모델이 요청마다 "생각할지·얼마나"를 스스로 정함. 단순한 요청엔 건너뜀.
  • 도구를 쓰면 도구 호출 사이에도 생각함(interleaved thinking, adaptive 면 자동). 도구 루프 전체가 한 어시스턴트 턴.
  • 비용 : thinking(사고) 토큰은 출력 토큰으로 청구, max_tokens 에 포함. 안 보여도 청구.
  • 한계 : 중간 결과가 모델 안에서만 흐름 → 코드·사람이 단계 사이에 끼어들 틈이 없음. 새 모델은 추론(reasoning) 원문도 안 줌(요약 또는 빈 칸).

prompt chaining(프롬프트 체이닝 · 여러 호출)

  • 일을 순서대로 나눠 앞 호출의 출력을 다음 호출이 처리. 사이에 코드 검사(gate)를 둘 수 있음.
  • 호출마다 쉬운 일이 되니 정확도가 오름. 대신 호출이 순서대로 쌓여 지연(latency)이 늘어남.
  • 얻는 것 : 단계마다 기록·평가·분기 · 사람 확인 · 정해진 구조 강제.
  • 흔한 모양 = 자기 교정 (초안 → 기준으로 검토 → 고침).

수동 CoT

  • thinking 이 꺼져 있을 때의 대안. "생각해 보라"고 요청하고 <thinking>·<answer> 태그로 추론과 답을 나눔.
  • 추론이 답 글 안에 섞여 나오므로 코드가 태그로 잘라 내야 함.

핵심 질문 두 개

  • 단계 사이의 중간 결과를 코드나 사람이 봐야 하나?
  • thinking 을 켤 수 있는 모델인가, 켜져 있나?

뒤집히는 때

1. 체이닝이 오히려 싼 때 — 단계를 작은 모델로

  • 조건 : 한 요청 + thinking 을 큰 모델에서 돌리던 일을, 체이닝으로 나눠 단계마다 작은 모델로 돌림.
  • 계산 : 입력 1만 · thinking+답 출력 3천을 Opus 5.5($4 / $20, 백만 토큰당)로 한 번 = 1만 × $4 + 3천 × $20 = $0.04 + $0.06 = $0.10. 3단계 체이닝을 Haiku 4.5($1 / $5)로, 단계마다 입력 1만 · 출력 800 = 3 × (1만 × $1 + 800 × $5) = 3 × ($0.010 + $0.004) = $0.042.
  • 전제 : 단계마다 같은 입력 1만을 다시 보냄(캐시 없음) · 작은 모델로도 eval 상 품질 유지 · 가격 = 2026-09-28 조회값.
  • 판단 : "체이닝 = 늘 비쌈"도 틀림. 비용은 호출 수보다 모델 단가가 좌우. 단 지연은 호출 3번이 순서대로 쌓임 → "체이닝이 더 빠르다"는 여전히 틀림.
  • 등급 : 계산 (단가 확인). 공식 근거 = 여러 프롬프트로 나눈 대화 흐름은 지연을 위해 Haiku 4.5 가 더 맞을 수 있다는 문장.
  • 근거 : ko-pricing 9줄 표 · customer-support-chat en 85줄 · building-effective-agents en 61줄

2. thinking 을 못 끄는 모델에서 "생각이 비싸니 쪼개자"

  • 조건 : Opus 5.5 에서 thinking 토큰 비용이 부담이라 일을 체이닝으로 나눔.
  • 판단 : 쪼개도 호출마다 thinking 이 또 켜짐(항상 켜짐). thinking 비용을 줄이는 lever(손잡이)는 체이닝이 아니라 effort ↓ (Opus 5.5 기본은 이미 medium). 체이닝은 중간 검사가 필요할 때만.
  • 등급 : ✓ 확인 (못 끔 · effort 가 주 lever) + 추론 (쪼개도 thinking 이 줄지 않을 것)
  • 근거 : effort en-2026-09-28 47줄 · thinking en 65줄

3. 수동 CoT 가 역효과인 때

  • 조건 : 옛 프롬프트의 "먼저 단계별 생각을 답에 적어라"를 새 모델에 그대로 가져옴.
  • 판단 : Fable 5.1·Opus 5.5·Fable 5 는 답 글로 내부 추론을 끌어내려는 요청을 거절할 수 있음. Opus 5 는 thinking 을 끄고 수동 CoT 를 쓰면 내부 XML 태그가 답에 샐 수 있음 → 켜 둔 채 낮은 effort. 수동 CoT 는 "thinking 이 꺼진" 모델의 대안일 뿐.
  • 등급 : ✓ 확인
  • 근거 : thinking en 121줄 · prompting-best-practices en 287줄 · thinking-troubleshooting en 134~136줄

■ 운영 → eval feedback loop

production signals → test cases → regression in CI4.6 본편아래 설명 보기

카드

출시 뒤 운영(production) 모니터링은 분포가 바뀌거나(distribution drift) 예상 못 한 실제 실패를 잡는 층. 단 사후 대응 — 사용자가 먼저 겪음 ✓ 확인

그래서 잡은 실패를 그대로 두지 않고 루프를 닫음 : 피드백은 계속 분류 · transcript 는 매주 표본으로 읽기 → 실패 한 건마다 transcript 로 "에이전트가 진짜 틀렸나, grader(채점기)가 맞는 답을 거절했나" 가름 → 진짜 실패는 테스트 케이스로 eval 셋에 → 다음 변경부터 CI 에서 막음 ✓ 확인

"실패가 테스트 케이스가 되고, 테스트 케이스가 regression(회귀)을 막는다" ✓ 확인

비유 SLO 위반 → 포스트모템 → 액션 아이템을 회의록에만 두지 않고 regression 테스트·알림 규칙으로 추가

함정

  • ≠"오프라인 eval 통과했으니 문제없다" → eval 셋에 없는 유형이면 통과는 아무것도 말해 주지 않음. 운영 모니터링이 잡는 층 ✓ 확인
  • ≠"사용자 신고로만 감시" → 드물고 내고 싶은 사람만 냄 ✓ 확인
  • ≠"모델이 저절로 드리프트했으니 모델 교체" → 모델 ID 는 고정 스냅숏 ✓ 확인
  • ≠eval 점수가 떨어지자 transcript 안 읽고 에이전트를 고침 → grader 가 맞는 답을 거절했을 수 있음 ✓ 확인
  • ≠놓친 사례를 회의에서 공유하고 끝 → eval 셋에 안 들어가면 루프가 안 닫힘 업계 일반
  • ≠"운영 대시보드가 초록이니 품질 OK" → 운영 모니터링엔 채점할 정답이 없음 ✓ 확인
  • ≠"online LLM judge 가 공식 처방" → 공식 본문엔 없음, 부록의 외부 도구 소개에만 ✓ 확인

ELI5

받아쓰기 시험을 떠올려 보세요.

  • 학교 시험지는 늘 같은 단어만 나와서 매번 100점이에요.
  • 그런데 밖에서 새 단어를 만나면 자꾸 틀려요.
  • 틀린 단어를 오답 노트에 적고, 다음 시험지에 넣어요.
  • 그러면 같은 단어는 다시 안 틀려요. 이 쪽은 "그 노트를 언제 어떻게 쓰나"를 모아 둔 곳이에요.

원리

운영(production) 모니터링은 입구, 끝이 아님

  • 오프라인 eval 은 가진 과제만 잼. 운영에 새 유형이 들어오면 eval 셋은 그걸 모름.
  • 운영 모니터링은 실제 사용을 봐서 그 빈틈을 잡음. 대신 사후 대응(사용자가 먼저 겪음) · 신호에 잡음이 많음 · 채점할 정답이 없음.
  • 그래서 잡은 실패를 eval 과제로 바꿔야 다음부터 출시 전에 막힘.

실패 판정이 먼저

  • eval 이 "실패"라고 해도 grader(채점기)가 맞는 답을 거절했을 수 있음. transcript 를 읽어 가름.
  • 에이전트 실수면 과제로 넣고 에이전트를 고침. grader 오판이면 grader 를 고침.

드리프트는 입력 쪽

  • 공식 글의 drift = 입력 분포가 바뀜. 모델 ID 는 고정 스냅숏이라 같은 ID 의 가중치·구성은 안 바뀜.
  • 같은 ID 에서 작은 동작 차이가 보이면 가장 유력한 원인은 서빙 인프라(라우터 · 안전 분류기 · 샘플링).

핵심 질문 두 개

  • 이 실패 유형이 지금 eval 셋에 있나?
  • 이 실패는 에이전트의 것인가, grader 의 것인가?

뒤집히는 때

1. "오프라인 eval 통과 = 품질 OK" 가 틀리는 때 — 분포가 바뀜

  • 조건 : eval 셋 40개는 전부 기존 상품군 문의, 통과율 95%. 새 상품군을 출시해 운영 문의의 25% 가 새 상품군이 됨. 새 상품군 성공률은 60% 라고 가정.
  • 계산 :
  • 오프라인 = 여전히 95% (셋에 새 상품군이 0개)
  • 운영 실제 = 0.75 × 95% + 0.25 × 60% = 71.25% + 15% = 86.25%

  • 새 상품군 과제 10개를 넣은 뒤 오프라인 = (40 × 0.95 + 10 × 0.6) ÷ 50 = (38 + 6) ÷ 50 = 88% → 이제 셋이 문제를 보여 줌

  • 판단 : 운영 모니터링·피드백으로 잡은 새 유형을 과제로 넣어야 오프라인 점수가 현실을 따라감. 과제 개수 비율은 운영 비율과 같을 필요는 없음(업계 일반).

  • 전제 : 성공률 60% · 비율 25% 는 가정.
  • 등급 : 계산 (층의 역할은 확인)
  • 근거 : demystifying-evals en 225·302줄

2. eval 점수가 떨어졌는데 에이전트는 맞은 때 — grader 오판

  • 조건 : 문구 일치로 채점하는 과제가 "환불 기한 14일"만 정답으로 받음. 새 프롬프트 뒤 에이전트가 "2주 안에 환불"로 답해 실패 처리가 늚.
  • 판단 : transcript 를 읽으면 답은 맞음 → 에이전트가 아니라 grader 를 고침(■ grader 고르기 · ■ LLM-as-judge 설계). 점수만 보고 프롬프트를 되돌리면 좋은 변경을 버림.
  • 등급 : ✓ 확인 (transcript 로 가름) · 예시는 설명용
  • 근거 : demystifying-evals en 261줄

3. "모델 ID 그대로니 모델 쪽은 볼 것 없음" 이 약간 틀리는 때

  • 조건 : 프롬프트·검색·문서 아무것도 안 바꿨는데 같은 모델 ID 에서 답 모양이 조금 달라짐.
  • 판단 : 가중치·구성은 고정이 맞음. 다만 서빙 인프라(요청 라우터 · 안전 분류기 · 샘플링 로직)는 바뀔 수 있고, 안정적이던 ID 의 뜻밖의 작은 차이는 그게 가장 유력한 원인. "가중치가 몰래 바뀜" 은 여전히 오답. 대응은 같음 — 그 사례를 과제로 넣어 regression 으로 지킴.
  • 등급 : ✓ 확인
  • 근거 : model-ids-and-versions ko·en 63·71~73줄

4. 들어온 실패를 전부 과제로 넣을 수 없는 때

  • 조건 : 월간 검토에서 실패 사례가 수십 건씩 옴.
  • 판단 : 사용자 영향 순으로 넣음. 처음엔 실제 실패에서 뽑은 20~50개로도 충분히 시작(■ 첫 eval 셋 만들기). 늘어 통과율이 높아진 과제는 regression suite 로 졸업.
  • 등급 : ✓ 확인
  • 근거 : demystifying-evals en 88·221·225줄

개념 설명

원리

왜 100% 를 약속 못 하나

  • 가장 발전된 모델도 때때로 사실과 다른 답을 냄 (공식). 모델을 키워도 이 문장은 안 바뀜.
  • 에이전트는 실행마다 결과가 다름 (공식). 같은 질문도 매번 같게 나오지 않음.
  • 그래서 "정확하다" 는 약속할 수 없는 것. 약속할 수 있는 건 잰 값(통과율·분위수)과 틀렸을 때의 경로.

무엇을 약속하나

  • 품질 : held-out 평가셋 통과율 + 오류 심각도. 한 차원이 아니라 여러 차원.
  • 지연 : 평균이 아니라 분위수 ("응답 95% 가 200ms 미만").
  • 가용성 : 내가 올라탄 윗단(API)이 무엇을 약속하는지부터. Standard 티어 = best-effort, Priority Tier = 99.5% 가동 목표.
  • 틀렸을 때 : 위험 등급별 사람 검토 · 에스컬레이션 · "모르겠다" 허용.

숫자를 거는 순서 (업계 일반 — SRE 습관)

  • SLI(실제로 잰 값) → SLO(내부 목표) → SLA(어기면 결과가 따르는 외부 약속).
  • 재기 전에 확인할, 숫자를 흔드는 요인 : effort 기본값(모델마다 다름) · rate limit(속도 제한 — 보장 아닌 최대치, 짧은 폭주도 429) · 인프라.

핵심 질문 두 개

  • 이 숫자를 실제로 재 봤나, 그리고 흔드는 요인을 확인했나?
  • 틀렸을 때 누가, 어떤 경로로 잡나?

갈림 기준

약속하는 것 = 잰 숫자 + 틀렸을 때의 경로. "정확하다"는 약속 안 함

  • "100% 정확"은 약속 안 함 — 가장 발전된 모델도 때때로 사실과 다른 답을 냄 ✓ 확인 · 에이전트는 실행마다 결과가 다름 ✓ 확인. 더 큰 모델로 바꿔도 이 문장은 그대로 ✓ 확인

대신 거는 것 : 품질 = held-out 평가셋 통과율 + 오류 심각도(공식 예 "오류의 90% 는 불편 수준") ✓ 확인 · 지연(latency) = 분위수(예 "응답 95% 가 200ms 미만") ✓ 확인 · 틀렸을 때 = 사람 검토 · 에스컬레이션 경로 ✓ 확인 → 기준 문장 쓰는 법 = ■ 성공 기준

  • "약속 안 함" 은 모델 행동에만 : 코드·권한이 강제하는 한도(권한 없는 자격증명 · 서비스 쪽 검사가 막는 금액·동작)는 그 장치를 근거로 약속해도 됨 — CLAUDE.md 지시는 권고, hook 은 결정적이고 반드시 실행 ✓ 확인 (코드·권한 검사로 넓힌 건 해석). 프롬프트 지시로 막은 한도는 권고일 뿐이라 약속 근거가 못 됨 ✓ 확인
  • 목표는 현재 프런티어 모델 역량에 비춰 현실적으로(달성 가능) · 대부분 여러 차원 ✓ 확인
  • "매번 맞아야" 하는 고객 대면이면 pass^k 로 측정 — 시도당 75% 면 3번 모두 성공 ≈ 42% ✓ 확인 → ◆ pass@k vs pass^k
  • 내부 eval 목표 100% 는 다른 말 : regression(회귀) eval 은 거의 100% 통과가 정상 · 맥락에 준 회사·상품 정보 정확도는 100% 목표 ✓ 확인 — 고객 약속이 아니라 평가 목표
  • SLA 를 아예 없애는 것도 답 아님 : 가이드 목표 6.3 이 "(including SLAs)", 1.6 value pillars(가치 축)에 성능 SLA ✓ 확인 → ■ value pillars 5개

거는 순서

실측(SLI) → 내부 목표(SLO) → 외부 약속(SLA = 어기면 보상 등 결과가 따르는 약속). 용어·순서는 업계 일반 — Anthropic 문서에 SLA/SLO 정의 없음

지연은 모델 크기 · 프롬프트 복잡성 · 기반 인프라에 따라 달라짐 ✓ 확인 → 재 보기 전 숫자는 못 믿음

effort 를 명시 : low effort 는 응답 시간·비용을 크게 줄임 ✓ 확인. 생략하면 모델 기본값 — Opus 5.5 는 medium, Opus 5 이전은 high → 모델만 바꿔도 지연·품질이 움직임 시험 뒤 변경 Opus 5.5 출시 2026-09-22 → ■ 지연 줄이기 lever

rate limit 은 보장된 최소가 아니라 허용 최대치 ✓ 확인 · 넘으면 429 + 어느 한도인지 + retry-after ✓ 확인 · 짧은 폭주도 429 ✓ 확인 → ■ rate limit

가용성 : Standard 티어 = best-effort 가용성 ✓ 확인 · Priority Tier = 99.5% 가동 목표, 약정(분당 입력·출력 토큰 · 1/3/6/12개월 · 특정 모델 버전) 넘는 요청은 Standard 로 ✓ 확인 · Opus 5.5 · Sonnet 5 · Fable 5.1 등은 Priority Tier 미지원 ✓ 확인 (2026-09-28 조회)

윗단(API)이 약속 안 한 가동률을 내 SLA 로 걸지 않음 — 그 가동률을 약속으로 걸려면 대비책(재시도·대체 경로)부터 업계 일반

사람 안전망

틀리면 비용이 큰 결과 → 사람 검토. 위험 등급을 나눠 고위험(high-risk)은 자동 차단, 중위험이 쌓이면 사람 검토 대상으로 표시 ✓ 확인 → ■ moderation 위험 등급 · 행동 앞 승인은 ■ human-in-the-loop 게이트 위치

"모르겠다" 허용 : 불확실을 인정할 권한을 명시적으로 줌 → 거짓 정보를 크게 줄임 ✓ 확인. 주장마다 인용을 달게 해 감사 가능하게 ✓ 확인

사람에게 넘길 대화를 붙잡지 않게(에스컬레이션 놓침을 따로 셈) : 에스컬레이션 정확도 95% 이상을 목표로 ✓ 확인

틀려도 비용이 작은 결과 → 자동 + 표본 확인 업계 일반

연습 문제

고객지원 Agent 가 환불 금액을 확정해 안내한다. 금액이 틀리면 고객에게 돈이 잘못 나간다비용이 큼. 영업은 "더 큰 모델로 바꾸고 계약서에 '100% 정확' 을 넣자"100% 약속고 한다. 틀린 답은 어떻게 다룰까?

시험 대비

함정

  • ≠"더 큰 모델로 바꾸면 100% 가 된다" → 가장 발전된 모델도 때때로 틀림 ✓ 확인
  • ≠사람 관문 없음 + "100% 정확" 약속 → 틀린 답이 그대로 고객에게 업계 일반 · 틀리면 비용이 큰 결과는 사람 검토 ✓ 확인
  • ≠"'빠르고 정확함'을 마케팅 문구로 약속" → 숫자 없는 말. 구체적·측정 가능해야 ✓ 확인 (■ 성공 기준)
  • ≠"약속이 위험하니 SLA 자체를 없앤다" → 가이드 목표가 SLA 를 관리 대상으로 둠 ✓ 확인. 잰 숫자로 거는 게 답 업계 일반
  • ≠"regression eval 이 거의 100% 통과하니 서비스 정확도 100% 약속" → regression eval = 예전에 되던 과제를 아직 하나. 고객 약속과 다른 말 ✓ 확인
  • ≠반대 함정 : "모델은 보장 못 하니 어떤 것도 약속 안 함 · 정확도 숫자만 제시" → 코드·권한이 막는 한도는 그 장치를 근거로 약속 가능 ✓ 확인 (적용은 해석)
  • ≠"프롬프트를 다듬었으니 정책대로 동작한다고 약속" → 프롬프트 지시는 권고 ✓ 확인
  • ≠"평균 지연 2초 약속" → 분위수로 ✓ 확인
  • ≠"rate limit 만큼 처리량 보장" → 허용 최대치일 뿐 ✓ 확인
  • ≠"Standard 티어 위에 99.9% 가동 SLA" → best-effort 위에 윗단보다 센 약속 업계 일반 계산 = 설명 쪽

뒤집히는 때

1. "100%" 가 맞는 답일 때 — 내부 eval 목표

  • 조건 : 지문이 계약 약속이 아니라 내부 평가 목표를 묻는다.
  • 판단 : 공식 고객지원 가이드는 맥락에 준 회사·상품 정보 정확도와 견적 정확도에 "100% 목표"를 둠. regression(회귀) eval 도 거의 100% 통과가 정상.
  • 등급 : ✓ 확인
  • 근거 : customer-support-chat-full en 144·156줄 "Target 100% accuracy" · demystifying-evals en 86줄 "should have a nearly 100% pass rate"
  • 주의 : "100% 가 나오면 항상 오답" 으로 외우면 여기서 틀림. 가르는 말 = 약속(외부)인가 목표(내부)인가.

2. 시도당 정확도가 높아도 "매번" 은 훨씬 낮을 때

  • 조건 : 고객 대면 에이전트, 같은 유형 요청을 반복 처리. 지문이 "사용자는 매번 같은 결과를 기대"라고 함.
  • 계산 : pass^k = (시도당 성공률)^k. 시도당 92% · k = 5 → 0.92^5 ≈ 0.659 → 약 66%.
  • 전제 : 시도끼리 독립이라고 봄 (공식 예 0.75³ ≈ 42% 와 같은 식).
  • 등급 : 계산 (식은 확인)
  • 근거 : demystifying-evals en 205·211줄
  • 뜻 : "정확도 92%" 를 "거의 항상 맞음" 으로 약속하면 사용자 체감과 어긋남 → 약속 문장에 무엇을 셌는지(시도당 vs k번 모두)를 적음.

3. 윗단보다 센 가용성 약속

  • 조건 : Priority Tier 약정 위에서 고객에게 99.9% 가동 SLA 를 걸려 함.
  • 계산 : 30일 = 43,200분. 99.5% → 허용 중단 216분(3.6시간). 99.9% → 43.2분. 내 약속이 윗단 목표보다 5배 빡빡.
  • 전제 : 윗단 중단이 곧 내 중단(대체 경로 없음). Standard 티어는 목표 숫자조차 없음(best-effort).
  • 등급 : 계산 (99.5% · best-effort 는 확인)
  • 근거 : service-tiers en 9·88줄
  • 처방 : 대비책(재시도 · 대체 모델·경로)을 먼저 설계하거나 약속을 낮춤 (업계 일반).

4. 분당 한도 안인데 429

  • 조건 : 분당 300 RPM 한도, 평균은 분당 200건인데 매시 정각에 1초에 12건이 몰림.
  • 계산 : 공식 예 "60 RPM 이 초당 1건으로 적용될 수 있음" 과 같은 비율이면 300 RPM ≈ 초당 5건 → 12건 폭주는 초과.
  • 등급 : 계산 (비율 적용은 추론 — 공식은 60→1 예만 듦)
  • 근거 : rate-limits en 14·17줄
  • 뜻 : 처리량 약속은 평균이 아니라 폭주 모양까지 재고 나서.

5. 모델만 바꿨는데 지연 SLO 가 흔들림

  • 조건 : Opus 5 에서 effort 를 안 적고 쓰다가 Opus 5.5 로 교체.
  • 판단 : Opus 5.5 기본 = medium (Opus 5 이전 = high) → 생략한 요청은 한 단계 낮게 돎 → 지연·비용·품질이 함께 움직임. 이전 설정을 가져오지 말고 effort 스윕.
  • 등급 : ✓ 확인 (시험 뒤 변경 — 2026-09-22 출시. 시험은 "effort 를 명시해 예상치 못한 지연 피하기" 로 물을 가능성 — Sonnet 4.6 문장)
  • 근거 : effort ko 47·101줄 · 릴리스 노트 en 15줄

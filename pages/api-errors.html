이 개념으로 푸는 판단 (할 수 있어야 하는 것)

  • 7.3③ API 오류가 쏟아질 때 무엇부터 보나? — 오류 종류별 대응 (재시도할 것 / 한도를 볼 것 / 오류가 아닌 것)

한눈에

API 오류 = HTTP 상태 + error.type(JSON). 할 일은 코드가 가름 — 500·529 = 일시 오류라 지수 백오프 재시도 · 429 = 한도(속도 또는 지출 상한) · 504 = 긴 요청은 스트리밍 · 400대 = 내 요청·키·권한을 고침 ✓ 확인

모든 응답에 request-id 헤더(오류 본문엔 같은 값 request_id) → 문의·추적의 열쇠. 거절은 오류가 아님(HTTP 200) → ■ stop_reason 으로 분기 ✓ 확인

비유 5xx 는 백오프 재시도 + 서킷 브레이커, 429 는 스로틀·쿼터 확인, 4xx 는 클라이언트 버그 수정. 추적은 X-Request-ID 로 게이트웨이·백엔드 로그를 잇기

ELI5

가게에 전화했는데 안 되는 이유가 여러 가지예요.

  • "지금 손님이 너무 많아요" → 조금 있다 다시 걸면 돼요 (500·529).
  • "오늘 주문 한도를 넘었어요" → 다시 걸어도 소용없을 때가 있어요 (429).
  • "주문서가 잘못 적혔어요" → 주문서를 고쳐야 해요 (400대).
  • 전화마다 붙는 접수 번호를 적어 두면, 나중에 가게에 물어볼 수 있어요 (request-id).

개념 설명

원리

오류는 "누구 문제인가"를 알려 줌

  • 5xx(500·529·504) = Anthropic 쪽 또는 요청 처리 쪽의 일시 문제 → 같은 요청을 잠시 뒤 다시 보내면 대개 풀림. 그래서 지수 백오프 재시도.
  • 429 = 내 조직의 한도 → 기다리면 풀리는 것(rate limit — 속도 제한, retry-after 있음)과 안 풀리는 것(티어 월 지출 상한, retry-after 없음)이 섞여 있음 → ■ rate limit 으로 가름.
  • 400대 = 내 요청 자체가 틀림 → 몇 번을 다시 보내도 같은 결과. 요청·키·권한을 고침.
  • 504 = 요청이 너무 오래 걸림 → 재시도보다 요청 방식을 바꿈(스트리밍·배치).

오류가 아닌 실패가 있음

  • 거절은 HTTP 200 + stop_reason: "refusal". 오류율 감시에 안 보임.
  • 스트리밍은 200 을 먼저 보낸 뒤 중간에 error 이벤트가 올 수 있음. HTTP 상태만 보면 놓침.

재시도는 이미 누가 하고 있음

  • 공식 SDK 는 일시 오류를 기본 2번 재시도. Claude Code 는 기본 10번 재시도하고, 포기한 뒤에야 api_error 를 1번 남김.
  • 그 위에 또 재시도를 감싸면 시도 수가 곱해져 한도·비용을 더 먹음(업계 일반).

추적 = request-id

  • 모든 응답에 붙음. 오류 본문에도 같은 값. 지원 문의·로그 대조의 열쇠.

핵심 질문 두 개

  • 이 실패는 기다리면 풀리나, 고쳐야 풀리나?
  • 내 감시가 이 실패를 볼 수 있나(200 인 실패 포함)?

함정

  • ≠"피크에 실패 급증 → 모델이 불안정하니 모델 교체" → 상태 코드부터. 5xx·529 는 일시 오류(백오프), 429 는 한도 — 모델 품질 문제가 아님 업계 일반 단 한도는 모델마다 따로라 다른 모델을 섞으면 429 는 덜 수 있음 ■ rate limit · 규칙 ④ ✓ 확인
  • ≠"429 면 즉시 무한 재시도" → retry-after 보다 이르면 또 실패 · 지출 상한 429 는 계속 실패 ✓ 확인
  • ≠"500 이 계속돼도 재시도만" → 계속되면 request ID 로 문의 ✓ 확인
  • ≠"504 면 타임아웃 값만 늘림" → 긴 요청은 스트리밍 ✓ 확인
  • ≠"오류율 대시보드가 조용하니 정상" → 거절은 200 · 스트림 중간 오류는 200 뒤 ✓ 확인
  • ≠"오류 메시지 문자열로 분기" → SDK 타입 예외, 구체적인 것부터 ✓ 확인
  • ≠"Claude Code api_error 1건 = 한 번 실패" → 재시도를 다 한 뒤 1번, 횟수는 attempt ✓ 확인

  • ≠"400 이니 한도는 아님" → 내가 건 지출 한도 도달도 400 ✓ 확인

뒤집히는 때

1. 모델을 바꾸는 게 맞는 때

  • 조건 : 오류가 한 모델의 429 에 몰려 있음, 또는 200 인데 refusal 로 빈 답.
  • 판단 : "모델 교체 = 엉뚱한 계층"은 5xx·529 일 때 이야기. rate limit 은 모델마다 따로라 다른 모델을 섞으면 그 모델의 한도까지 더 씀(■ rate limit · 규칙 ④). 거절은 같은 모델에 다시 보내면 대개 또 거절 → 다른 모델로(■ stop_reason 으로 분기 · 규칙 ③).
  • 등급 : ✓ 확인
  • 근거 : rate-limits 카드 ④ · stop-reason 카드 ③
  • 그래도 첫 수는 상태 코드·stop_reason 확인 — 그걸 안 보고 "불안정하니 교체"는 오답 쪽.

2. 재시도를 겹쳐 감쌌을 때

  • 조건 : 앱이 SDK 호출을 자체 재시도 4번으로 감쌈. SDK 는 기본 2번 재시도.
  • 계산 : 앱 1회 호출 = SDK 가 최대 3번 시도(1 + 2). 앱이 최대 5번 호출(1 + 4) → 요청 하나가 최대 15번 API 를 두드림.
  • 판단 : 과부하·rate limit 상황에서 시도가 곱해지면 회복을 늦춤. SDK 의 max_retries 를 조정하거나 겹친 재시도를 걷어 냄.
  • 등급 : 계산 (SDK 기본 2번은 확인 · "회복을 늦춤"은 업계 일반)
  • 근거 : errors en 17줄

3. Claude Code 의 api_error 1건

  • 조건 : 텔레메트리에 claude_code.api_error 가 1건, attempt = 11.
  • 판단 : 1번 실패가 아니라 일시 오류로 11번(첫 시도 + 기본 10번 재시도) 다 해 보고 포기한 것. attempt 가 1~2 처럼 작으면 400 같은 재시도 안 되는 오류이거나 자체 재시도 예산이 작은 원인(예 AWS·Google Cloud 자격증명 로드 실패는 최대 2번).
  • 회복 여부 : 같은 session.id 에서 그 오류 뒤에 api_request 가 이어지나로 봄.
  • 등급 : ✓ 확인
  • 근거 : monitoring-usage en 1663줄

4. 429 인데 기다려도 안 풀리는 때

  • 조건 : 월 중순부터 모든 요청이 429, 헤더에 retry-after 가 없음.
  • 판단 : rate limit 이 아니라 티어 월 지출 상한. error.details.error_code = enforced_spend_limit_reached. SDK 재시도도 계속 실패 → 상향 요청.
  • 등급 : ✓ 확인
  • 근거 : errors en 12줄 · rate-limits en 33·48줄

미해결

  1. 목록 7.3③ 의 "529 overloaded = 일시 과부하" 뒤 처방 : errors 문서의 529 줄엔 처방 문장이 없음. "백오프 재시도"는 SDK 가 5xx 를 재시도한다는 17줄과 ■ rate limit 카드에서 가져옴.
  2. 가속 한도(acceleration limits) : 2025-08-11 릴리스 노트에만 있고 지금 rate-limits 문서엔 이 단어가 없음(검색어 acceleration). 지금 문서의 가까운 문장 = "Short bursts of requests can exceed the limit"(■ rate limit).
  3. 408·409 를 SDK 가 자동 재시도하는지 : errors 문서는 "such as connection errors, rate limits, and 5xx" 예시만. 409 는 "충돌을 풀고 재시도"만 확인.
  4. 목록의 영어 신호 두 개(500 줄 · 지출 상한 429 줄)는 원문에서 찾음 — 목록 그대로 ✓. 목록의 "Claude Code 감시도 api_error 가 아니라 api_refusal" 도 monitoring-usage en 1096줄에서 ✓.

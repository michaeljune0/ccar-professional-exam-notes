카드

같은 결정도 듣는 사람마다 순서·깊이를 바꿔 말함 — 결정은 같고 내용이 바뀜. 비기술 결정자에게는 요청하는 결정 → 그들이 이미 보는 지표로 나타낸 효과 → 남은 위험과 각 통제 → 근거 순, 기술 세부는 부록 업계 일반 공식 문서에 브리핑 규칙 없음

공식 근거는 목표 문구 수준 : 가이드 = 여러 부서 이해관계자(stakeholder)와 일하며 아키텍처 결정을 잘 전함 · 보안·법무·경영진 논의까지 이끎 ✓ 확인. 선택지 표에 무엇을 넣나는 ■ trade-off 전달, 사업 지표 목록은 ■ impact metrics

비유 장애 보고. 경영진엔 "영향 고객 수 · 복구 시각 · 재발 방지 결정 요청" 한 장, 온콜엔 타임라인·원인·복구 명령, 보안팀엔 어떤 데이터가 어디로 나갔나. 같은 장애, 세 문서. "포스트모템 40쪽을 전부에게 전달" 이 속이는 습관

아키텍트가 고객지원 Agent 의 환불 초안 자동화를 임원 위원회 10분 안건비기술 결정자으로 올린다. 위원회가 정할 것은 전 상담팀으로 넓힐지 하나요청할 결정다. 준비한 자료는 임베딩 비교표 · 시퀀스 다이어그램 · 프롬프트 시연 순서기술 세부 먼저이고, 팀은 "꼼꼼해 보이게 다 보여 주자"고 한다. 자료를 어떻게 고칠까?

흐름

규칙 원문 ①②③④⑤ (갈림길로 그린 규칙)
  1. ①

    비기술 결정자 (스폰서·임원 위원회, 10~15분) : 요청하는 결정 → 그들이 이미 보는 지표로 나타낸 효과(처리 시간 · 밀린 문의 · 잘못 나간 환불) → 남은 위험과 각 통제 → 근거 업계 일반 [6.2①]

    기술 세부(검색 방식 비교 · 프롬프트 시연 · 벤치마크 · 구성 요소·시퀀스 다이어그램 · SDK 목록)는 부록 업계 일반

    가장 가까운 공식 원칙 : 요약을 세부 앞에 — 리뷰 요약은 건수 한 줄로 열고, 사실 오류가 없으면 그 말부터. 세부보다 일의 모양을 먼저 알고 싶어 함 ✓ 확인 (Claude Code 리뷰 요약 문맥 — 사람 브리핑으로 넓힌 건 해석)

    정보 양 : 너무 적으면 제대로 가는지 판단 못 하고, 너무 많으면 관련 없는 세부에 묻힘 ✓ 확인 (에이전트 계획 공개 문맥 — 넓힌 건 해석) → ■ 과정 투명성

    통제가 뒷받침 못 하는 안심 문구("사인오프로 위험 제거") 금지 업계 일반 · 가장 앞선 모델도 때때로 틀림 ✓ 확인 → ◆ 100% 약속 vs 측정된 SLO + 사람 안전망

  2. ②

    청중이 바뀌면 내용이 바뀜, 결정은 같음 업계 일반 [6.2①] [6.4]

    청중줄 것부록으로
    스폰서·위원회요청하는 결정 · 그들의 지표로 나타낸 효과 · 위험 + 통제 · 비용구성 요소 그림 · 시스템 프롬프트 원문
    on-call 엔지니어의존성 · 신호 · 실패 유형 · 복구 단계사업 효과
    보안·감사 검토데이터·자격증명이 경계를 넘는 길 그림 · 통제 증거없음 — 이 청중엔 기술 세부가 답
    위험 위원회결정 흐름 · 가드레일 · eval 결과시스템 프롬프트 원문

    가이드는 보안·법무·경영진 논의를 이 역할의 일로 적음 ✓ 확인 — 청중별 내용은 업계 일반 · 운영 세부는 ■ 구현 가이드

    두 청중에게 같은 자료 한 벌(ADR + 다이어그램) = 오답 업계 일반

  3. ③

    "숫자 하나만" 요구 : 하나를 주되 조각별(문의 종류별) + 재는 법 + 사람 검토 뒤 끝-끝(end-to-end) 결과 + 이 숫자가 못 말하는 것을 붙임 업계 일반 [6.2①] [4.1]

    공식 : 대부분 여러 성공 기준(success criteria)으로 다차원 평가 ✓ 확인 · 오류의 무게도 기준("오류의 90% 는 불편 수준") ✓ 확인 → ■ 성공 기준 · 사업 쪽 숫자는 사업 영향 지표로 ✓ 확인 → ■ impact metrics

    최고치 · 가중 평균 하나 · 공개 벤치마크 · "요약 불가" 는 아님 업계 일반

    "가끔 틀린다" 는 불만 → 문의 종류별 오류율 + 어떤 오류가 사업에 닿았나로 옮김 업계 일반

    상대가 윗선을 다시 설득해야 하면 한계를 먼저 말해 그 근거를 쥐여 줌 업계 일반

    eval 은 제품팀과 연구팀 사이 가장 넓은 소통 창구 ✓ 확인 → 숫자는 같은 과제 묶음에서 (해석 — ■ trade-off 전달 · 규칙 ①)

  4. ④

    반론 3종 : 할 수 있나(능력 → 시연) · 믿고 통제·증명할 수 있나(governance(관리·통제 체계) → 통제·증거) · 왜 이 안인가(설계 선택 → 고른 trade-off(절충) + 대안이 냈을 비용). 각각의 말로 답함 업계 일반 과정 고유 틀, 공식 문서에 없음 [6.2①]

    믿음 쪽 반론엔 남은 위험마다 통제와 증거 업계 일반

    거절도 같은 틀 : 한 줄 "안 됨" 대신 경계 · 결정 소유자 · 규정 안에서 되는 대안(승인된 경계 · 마스킹 · 좁힌 범위) 업계 일반 · 안전 요건은 선택지가 아니라 경계 → ■ trade-off 전달 · 규칙 ③

  5. ⑤

    데모 : 상대의 다음 결정 · 상대의 워크플로·데이터(또는 충실한 대체물)에 맞추고, 한계 1~2개를 의도된 범위로 먼저 말함. 기능 총람 · 광택 · 무결점 시연은 믿음을 못 만듦 업계 일반 [6.2①] [6.3]

    가까운 공식 원칙 : 자동 eval 도 실제 사용 모양과 안 맞으면 거짓 자신감을 줌 ✓ 확인 (eval 문맥 — 데모로 넓힌 건 해석)

함정

  • ≠임원 안건을 검색 방식 비교 · 프롬프트 시연부터 → 요청하는 결정 먼저, 세부는 부록 업계 일반
  • ≠"꼼꼼해 보이게 다 보여 주자" → 너무 많으면 관련 없는 세부에 묻힘 ✓ 확인 (넓힌 건 해석)
  • ≠"위원회와 보안팀에 같은 ADR + 다이어그램" → 청중마다 내용 업계 일반
  • ≠반대 함정 : "보안 검토에도 요약 한 장만" → 이 청중엔 경계 그림 · 기술 세부가 답 업계 일반

ELI5

같은 소풍 계획을, 교장 선생님께는 "허락해 주세요 + 안전 대책" 으로, 버스 기사님께는 "길과 시간" 으로 말하는 거예요.

  • 소풍은 하나인데, 듣는 사람마다 궁금한 게 달라요.
  • 교장 선생님께 버스 노선도부터 보여 주면 "그래서 뭘 허락하라고?" 가 돼요.
  • 버스 기사님께 "재밌을 거예요" 만 말하면 길을 못 찾아요.
  • "비 오면 어떡하지" 는 숨기지 말고 먼저 말해야 믿어 줘요.

원리

결정은 같고 내용이 바뀜

  • 청중마다 다른 결정을 말하는 게 아님. 같은 결정을, 그 사람이 내릴 판단에 필요한 것만 골라 그 사람의 말로 (업계 일반).
  • 비기술 결정자가 내릴 판단 = 승인할까. 필요한 것 = 무엇을 승인하나 · 무엇이 좋아지나(그들이 이미 보는 숫자로) · 무엇이 남는 위험이고 누가 막나.
  • 보안 검토가 내릴 판단 = 경계를 넘는 데이터가 안전한가. 필요한 것 = 경계 그림 · 통제 증거 → 이 청중엔 기술 세부가 곧 요약.

요약을 세부 앞에

  • 가장 가까운 공식 원칙 : 코드 리뷰 요약도 건수 한 줄로 열고 "사실 오류 없음" 부터 — 읽는 사람은 세부보다 일의 모양을 먼저 알고 싶어 함 (Claude Code 리뷰 문맥).
  • 정보 양 원칙 : 너무 적으면 판단을 못 하고, 너무 많으면 관련 없는 세부에 묻힘 (에이전트 계획 공개 문맥).

숫자 하나(평균)는 조각의 낮은 값을 숨김

  • 공식 : 대부분 여러 성공 기준으로 다차원 평가, 오류의 무게도 기준. 한 숫자로 줄이면 돈이 나가는 조각의 낮은 값이 평균에 묻힘 → 뒤집히는 때 3.

믿음은 한계를 먼저 말할 때 생김

  • 무결점 데모·안심 문구는 첫 오류 한 번에 신뢰를 다 잃음. 한계를 의도된 범위로 먼저 말하면, 상대가 윗선을 설득할 근거가 됨 (업계 일반).
  • 공식 가까운 원칙 : 자동 eval 도 실제 사용 모양과 안 맞으면 거짓 자신감을 줌.

뒤집히는 때

1. 보안 사인오프에는 기술 세부가 요약이다

  • 조건 : 청중이 보안 검토팀, 판단 = "카드번호·주문 정보가 경계를 넘어도 되나".
  • 판단 : "세부는 부록" 을 그대로 쓰면 오답. 이 청중이 판단할 대상이 바로 경계 그림·통제라 그것이 본문. 반대로 사업 효과(처리 시간)는 부록.
  • 등급 : 업계 일반

2. 기술 검토 위원회는 비기술 결정자가 아니다

  • 조건 : "위원회" 라도 CTO·아키텍처 검토 위원회 — 판단 = 설계가 맞나.
  • 판단 : 검색 방식 비교 · 시퀀스 다이어그램이 본문으로 올라옴. "위원회 = 요약 한 장" 으로 외우면 틀림. 청중 이름이 아니라 그 청중이 내릴 판단으로 가름.
  • 등급 : 업계 일반

3. 평균 94% 가 숨기는 81%

  • 조건 : 위원회가 "정확도 숫자 하나만" 요구. 문의 비중과 조각별 정확도 = 배송 70% · 97% / 반품 20% · 90% / 환불 10% · 81%.
  • 계산 : 가중 평균 = 0.7 × 97 + 0.2 × 90 + 0.1 × 81 = 67.9 + 18.0 + 8.1 = 94.0%. 돈이 나가는 환불 조각은 81% — 다섯 건 중 약 한 건이 틀림.
  • 전제 : 비중·정확도는 예시 · 사람 검토 전 값.
  • 등급 : 계산 (다차원 평가 원칙은 확인)
  • 근거 : define-success en-full 96·102줄
  • 판단 : 94% 한 줄만 주면 위원회는 환불까지 넓혀도 된다고 읽음. "94% (환불 81%, 5만 원 넘는 환불은 사람 확인 뒤 끝-끝 결과 따로)" 처럼 한 숫자 + 조각 + 못 말하는 것.

4. 한계를 먼저 말하는 게 불리해 보일 때

  • 조건 : 스폰서가 이사회에 다시 올려야 하고, 팀은 "승인받기 쉽게 한계는 빼자" 고 함.
  • 판단 : 한계를 빼면 이사회 질문에 스폰서가 답을 못 함 → 다음 승인에서 신뢰를 잃음. 한계 1~2개를 의도된 범위("환불은 초안까지, 확정은 사람")로 먼저 주는 것이 스폰서에게 근거를 쥐여 줌.
  • 등급 : 업계 일반

CCA-F

봄 (3.1 CLAUDE.md 4층 · "새 팀원만 규칙을 못 받는다" = 사용자 층에 적음 → 프로젝트 층으로 커밋) — 여기선 settings.json 범위·우선순위·신뢰 대기·관리형 강제까지 넓혀, 여러 명 팀과 조직 정책을 어디에 싣나를 운영 설계로 묻는다

함정

  • ≠"각자 개인 메모리(~/.claude/CLAUDE.md)·프롬프트에 팀 규칙 추가" → 내 기계에만 있음. 팀 = 프로젝트 파일 커밋 ✓ 확인
  • ≠"더 큰 모델이면 팀 규칙을 알아서 지킨다" → 모델은 안 실린 규칙을 모름. 어디에 적었나의 문제 업계 일반
  • ≠"@import 로 쪼개면 컨텍스트가 준다" → 시작할 때 다 로드 ✓ 확인
  • ≠"사용자 설정이 프로젝트 설정을 이긴다" → 반대. 공유 프로젝트 > 사용자 ✓ 확인
  • ≠"--settings 로 관리형 값을 덮는다" → 관리형은 명령줄로도 못 덮음 ✓ 확인
  • ≠"조직 보안 규칙을 관리형 CLAUDE.md 에만 적음" → 행동 지침일 뿐. 막으려면 관리형 settings permissions.deny ✓ 확인
  • ≠"팀 .claude/settings.json 에 defaultMode: bypassPermissions 커밋" → 저장소 파일에선 안 먹음 ✓ 확인
  • ≠"위키·README 에 적어 두면 다 본다" → Claude 가 읽는 파일이 아님 업계 일반

ELI5

공지를 어디에 붙이느냐가 누가 보느냐를 정해요.

  • 내 수첩에 적으면 나만 봐요.
  • 팀 게시판에 붙이면 팀 모두가 봐요.
  • 회사 정문 규정은 아무도 떼지 못해요.
  • 같은 칸에 두 공지가 부딪히면 윗선 공지가 이겨요.

원리

파일 위치 = 적용 대상

  • 설정·지시는 내용이 아니라 어느 파일에 있나로 누구에게 먹는지가 정해짐.
  • 팀에 가는 통로는 저장소 하나 → 커밋한 프로젝트 파일만 클론한 사람에게 감. 사용자 파일(~/.claude/…)은 내 기계 밖으로 안 나감.
  • 조직은 저장소 밖에서 관리형(managed)으로 내려보냄 → 개인·프로젝트 파일이 못 덮음.

두 시스템, 합치는 법이 다름

  • settings.json : 같은 키면 높은 층 하나가 이김(관리형 > 명령줄 > 로컬 > 공유 프로젝트 > 사용자). 목록 키는 층마다 합침.
  • CLAUDE.md : 이기고 지는 게 없음. 다 이어 붙여 모델에게 보여 줌 → 충돌하면 모델이 아무거나 고를 수 있음. 그리고 애초에 강제가 아님(◆ CLAUDE.md(지시) vs 훅(강제)).

커밋해도 바로 안 먹는 까닭

  • 능력을 주는 키(permissions.allow·additionalDirectories·대부분 env)는 남이 커밋한 파일이 내 기계에 권한을 여는 것이라, 팀원마다 폴더를 신뢰해야 켜짐.
  • 제한만 하는 키(deny·ask)는 위험이 없어 바로 먹음.
  • 일부 키는 저장소 파일에선 아예 무시(예 defaultMode 의 auto·bypassPermissions) — 저장소가 내 세션의 안전장치를 끄지 못하게.

  • 이 규칙을 누가 받아야 하나 — 나, 팀, 조직?
  • 받는 사람이 끌 수 있어도 되나?

뒤집히는 때

1. 개인 값이 팀 값을 이기는 때

  • 조건 : 팀 .claude/settings.json 이 model 을 정했는데 나만 다른 모델을 쓰고 싶음.
  • 판단 : 로컬(.claude/settings.local.json)이 공유 프로젝트보다 위 → 로컬에 적으면 내 세션만 바뀜. "팀 파일이 항상 이긴다"는 사용자 파일 기준일 때만 맞음.
  • 단 권한 규칙은 안 뒤집힘 : 로컬 allow 는 프로젝트 ask 를 못 이기고, 어느 층이든 deny 가 이김.
  • 등급 : ✓ 확인
  • 근거 : settings en 226·417·513줄 · permissions en 790줄

2. 커밋했는데 새로 온 팀원에게 안 먹는 때

  • 조건 : 개발자 12명이 쓰는 저장소에 permissions.allow 를 커밋. 어제 클론한 3명은 계속 확인창을 받음.
  • 판단 : 설정이 틀린 게 아니라 신뢰 대기. 그 3명이 폴더를 신뢰하면 적용. 같은 파일의 deny 는 이미 먹고 있음.
  • 같은 부류 : 커밋한 enableAllProjectMcpServers 도 미신뢰 폴더에선 무시 → ■ 에이전트 권한 · 규칙 ⑥.
  • 등급 : ✓ 확인
  • 근거 : settings en 503줄 · permissions en 800줄 · mcp en 496줄

3. 클라우드 세션에서 개인 설정이 사라지는 때

  • 조건 : 권한 규칙을 ~/.claude/settings.json 에만 두고 claude.ai/code 클라우드 세션을 띄움.
  • 판단 : 클라우드 세션은 새 클론에서 돌아 사용자·로컬 파일을 안 읽음. 관리형도 기기에 깐 파일·MDM 은 안 닿고 server-managed 만 닿음 → 팀 규칙은 커밋, 조직 규칙은 server-managed.
  • 여러 저장소를 여는 클라우드 세션은 각 저장소의 .claude/settings.json 에서 enabledPlugins·extraKnownMarketplaces 만 읽음(권한·훅 안 읽음).
  • 등급 : ✓ 확인
  • 근거 : settings en 548~551줄

4. 관리형인데 아래 층 값이 이기는 때

  • 조건 : 관리형이 disableClaudeAiConnectors: false, 프로젝트가 true.
  • 판단 : 보안 키 몇 개는 "더 엄격한 값"이 어느 층에서 와도 먹음 → true 가 이김. "관리형이 항상 이긴다"의 예외.
  • 등급 : ✓ 확인 (예외 키 목록은 자주 바뀜 — 조회일 확인)
  • 근거 : settings en 524~536줄

5. 사용자 CLAUDE.md 와 프로젝트 CLAUDE.md 가 부딪히는 때

  • 조건 : 내 ~/.claude/rules/ 는 "탭 들여쓰기", 프로젝트 규칙은 "공백 2칸".
  • 판단 : settings 처럼 높은 층이 이기는 게 아님. 프로젝트 규칙이 뒤에 실리지만 서로 못 덮음 → Claude 가 어느 쪽이든 따를 수 있음. 처방은 둘을 맞추기. 반드시 지켜야 하면 지시가 아니라 훅.
  • 등급 : ✓ 확인
  • 근거 : memory en 307·453줄

미해결

  1. 목록 7.1① "Part 24 Q7.1 함정 · 샘플 1 D 해설"의 "더 큰 모델이면 팀 규칙을 알아서" — 샘플 1 D 해설("model size (D) is unrelated to authorization scope")은 권한 범위 이야기라 팀 규칙 배포와는 다름. 공식 문장 없음 → 업계 일반으로 둠.
  2. 목록 "커밋하면 버전 관리·PR 리뷰를 탄다" — "source control"·"version control" 은 원문 확인(memory en 242·255줄), "PR 리뷰" 는 settings·memory 원문에서 못 찾음(파일 en-claude-code-settings.md·en-claude-code-memory.md, 검색어 review·pull request). 카드엔 안 넣음.
  3. 관리형 전달 방식(server-managed·MDM·파일)과 관리형 안의 우선순위는 managed-settings 문서 소관 — 이번에 받지 않음(settings 원문의 링크만 봄).

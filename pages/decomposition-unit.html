한눈에

복잡한 일을 "과제"로 쪼개기 = 설계·평가의 기본 단위라 먼저 함. 호출까지 나눌지는 따로 정함 ✓ 확인

공식 고객지원 예 : 대화를 과제 4개로 쪼개 과제마다 프롬프트 부분을 쓰고, 부분들을 하나의 문자열로 합쳐 한 프롬프트로 씀. 견적은 도구 하나로 계산 ✓ 확인

비유 헬스체크. 하나로 뭉치면 어디가 깨졌는지 안 보여서 구성요소별로 나눠 봄. 그렇다고 구성요소마다 서버를 따로 띄우진 않음

ELI5

숙제 공책 한 권에 과목별로 칸을 나눠 쓰는 것과, 과목마다 공책을 따로 사는 것의 차이예요.

  • 먼저 과목(할 일)을 다 적어 봐야 빠진 과목이 안 생겨요.
  • 대부분은 공책 한 권에 칸만 나눠도 충분해요.
  • 한 과목만 자꾸 틀리면, 그 과목 칸을 먼저 고쳐 봐요.
  • 칸으로 안 될 때만 공책을 따로 사요. 공책이 늘면 들고 다니기 무거워요.

개념 설명

원리

과제 쪼개기 = 설계·평가 단위

  • 고객지원 대화 한 번 안에는 질문 답변 · 정보 찾기 · 요청 처리 같은 서로 다른 과제가 묶여 있음.
  • 만들기 전에 이상적인 대화를 과제로 다 쪼갬 → 과제마다 프롬프트를 쓰고 평가할 수 있고, 테스트 케이스 범위가 보임.
  • 공식 예는 쪼갠 과제마다 프롬프트 부분을 따로 쓴 뒤 하나의 문자열로 합쳐 한 프롬프트로 씀. 견적 계산은 도구 하나에 맡김. 즉 과제 decomposition(분해) ≠ 호출 decomposition.

호출 쪼개기 = 조건이 있을 때만

  • 고려할 점이 여럿이면 점마다 따로 호출해 각 측면에 집중하게 함 (나눠 돌리기).
  • 가드레일 : 답하는 인스턴스와 검사하는 인스턴스를 나누면 한 호출이 둘 다 할 때보다 나음.
  • 긴 프롬프트에서 일부 제약을 계속 무시하면 "생성 → 고치기" 2단계로 (Skilljar).
  • 중간 출력을 검사하거나 파이프라인 구조를 강제해야 하면 명시적 체이닝.
  • 그 밖의 다단계 추론(reasoning)은 최신 모델이 adaptive thinking·서브에이전트로 한 요청 안에서 대부분 처리.

나누는 대가

  • 체이닝은 지연(latency)을 내주고 정확도를 얻는 거래. 의도 분류기는 Claude 호출 1번 더 → 지연 ↑.
  • 여러 프롬프트로 나눈 대화 흐름이면 지연 최적화 쪽 모델도 검토하라는 공식 문장이 있음.

층을 더하는 순서

  • 프롬프트 엔지니어링 → 도구 추가(프롬프트 체인 포함) → 과제가 아주 다양할 때만 의도 분류기 + 전문 대화.

핵심 질문 두 개

  • 지금 틀리는 게 어느 과제인지 보이나? (안 보이면 먼저 과제로 쪼개 평가)
  • 그 과제가 틀리는 이유가 "한 호출이 여러 걸 저울질해서"인가? (그렇다면 호출을 나눔)

  2. ②

    쪼갠 과제는 프롬프트 부분(하위 섹션)으로 한 번에 하나씩 씀 → 부분만 고치면 되니 디버깅 쉬움. 다 쓰면 하나의 문자열로 합쳐 한 프롬프트 ✓ 확인 [1.5②]

    여러 갈래가 같은 중간 산출물(장면 경계·항목 목록)을 똑같이 써야 함 → 그것을 먼저 한 단계로 만들고, 그 결과를 나눠 돌리기 갈래마다 같게 넘김. "도착하자마자 전부 병렬" 은 갈래마다 경계가 달라짐 (공식 = 패턴은 섞어 씀 ✓ · 이 조합은 이 카드의 해석)

연습 문제

자동차 보험 고객지원 Agent 의 한 프롬프트에 규칙이 30줄 있다. 답장이 "환불·보상을 약속하지 마라" 같은 몇몇 제약을 계속 어긴다일부 제약 무시. 팀장은 "그 규칙을 더 길고 강하게 다시 써서 한 호출로 해결하자"고 한다. 무엇을 할까?

시험 대비

함정

  • ≠"한 프롬프트에 몰아넣었더니 견적이 틀림 → 과제별 호출로" → 바로 호출을 나누지 않음. 과제별로 평가해 어디가 틀리는지 봄. 공식 예는 한 프롬프트 + 견적은 도구 하나로 계산 ✓ 확인
  • ≠"지시를 더 길고 강하게 써서 한 호출로" → 제약을 분명히 적어도 일부를 어김 → 고치기 단계를 따로 ✓ 확인 (Skilljar)
  • ≠"과제마다 에이전트 하나씩" → 역할별 decomposition(분해)은 말 전달 놀이(거쳐 갈수록 내용이 빠짐) → ◆ 단일 vs 멀티 에이전트 ✓ 확인
  • ≠"체이닝으로 나누면 더 빠르고 싸다" → 지연을 내주고 정확도를 얻음 ✓ 확인
  • ≠"단계가 여러 개면 무조건 체이닝" → 최신 모델은 대부분 한 요청 안에서 처리. 명시적 체이닝은 중간 검사·구조 강제일 때 ✓ 확인
  • ≠"처음부터 의도 분류기 + 전문 대화" → 층을 더하기 전에 프롬프트·도구부터. 분류기는 과제가 아주 다양할 때, 지연 ↑ ✓ 확인

신호

"For complex tasks with multiple considerations, LLMs generally perform better when each consideration is handled by a separate LLM call, allowing focused attention on each specific aspect."

"Explicit prompt chaining (breaking a task into sequential API calls) is still useful when you need to inspect intermediate outputs or enforce a specific pipeline structure."

"break down your ideal customer interaction into every task you want Claude to be able to perform. This ensures you can prompt and evaluate Claude for every task"

"Now combine all these sections into a single string to use as your prompt."

"Note, this method requires an additional call to Claude that can increase latency."

"Claude consistently ignores some constraints in long prompts" (Skilljar)

뒤집히는 때

1. 견적이 틀리는데 "호출 분리"가 답이 아닌 때

  • 조건 : 한 프롬프트 고객지원 Agent 에서 견적 금액만 자주 틀림.
  • 판단 : 공식 예는 견적을 LLM 이 계산하지 않고 get_quote 도구 하나가 계산함. 금액이 틀리면 먼저 계산을 도구로 옮기고, 과제별 평가(견적 정확도 목표 100%)로 확인. 호출을 과제별로 쪼개는 건 그다음.
  • 등급 : ✓ 확인
  • 근거 : customer-support-chat en 156·384·399~400줄 · ko 384줄

2. 나눠 놨더니 지연이 문제가 되는 때

  • 조건 : 인사 → 분류 → 답변 → 검사를 호출 4개로 나눔. 사용자는 채팅 창에서 기다림.
  • 판단 : 호출마다 지연이 붙음. 공식 문서는 여러 프롬프트로 된 대화 흐름이면 지연 최적화 쪽 모델(Haiku 4.5)을 검토하라고 함. 검사처럼 독립인 단계는 병렬로, 나머지는 한 프롬프트로 되돌리는 것도 선택지.
  • 등급 : ✓ 확인 (방향) · 업계 일반 (어느 단계를 되돌릴지)
  • 근거 : ko 190줄 · building-effective-agents en 61·99줄

3. 한 프롬프트로 두다가 체이닝이 필요해지는 때

  • 조건 : 환불 요청 처리에서 "환불 가능 판정" 결과를 사람이 확인한 뒤에 답장을 보내야 한다는 규정이 생김.
  • 판단 : 중간 출력 검사가 요구됨 → 명시적 체이닝(판정 호출 → 사람 확인 → 답장 호출). 모델이 내부에서 잘 처리하더라도 검사 지점을 만들려면 호출을 나눔.
  • 등급 : ✓ 확인
  • 근거 : prompting-best-practices en 404·406줄

4. 과제가 늘어 의도 분류기가 쓸 만한 때

  • 조건 : 보험 상담에 청구 접수 · 계약 변경 · 해지 방어가 추가돼 과제마다 도구 묶음과 규칙이 서로 충돌.
  • 판단 : 프롬프트·도구 추가로 버티다 과제가 "아주 다양"해지면 의도 분류기로 전문 대화(각자 도구·시스템 프롬프트)에 보냄. 호출 1번 더 = 지연 ↑ 을 감수할 만큼 충돌이 클 때.
  • 등급 : ✓ 확인 (조건·대가) · 업계 일반 ("충돌"을 기준으로 삼는 부분)
  • 근거 : en 1187~1192줄

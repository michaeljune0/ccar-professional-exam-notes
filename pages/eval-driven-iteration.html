  • 4.3③ 프롬프트 한 줄·모델 버전을 바꿨다 — 무엇을 다시 돌리나? — 반복 개선 루프 (변경 = 시스템 변경, eval 통과 뒤 배포)
  • 4.4① 문서 갱신 뒤 자신 있게 틀린다 — 모델·지연은 그대로 — 어느 계층부터 조사하나 (첫 질문 = 증상 직전에 무엇이 바뀌었나)
  • 4.5② 보기마다 다른 최적화 — 이 시나리오의 레버는 무엇 하나? — 시나리오 단서 → 레버 하나 (캐싱 · 배치 · 라우팅/effort · 스트리밍)

한눈에

프롬프트 한 줄·도구·effort·모델 버전도 시스템 변경. 바꿀 때마다 같은 eval 을 다시 돌려 기준선과 비교하고, 통과한 것만 배포 = 품질 문제의 첫 방어선 ✓ 확인

eval 이 없으면 불만을 기다리는 사후 대응 : 불만 대기 → 손으로 재현 → 고침 → 다른 데가 안 깨졌길 바람 ✓ 확인

비유 GitOps. 설정 한 줄도 PR → CI 테스트 → 통과해야 배포. 핫픽스라고 파이프라인을 건너뛰지 않음

ELI5

빵집에서 반죽 비법을 조금 바꿀 때마다 시식단에게 다시 먹여 보는 거예요.

  • 소금 한 꼬집만 바꿔도 맛이 달라질 수 있어요.
  • 사장님 혼자 한 입 먹어 보고 "괜찮네" 하면 손님이 먼저 실망해요.
  • 밀가루 회사를 바꾸면 맛뿐 아니라 빵 한 개 값도 다시 따져야 해요.
  • 이 쪽은 "무엇을 바꾸면 무엇을 다시 재나"를 모아 둔 곳이에요.

개념 설명

원리

변경 = 시스템 변경

  • 프롬프트 한 줄 · 도구 정의 · 하네스 · effort · 모델 버전 — 어느 것을 바꿔도 에이전트 동작이 바뀜.
  • 그래서 바꿀 때마다 같은 과제 은행(static bank of tasks)으로 다시 돌려 기준선과 비교. 통과한 것만 배포. 이게 품질 문제의 첫 방어선(CI/CD).
  • eval 이 없으면 사후 대응 : 불만을 기다리고 → 손으로 재현하고 → 고치고 → 다른 데가 안 깨졌길 바람. 진짜 regression(회귀)과 잡음을 못 가름.

루프 (공식 흐름도 · Skilljar)

  • 과제 셋 → 첫 프롬프트 → 돌리고 채점 → 기준선 점수 → 프롬프트를 바꿔 같은 셋으로 다시 → 점수로 비교, 제일 나은 판을 씀.
  • 한 번 · 몇 번 해 보고 "됐다"는 흔한 함정 — 실사용자는 예상 못 한 입력을 넣음.

eval 먼저 (eval-driven development)

  • 만들 기능의 eval 을 먼저 정의하고, 통과할 때까지 반복.
  • 아직 에이전트가 못 하는 기능도 capability(능력) eval 로 먼저 만들어 둠 → 새 모델이 나오면 돌려서 미리 만든 eval 중 어느 것이 통과하는지(어느 예상이 맞았는지) 바로 봄.
  • eval 이 있는 팀은 새 모델 도입이 며칠, 없는 팀은 몇 주.

모델을 바꾸면 품질 + 비용·지연(latency) 기준선을 다시

  • eval 이 있으면 지연 · 토큰 사용량 · 과제당 비용 · 오류율 기준선이 덤으로 생김 → 모델 교체 전후를 같은 과제로 비교.
  • 비용이 달라지는 공식 이유 셋 : ① 새 토크나이저(Claude 4.7 이후, 같은 글에 토큰 약 30% 더) ② 모델별 최소 캐시 길이(바꾼 모델에서 조용히 캐싱이 꺼질 수 있음) ③ 모델별 기본 effort·thinking(사고) 동작(Opus 5.5 는 기본 medium, thinking 을 끌 수 없음 — 시험 뒤 변경).
  • 공식 업그레이드 절차 : 내 사용 사례 벤치마크(가장 중요) → 실제 프롬프트·데이터 → 정확성·품질·엣지 케이스 비교 → 성능·비용 저울질.

도구보다 과제

  • Harbor · Braintrust · LangSmith · Langfuse · Arize 는 예시일 뿐. 프레임워크는 돌리는 과제만큼만 좋음 → 빨리 하나 고르고 과제·grader(채점기)에 힘을 씀.

핵심 질문 두 개

  • 이번에 바꾼 것이 무엇이고, 같은 과제로 전후를 비교했나?
  • 품질만 봤나, 비용·지연 기준선도 다시 쟀나?

연습 문제

고객지원 Agent 를 Opus 4.6 에서 Opus 4.7 로모델 버전 올린다. 단가표는 입력·출력 모두 그대로단가 같음라서 팀장은 비용 걱정은 없으니 품질 eval 만 다시 보자고 한다. 무엇을 다시 재야 할까?

시험 대비

함정

  • ≠"데모에서 잘 됐으니 바로 배포" → 한 번·몇 번 테스트는 흔한 함정. eval 파이프라인으로 점수 ✓ 확인 (Skilljar)
  • ≠"프롬프트 한 줄·핫픽스는 eval 건너뜀" → 변경마다 자동 eval → 통과한 것만 배포 ✓ 확인
  • ≠"단가가 같으니 모델 올려도 비용 그대로" → 새 토크나이저 = 같은 글에 토큰 약 30% 더 ✓ 확인
  • ≠"모델을 바꾸면 캐시가 무효라서 비용이 올랐다"를 근거로 드는 보기 → 근거로 약함(prompt-caching 문서에 이 문장 없음). 공식 근거 = 새 토크나이저 · 모델별 최소 캐시 길이 ✓ 확인
  • ≠"Promptfoo 같은 특정 도구 이름"으로 고르는 보기 → 공식 글 예시에 없음. 도구보다 과제 ✓ 확인
  • ≠"eval 은 기능이 된 다음에 만든다" → 권장은 eval 먼저(eval-driven development) ✓ 확인
  • ≠"새 모델이 나오면 몇 주 손으로 테스트" → eval 이 있으면 며칠 ✓ 확인
  • ≠"eval 없이 불만이 오면 고친다" → 불만을 기다리는 사후 대응 ✓ 확인

신호

"Automated evals are especially useful pre-launch and in CI/CD, running on each agent change and model upgrade as the first line of defense against quality problems."

"Absent evals, debugging is reactive: wait for complaints, reproduce manually, fix the bug, and hope nothing else regressed."

"We recommend practicing eval-driven development: build evals to define planned capabilities before agents can fulfill them, then iterate until the agent performs well."

"Once evals exist, you get baselines and regression tests for free: latency, token usage, cost per task, and error rates can be tracked on a static bank of tasks."

"teams without evals face weeks of testing while competitors with evals can quickly determine the model’s strengths, tune their prompts, and upgrade in days."

"This tokenizer produces approximately 30% more tokens for the same text."

뒤집히는 때

1. 단가가 싼 새 모델로 옮겼는데 per-request cost 가 오르는 때

  • 조건 : Sonnet 4.6 → Sonnet 5. 요청 = 입력 6,000 · 출력 800 토큰(옛 토크나이저 기준).
  • 계산 : Sonnet 4.6 = 6,000 × $3 + 800 × $15 (백만 토큰당) = $0.018 + $0.012 = $0.030. Sonnet 5 = 같은 글이 7,800 · 1,040 토큰 → $0.0156 + $0.0104 = $0.026 (약 13% 쌈). 그런데 Sonnet 5 는 adaptive thinking 이 기본 켜짐 → thinking 이 출력 1,500 토큰을 더 쓰면 +$0.015 → $0.041 (약 37% 비쌈).
  • 전제 : 캐싱 없음 · thinking 토큰이 출력 단가로 과금된다고 봄(추론 — 받아 둔 파일에서 과금 문장은 못 찾음, 미해결 4) · 1,500 은 가정값 · 가격 = 2026-09-28 조회값.
  • 판단 : 단가표만 보고 "싸다"고 하지 않음. 같은 과제 은행으로 토큰·비용 기준선을 다시 잰 뒤 effort 로 조정.
  • 등급 : 계산 (단가 · 30% · adaptive thinking 기본 켜짐은 확인)
  • 근거 : pricing ko 9·15줄 · 릴리스 노트 en 168줄 "adaptive thinking is now on by default" · effort ko 47줄(max_tokens = 사고 + 응답 합)

2. 더 싼 모델로 내렸더니 앞부분 캐싱이 꺼지는 때

  • 조건 : 시스템 프롬프트 3,000 토큰(Sonnet 5 기준)을 매 요청 재사용, 캐시 적중. Haiku 4.5 로 내림.
  • 계산 : Sonnet 5 최소 캐시 1,024 → 캐싱됨. 앞부분 비용 = 3,000 × $0.20 = $0.0006. Haiku 4.5 는 옛 토크나이저라 같은 글 ≈ 3,000 ÷ 1.3 ≈ 2,300 토큰 < 최소 4,096 → 캐싱 안 됨, 오류도 없음. 앞부분 비용 = 2,300 × $1 = $0.0023 → 단가가 싼 모델인데 앞부분은 약 3.8배 비쌈.
  • 전제 : 뒤 부분(바뀌는 입력·출력)은 뺌 · 적중률 100% 로 봄 · 가격 = 2026-09-28 조회값.
  • 판단 : 모델 교체 뒤 cache_creation_input_tokens·cache_read_input_tokens 가 둘 다 0 이면 최소 길이부터(■ 프롬프트 캐싱). 비용 기준선은 캐싱 포함으로 다시 측정.
  • 등급 : 계산 (최소 길이·단가는 확인)
  • 근거 : prompt-caching ko 182·183·188줄 · en 39줄 표(Sonnet 5 읽기 $0.20 · Haiku 4.5 입력 $1) · pricing ko 15줄

3. 아주 초기 프로토타입 — eval 없이도 되는 것 같은 때

  • 조건 : 사내 시연용 첫 주, 수동 테스트·도그푸딩으로 빠르게 고치는 중.
  • 판단 : 공식도 초기엔 수동 테스트·직관으로도 한동안은 된다고 인정. 하지만 운영·규모로 가면 eval 없이는 무너지고, 늦을수록 eval 만들기가 어려움 → 실제 실패에서 뽑은 20~50개로 일찍 시작(■ 첫 eval 셋 만들기).
  • 등급 : ✓ 확인
  • 근거 : en 38·221줄

4. 새 모델이 기본값을 바꾼 때 (시험 뒤 변경)

  • 조건 : Opus 5 → Opus 5.5. effort 를 안 적은 요청.
  • 판단 : Opus 5.5 는 기본 effort 가 medium(Opus 5 = high) → 같은 요청이 한 단계 낮게 돎. thinking 을 끌 수 없음. 이전 모델 설정을 그대로 쓰지 말고 자체 eval 에서 effort 스윕.
  • 등급 : ✓ 확인 · 시험 뒤 변경 (2026-09-22 출시 — 시험은 이 모델을 모를 수 있음)
  • 근거 : effort ko 47줄 · en 47줄 · 릴리스 노트 en 15·16줄

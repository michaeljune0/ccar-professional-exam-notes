  • 6.5② 문서를 갱신한 뒤 확신에 찬 오답이 나온다 — "모델이 드리프트했다"? — 핸드오프 뒤 품질 저하의 원인 가리기 (고정 모델 ID vs 검색·색인·요구 변화)

한눈에

갑자기 나빠지면 첫 질문 = "증상 직전에 무엇이 바뀌었나". 그 변경이 일으킬 수 있는 계층부터 조사하고, 그 변경으론 안 생길 원인은 버림 ✓ 확인 (가이드 샘플 3)

모델 ID = 고정 스냅숏. 같은 ID 의 가중치·구성은 안 바뀌고, 새 버전은 새 ID 로 나옴 → "모델이 저절로 변함"은 첫 후보가 아님 ✓ 확인

비유 배포 직후 장애는 변경 이력(change log)부터. 데이터만 갱신했으면 같이 갱신되지 않은 인덱스를 의심하지, 인스턴스부터 키우지 않음

어제까지 잘 되던 장난감이 오늘 고장 났어요.

  • 제일 먼저 물어요. "어제랑 뭐가 달라졌지?"
  • 새 건전지를 넣었다면 건전지부터 봐요.
  • 장난감 속 기계는 몰래 바뀌지 않아요. 바뀌면 이름이 새로 붙어요.
  • 아무것도 안 바꿨는데 조금 달라졌다면, 가게에서 포장을 바꾼 걸 수 있어요.

개념 설명

원리

시스템은 층으로 나뉨

  • 문서·데이터 → indexing(색인) → 검색(retrieval) → 프롬프트 → 모델(ID) → 서빙 인프라. 그리고 이걸 재는 eval·grader(채점기).
  • 변경 하나가 깨뜨릴 수 있는 층은 정해져 있음. 문서 갱신은 indexing·검색을 흔들 수 있지만, 모델 가중치나 context window 를 바꾸진 못함.
  • 그래서 "무엇이 바뀌었나"가 조사 순서를 정함. 그 변경으론 안 생길 원인은 먼저 버림 (가이드 샘플 3 해설).

모델 ID 는 움직이지 않는 기준점

  • 4.6 이후 날짜 없는 ID 는 스냅숏 그 자체. 같은 ID 의 가중치·구성은 안 바뀌고, 새 버전은 새 ID 로 나옴.
  • 그래서 "모델이 저절로 변했다"는 첫 후보가 아님. 이 고정 덕분에 모델 층을 배제하고 나머지를 볼 수 있음.
  • 예외 둘 : ⓐ 4.6 이전 별칭(claude-sonnet-4-5 등)은 최신 날짜 스냅숏을 가리키는 포인터라 고정 보장 밖 ⓑ 가중치는 고정이어도 서빙 인프라(라우터·안전 분류기·샘플링 로직)는 바뀔 수 있고, 사소한 동작 차이를 낼 수 있음.

모델을 바꾼 경우엔 달라진 것 목록부터

  • 토크나이저 · effort 기본값 · 400 으로 막힌 기능(prefill · temperature). 증상과 목록을 짝지으면 대부분 여기서 걸림.

eval 도 바뀌는 층

  • 점수가 떨어졌을 때 에이전트가 틀린 건지, grader 가 맞는 답을 떨어뜨린 건지 transcript 를 읽어 가름.

연습 문제

고객지원 Agent 가 어젯밤 환불 규정 문서를 새로 올린 뒤문서 갱신부터 틀린 환불 기한을 자신 있게 답한다. 모델 ID 와 응답 시간은 그대로모델 그대로다. 한 팀원은 모델 가중치가 몰래 바뀐 것 같다고 한다. 어디부터 볼까?

시험 대비

함정

  • ≠"모델 가중치가 몰래 바뀜" (샘플 3 A) → 같은 ID 의 가중치는 고정, 새 버전은 새 ID ✓ 확인
  • ≠"temperature 가 너무 낮음" (C) · "context window 축소" (D) → 문서 갱신으로 생길 일이 아님 ✓ 확인
  • ≠"바뀐 게 없는데 이상하니 모델이 저절로 드리프트" → 같은 ID 면 서빙 인프라 업데이트가 가장 유력, 4.6 이전 별칭이면 별칭이 옮겨간 것 ✓ 확인
  • ≠"날짜 없는 ID = 늘 최신을 가리키는 별칭" → 4.6 이후는 날짜 없는 ID 가 스냅숏 그 자체 ✓ 확인
  • ≠Opus 5.5 로 옮긴 뒤 추론(reasoning)이 얕아짐 → "모델이 약함" 전에 effort 기본값(medium) ✓ 확인 시험 뒤 변경
  • ≠원인이 안 보이면 모델부터 키움 → 변경 이력부터 업계 일반

뒤집히는 때

1. "모델 안 바꿨다"가 틀린 때 — 4.6 이전 별칭

  • 조건 : 코드엔 claude-sonnet-4-5 처럼 날짜 없는 이름이 박혀 있음. 코드 변경 없음.
  • 판단 : 4.6 이전 모델의 날짜 없는 이름은 별칭이라 최신 날짜 스냅숏을 가리킴. 고정 보장은 모델 ID 에만 있고 별칭엔 없음 → 이 경우 "같은 ID"라는 전제가 깨짐.
  • 등급 : ✓ 확인 (별칭 성질) · 날짜 붙은 ID 로 고정하라는 처방은 업계 일반.
  • 근거 : model-ids-and-versions en 1·57·65줄

2. 문서 갱신 + 같은 주에 모델도 교체

  • 조건 : 두 변경이 겹침. 자신 있게 틀리는 답 + 토큰 수도 늘어남.
  • 판단 : 샘플 3 의 "모델 그대로" 단서가 없어져 검색만 단정 못 함. 변경을 하나씩 되돌려(또는 eval 로 따로 돌려) 가름.
  • 계산 예 : 요청당 입력 6,500 토큰(옛 토크나이저)이 4.7 이후 모델에선 약 8,450 토큰 (6,500 × 1.3). 토큰 증가는 토크나이저로 설명되지만, 틀린 답은 설명 못 함 → 틀린 답은 여전히 검색 쪽 후보.
  • 전제 : 30% 는 평균값, 실제 증가는 내용 따라 다름.
  • 등급 : 계산 (30% 는 확인) · 되돌려 가르기는 업계 일반
  • 근거 : pricing en 15줄 · 가이드 샘플 3

3. 모델을 바꿨는데 원인이 모델이 아닌 때 — effort 기본값

  • 조건 : Opus 5 → Opus 5.5 로 옮긴 뒤 어려운 문제에서 추론이 얕아짐. 요청에 effort 를 안 적음.
  • 판단 : Opus 5.5 기본값은 medium 이라 같은 요청이 한 단계 낮게 돎. "새 모델이 약하다" 전에 effort 를 올려 봄.
  • 등급 : ✓ 확인 · 시험 뒤 변경 (2026-09-22 출시)
  • 근거 : effort en 47줄 · 릴리스 노트 en 15줄

4. 아무것도 안 바꿨는데 크게 달라진 때

  • 조건 : 같은 날짜 없는 4.6 이후 ID, 코드·프롬프트 그대로인데 정확도가 눈에 띄게 떨어짐.
  • 판단 : 공식은 인프라 업데이트가 "사소한" 차이를 낼 수 있다고만 함. 큰 변화면 내 쪽에서 안 보이게 바뀐 것(들어오는 질문 종류 · 데이터 · 트래픽)을 먼저 다시 찾음.
  • 등급 : 업계 일반 (큰 변화에 대한 공식 문장 없음)
  • 근거 : model-ids-and-versions en 73줄

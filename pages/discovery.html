카드

"완벽한 X 를 제일 좋은 모델로" 같은 해법 요청을 받으면 짓기 전에 묻고 적음 — 진짜 필요 · 범위 · 데이터 사실. 공식 근거는 코딩 세션 문서 : 바로 코딩하면 엉뚱한 문제를 풂 → 탐색·계획을 구현과 떼고, 큰 기능은 인터뷰 먼저 하고 명세(spec)를 씀 ✓ 확인

이걸 AI 시스템 설계 전체로 넓힌 건 이 카드의 해석 업계 일반. 적는 법(결과·범위·증거)은 ■ 문제 정의, 여기는 묻는 법·사실 모으기

비유 "DB 더 큰 걸로 바꿔 줘" 티켓에 느린 쿼리·목표 지연(latency)부터 묻기. PCI 범위는 카드 데이터가 흐르는 시스템에만 — 모든 워크로드에 PCI 통제(control)를 걸지 않음

규칙 원문 ①②③④⑤ (갈림길로 그린 규칙)
  1. ①

    먼저 묻기 : 처음 온 기능 요청 말고 진짜 필요를 찾음. 공식(코딩 세션) = 바로 코딩하면 엉뚱한 문제를 풂 → 탐색·계획을 구현과 뗌(plan mode) ✓ 확인 [6.1①]

    큰 기능은 인터뷰 먼저 : 구현·UX·엣지 케이스·걱정·trade-off 를 묻고, 뻔한 질문 말고 안 떠올린 어려운 곳을 팜 → 다 덮을 때까지 묻고 명세로 ✓ 확인

    반대로 범위가 분명하고 작으면 계획 없이 바로 — 한 문장으로 설명되는 변경이면 계획 생략. 계획에도 부담이 있음 ✓ 확인

  2. ②

    무엇을 묻나 (계약 검토기 예) : 어떤 조항이 중요한지 · 누가 결과를 읽나 · 놓치면 비용이 얼마인지 · 데이터가 민감한지 업계 일반 목록 6.1① [6.1①]

    모델·도구는 범위·위험·성공 기준이 보인 뒤 업계 일반 · 규칙이 안정적이면 LLM 없는 코드도 선택지 → ◆ 코드 vs LLM vs hybrid

  3. ③

    충분히 구체적인가 : eval 과제를 적어 보면 요구가 짓기에 충분히 구체적인지 드러남 ✓ 확인 [6.1①] [6.1②]

    좋은 과제 = 전문가 둘이 따로 봐도 같은 합격·불합격 ✓ 확인 · 같은 명세를 읽은 엔지니어 둘이 엣지 케이스를 다르게 해석할 수 있음 → eval 이 이 모호함을 풂 ✓ 확인

    안 적은 기대는 초기 테스트에선 "되는" 기능이 나중에 못 맞춤 — 잘 만든 eval 이면 일찍 드러났을 것 ✓ 확인

  4. ④

    결과물 = 명세(spec) : 스스로 완결 — 관련 파일·인터페이스 이름 · 범위 밖 명시 · 마지막에 기능이 되는지 증명하는 end-to-end 검증 단계. 명세를 정확히 만드는 시간이 구현을 지켜보는 시간보다 더 쓸 만함 ✓ 확인 (코딩 명세 기준 — 설계 문서로 넓힌 건 해석) [6.1①] [6.4]

함정

  • ≠"요청대로 가장 좋은 모델과 프롬프트부터" → 먼저 묻기. 바로 코딩하면 엉뚱한 문제를 풂 ✓ 확인 (코딩 문맥 — 넓힌 건 해석)
  • ≠"완벽한 정확도를 약속하고 착수" → 약속하지 않음 → ■ 문제 정의 · 규칙 ⑤
  • ≠"민감하니 BAA·GDPR·ZDR 을 한 묶음으로" → 셋은 대상·조건이 다름. PHI 없으면 BAA 대상 아님 ✓ 확인
  • ≠"HIPAA 에 ZDR 도 추가" → ZDR 은 따로 필요 없음 ✓ 확인 (Claude Code 예외는 ■ BAA 적용 범위)
  • ≠"ZDR 조직에서 Fable 5.1" → Covered Models 를 쓰는 워크스페이스엔 ZDR 없음 ✓ 확인 (한시 전환 옵션은 예외)
  • ≠"인터뷰 = '뭐가 필요하세요?'" → 뻔한 질문 말고 안 떠올린 어려운 곳(엣지 케이스·trade-off) ✓ 확인
  • ≠반대 함정 : "모든 일에 인터뷰·명세부터" → 범위가 분명하고 작으면 바로 ✓ 확인

  • 감기약 하나 사러 온 손님에겐 길게 묻지 않아요.

원리

해법 요청은 필요의 추측

  • 요청자가 떠올린 해법("가장 좋은 모델로")은 문제를 풀 방법에 대한 짐작일 뿐. 문제 자체가 아님.
  • 공식(코딩 세션) : 바로 짓기 시작하면 엉뚱한 문제를 풂 → 탐색·계획을 구현과 뗌.
  • 묻는 비용 < 잘못 짓는 비용 : 명세를 정확하게 만드는 시간이 구현을 지켜보는 시간보다 더 쓸 만함 (공식).

모호함은 eval 로 드러남

  • 요구 문장을 eval 과제로 적어 보면, 전문가 둘이 같은 합격·불합격을 낼 수 있는지로 구체성을 판정할 수 있음.
  • 같은 명세를 읽은 두 사람이 엣지 케이스를 다르게 해석함 → 이게 나중에 "되는데 기대와 다름"이 됨.

약정은 데이터 사실에서 나옴

  • 약정(BAA·DPA·ZDR·거주지)은 대상·조건이 제각각. 데이터 사실(PHI 유무 · EU 개인정보 · 추론 위치 요구 · 보존 요구)을 먼저 모아야 어느 약정이 걸리는지 정해짐.
  • 거꾸로(약정부터 묶기) 하면 : 필요 없는 제약(쓸 수 없는 모델·기능)과 비용이 붙고, 정작 걸려야 할 조건은 빠질 수 있음.

discovery 양은 범위에 비례

  • 범위가 분명하고 작으면 생략이 공식 권장. 탐색형 과제는 오히려 먼저 돌려 보는 게 묻는 방법.

뒤집히는 때

1. 작은 일엔 discovery 를 생략

  • 조건 : 범위가 분명하고 고칠 게 작음(오타·로그 한 줄·이름 바꾸기).
  • 판단 : 계획은 부담도 있음 → 바로 함. "모든 요청에 인터뷰부터"는 반대 함정.
  • 등급 : ✓ 확인
  • 근거 : best-practices en 265줄

2. 탐색형이면 먼저 돌려 보는 게 묻는 방법

  • 조건 : 요구자도 무엇을 원하는지 아직 모름. 모델이 문제를 어떻게 해석하는지부터 보고 싶음.
  • 판단 : 계획을 건너뛰고 모호한 프롬프트로 먼저 돌려 본 뒤 좁힘. 결과물을 보여 주는 것이 곧 질문.
  • 등급 : ✓ 확인 (문장은 코딩 세션 문맥 — 설계 discovery 로 넓힌 건 해석)
  • 근거 : best-practices en 821줄 "Sometimes a vague prompt is exactly right because you want to see how Claude interprets the problem before constraining it."

3. "HIPAA 면 ZDR 불필요" 가 뒤집히는 surface

  • 조건 : PHI 를 Claude Code(CLI · 데스크톱 로컬)로 다룸.
  • 판단 : API 는 HIPAA readiness 로 ZDR 없이 되지만, Claude Code 는 API HIPAA readiness 대상이 아니고 BAA 적용은 ZDR 을 켰을 때만. surface 가 바뀌면 사실 → 약정 짝도 바뀜.
  • 등급 : ✓ 확인
  • 근거 : api-and-data-retention en 49·66줄 · privacy-baa en 39줄 → 세부 ■ BAA 적용 범위

4. Covered Models 인데 ZDR 이 되는 때

  • 조건 : Fable 5.1 을 쓰고 싶고 보존 최소화 요구가 있음.
  • 판단 : 기본은 ZDR 불가(30일 보존). 단 자격 고객에게 사내 업무 앱용으로 한시 ZDR 옵션이 주어짐(EFS 로 가는 전환).
  • 등급 : ✓ 확인 · 시험 뒤 변경(Fable 5.1 = 2026-08-31)
  • 근거 : covered-models en 12·20·36줄

5. 거주지 요구를 사실 확인 없이 걸면 드는 값

  • 조건 : "민감하니까 미국 안에서만" 을 사실 확인 없이 inference_geo: "us" 로 고정.
  • 계산 : 월 입력 3억 · 출력 5천만 토큰, Sonnet 5($2 / $10 백만 토큰당) → global = 300 × $2 + 50 × $10 = $1,100. us = 1.1배 = $1,210. 월 $110 더 냄.
  • 전제 : 캐싱·배치 없음 · 가격 = 2026-09-28 조회값 · Sonnet 5 는 4.6 이후 모델이라 inference_geo 지원.
  • 등급 : 계산 (1.1배는 확인)
  • 근거 : data-residency en 58줄 · prompt-caching ko 39줄 표(Sonnet 5 가격)
  • 판단 : 거주지 요구가 사실이면 당연히 냄. 사실이 아니면 값만 붙은 제약 → 그래서 사실 먼저.

■ lifecycle 루프

lifecycle : discovery · design · handoff · monitoring · iteration — 핸드오프 뒤 할 일6.5 본편

왜 배우나 — 시험이 요구하는 것

시험 목표 6.5 수명주기 지원 · D6 사람·문서 14%
Support lifecycle phases (discovery, design, handoff, monitoring, iteration)

이 개념으로 푸는 판단 (할 수 있어야 하는 것)

  • 6.5① 핸드오프가 끝났다 — 아키텍트가 계속 할 일 두 가지는? (복수 응답) — 수명주기 5단계(디스커버리·설계·핸드오프·모니터링·반복)는 되돌아오는 루프 — 핸드오프 뒤 할 일
  • 6.3② 월간 검토에서 법무팀이 놓친 조항 사례를 들고 왔다 — 이 피드백을 어디로 보내나? — 피드백 루프를 닫는 방법 (상태 보고 회의 vs 평가셋 편입)

한눈에

가이드 목표 6.5 의 5단계 = discovery · 설계 · 핸드오프 · 모니터링 · 반복 ✓ 확인. 한 번 지나가는 줄이 아니라 반복이 설계로(요구가 바뀌었으면 discovery 로) 되돌아가는 루프 — 루프 모양은 업계 일반. 공식 글은 "일찍 성공을 정하고, 분명히 재고, 계속 반복" 까지 ✓ 확인

핸드오프는 끝이 아님 : 그 뒤 할 일 두 가지 = 모니터링(운영(production) 신호 + 사람 정기 검토) · 반복(실패를 eval 과제로 넣어 다음 결정의 증거로) ✓ 확인

비유 운영 이관 뒤에도 재발 장애는 regression(회귀) 테스트로 만들고, 작은 장애마다 아키텍처를 다시 그리지 않음. "이관하면 끝"이 속이는 습관

ELI5

정원 가꾸기와 같아요. 씨앗을 심고 끝이 아니에요.

  • 무엇을 심을지 정하고(디스커버리), 어디에 심을지 그려요(설계).
  • 심고 나서 관리할 사람에게 넘겨요(핸드오프).
  • 그 뒤에도 잎을 살피고(모니터링), 병든 가지는 고쳐요(반복).
  • 잎 하나 시들었다고 정원을 갈아엎지 않아요. 같은 병이 계속 돌면 그때 흙을 바꿔요.

개념 설명

원리

5단계와 루프

  • 가이드 목표 6.5 가 단계 이름 5개를 줌 : discovery · 설계 · 핸드오프 · 모니터링 · 반복.
  • 공식 글의 요지 : 일찍 성공을 정하고, 분명히 재고, 계속 반복. eval 은 lifecycle(수명주기) 어느 단계에서도 쓸모.
  • 반복이 설계(또는 discovery)로 되돌아가는 모양은 업계 일반. 공식은 "실패가 테스트 과제가 되고, 테스트 과제가 regression(회귀)을 막는다" 까지.

핸드오프가 끝이 아닌 이유

  • 운영(production) 모니터링은 출시 뒤에야 분포 변화 · 예상 못 한 실패를 잡음. 단 사후 대응 — 사용자가 먼저 겪음.
  • 반복이 빠지면 하나 고치면 다른 게 깨지는 사후 대응 루프에 갇힘 (공식 "reactive loops").
  • eval 셋은 살아 있는 산출물 → 소유자가 없으면 낡음. 전담 팀이 인프라, 도메인 전문가·제품팀이 과제를 기여.
  • 모델 lifecycle : 모델 ID 마다 지원 중단·종료 일정. 교체는 반복 단계의 일, eval 이 있으면 며칠.

되돌아가는 폭 (업계 일반)

  • 사소한 결함 한 건 → 반복 안에서 고치고 regression eval.
  • 같은 실패가 반복 → 설계를 바꾸기 전에 그 사례를 eval 에 넣어 커버리지부터 → 다음 변경을 그 사례로 검증.
  • 증거가 요구 변화를 보여 줌 → discovery 로.

핵심 질문 두 개

  • 핸드오프 뒤 모니터링과 반복을 누가, 무엇으로 계속하나?
  • 들어온 문제가 어느 단계까지 되돌아갈 크기인가?

  4. ④

    eval 셋은 핸드오프 뒤에도 소유자가 있어야 : 살아 있는 산출물 · 계속 손보고 명확한 소유권이 있어야 쓸모 ✓ 확인 [6.5①]

    가장 잘 된 방식 = 전담 eval 팀이 핵심 인프라, 도메인 전문가·제품팀이 과제 대부분을 기여하고 직접 돌림 ✓ 확인. PM · 고객 성공 매니저 · 영업도 Claude Code 로 과제를 PR 로 기여 ✓ 확인

    100% 통과한 capability(능력) eval → regression 스위트로 졸업 · 100% eval 은 regression 만 잡고 개선 신호 없음(포화) ✓ 확인 → ◆ capability eval vs regression eval

  5. ⑤

    모델 lifecycle : 모델 ID = 고정 스냅숏, 새 버전 = 새 ID ✓ 확인 · 모델 ID 마다 지원 중단·종료 일정이 따로 ✓ 확인 [6.5①]

    교체는 반복 단계의 일 : eval 이 있으면 며칠, 없으면 몇 주 ✓ 확인 · effort 설정도 이전 모델에서 가져오지 말고 자체 eval 에서 새로 스윕 ✓ 확인 → ■ 변경마다 eval 다시

더 깊이 : 뒤집히는 때 · 오답 재료 (설명)

뒤집히는 때

1. 작은 결함인데 discovery 로 가야 할 때

  • 조건 : 서식 오류 한 건이 들어왔는데, 원인이 "법무팀이 새 규정을 도입해 출력 양식 자체가 바뀜".
  • 판단 : 결함의 크기가 아니라 원인이 요구 변화면 discovery 로. "작으면 반복 안에서" 는 원인이 기존 요구 안에 있을 때만.
  • 등급 : 업계 일반
  • 근거 : 공식 문장 없음. eval 과제를 정의하는 것이 요구의 구체성을 시험한다(demystifying-evals en 277줄)는 원칙과 같은 방향.

2. 반복 실패인데 eval 추가보다 먼저 막아야 할 때

  • 조건 : 하루 1,200건 중 30건(2.5%)에서 환불 금액을 잘못 안내, 고객 금전 피해가 진행 중.
  • 판단 : 피해가 진행 중이면 먼저 사람 검토 경로를 넓히거나 기능을 좁혀 막고, 그다음 그 사례를 eval 에 넣어 설계 변경을 검증. "eval 먼저" 는 피해를 방치하라는 뜻이 아님.
  • 등급 : 업계 일반 (사람 검토 경로 = ■ human-in-the-loop 게이트 위치 · ◆ 100% 약속 vs 측정된 SLO + 사람 안전망)
  • 근거 : 공식 순서 문장 없음.

3. 아키텍트 개인이 빠져도 되는 때

  • 조건 : 핸드오프 때 eval 셋 소유 팀이 정해지고, 도메인 전문가가 과제를 PR 로 기여하는 경로가 있음.
  • 판단 : 틀린 보기 "핸드오프로 아키텍트 역할은 끝" 이 틀린 이유는 모니터링·반복이 멈추기 때문이지, 그 사람이 꼭 남아야 해서가 아님. 소유권이 넘어가 루프가 돌면 개인은 빠져도 됨.
  • 등급 : 확인(소유권·기여 구조) · 업계 일반(개인 역할 해석)
  • 근거 : demystifying-evals en 273·275·281줄

4. eval 이 100% 인데 할 일이 남을 때

  • 조건 : capability eval 40문항이 석 달째 40/40.
  • 판단 : 포화 — regression 만 잡고 개선 신호 없음. 이 셋은 regression 스위트로 졸업시키고, 운영에서 들어온 새 실패로 capability eval 을 새로 만듦.
  • 등급 : ✓ 확인
  • 근거 : demystifying-evals en 88·267줄

5. 모델 종료 공지가 반복을 강제로 여는 때

  • 조건 : 쓰던 모델 ID 에 종료 일정이 공지됨.
  • 판단 : 모델 ID 는 고정 스냅숏이라 스스로 안 바뀌지만, 종료 일정은 ID 마다 있음 → 교체는 반복 단계의 일. eval 이 있으면 며칠, 없으면 몇 주. effort 설정은 가져오지 말고 새로 스윕.
  • 등급 : ✓ 확인
  • 근거 : model-ids-and-versions en 63·67줄 · demystifying-evals en 50줄 · effort en 47줄

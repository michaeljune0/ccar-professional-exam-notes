■ 모델별 thinking 제어

adaptive + effort vs budget_tokens · 400 조건2.3 본편아래 설명 보기

카드

thinking(사고) lever(손잡이)는 모델마다 다름 → 문항의 모델 이름을 먼저 봄. 새 방식 = thinking: {type: "adaptive"} + output_config.effort(Claude 가 thinking 할지·얼마나 할지 정함) · 옛 방식 = thinking: {type: "enabled", budget_tokens: N}(수동 extended thinking). 모델이 안 받는 설정은 400 ✓ 확인

지출의 엄격한 상한은 어느 방식이든 max_tokens(thinking + 답 합계). effort 는 유연한 지침, budget_tokens 는 목표치 ✓ 확인

비유 Kubernetes apiVersion. 버전마다 받는 필드가 다름 → 매니페스트에 적힌 버전의 스펙으로 판단. 그 버전에 없는 필드를 넣으면 API 서버가 거부

나머지 규칙

  1. ⑤

    바꾸면 캐시가 깨짐 : thinking 모드 전환 · budget_tokens 변경 · 요청 단위(top-level) effort 변경 = 메시지 캐시 무효화 → 대화 안에서는 고정. 기본값을 명시하는 건 생략과 같아 안 깨짐 ✓ 확인. 메시지별 effort(베타, Fable 5.1·Mythos 5.1·Opus 5.5·Opus 5)는 캐시 유지 시험 뒤 변경 2026-09-01~ · 상세 = ■ 프롬프트 캐싱

  2. ⑥

    thinking 과 같이 걸리는 그 밖의 400 ✓ 확인

    새 모델(Fable·Mythos · Opus 5.5·5·4.8·4.7 · Sonnet 5)은 temperature·top_p·top_k 를 기본값 아닌 값으로 주면 thinking 과 무관하게 400

    수동 extended thinking + 강제 도구 사용(tool_choice any·tool) = 오류 · Opus 5.5·Fable 5.1 은 강제 도구 사용 자체가 400 → auto + strict tool use

    thinking 켠 채 prefill 불가

    도구 결과를 보낼 때 thinking 블록을 고치거나 빼면 400 → 받은 그대로 돌려줌

    모델별 thinking 방식 (2026-09-28 조회) ✓ 확인 [2.3③]

  2. ②

    effort : output_config.effort(thinking 객체 안 아님). 단계 = low · medium · high · xhigh · max ✓ 확인

    기본 = high, Opus 5.5 만 medium (2026-09-28 조회 · 시험 뒤 변경 — Opus 5.5 2026-09-22 출시)

    모든 출력 토큰(답 · 도구 호출 · thinking)에 걸림 → thinking 이 꺼져도 작동 ✓ 확인. thinking 의 주 lever 인 건 adaptive 모드에서만 — extended thinking 전용 모델은 budget_tokens 가 깊이를 정함 ✓ 확인

    max 지원 모델 = Fable·Mythos 계열 · Opus 5.5·5·4.8·4.7·4.6 · Sonnet 5·4.6 / xhigh 지원 모델 = Fable·Mythos 5.x·5 · Opus 5.5·5·4.8·4.7 · Sonnet 5 (4.6 은 xhigh 없음) (2026-09-28 조회) ✓ 확인

    adaptive 는 effort 값이 아님(thinking 모드) ✓ 확인

    Opus 4.5 = effort 를 지원하는 유일한 extended thinking 전용 모델 → Haiku 4.5·Sonnet 4.5 는 effort 없음 ✓ 확인 (문장의 '유일한'에서)

    effort 를 모델 교체와 비교하는 판단 = ◆ effort 조정 vs 모델 교체 · 지연(latency) 쪽 = ■ 지연 줄이기 lever

  3. ③

    budget_tokens (수동 extended thinking) ✓ 확인

    최소 1,024 · max_tokens 보다 작게(interleaved thinking 은 예외) · 목표치이지 엄격한 상한 아님 → 엄격한 상한은 max_tokens

    시작점 = 단순한 일 1,024 근처 · 복잡한 일 16,000 이상. 32k 넘는 예산은 배치 처리로

    예측 가능한 지연·thinking 비용 정밀 제어가 필요하면 수동 모드가 여전히 유용

    고정 예산은 매 요청 thinking · adaptive 는 요청마다 thinking 할지 정함(낮은 effort 면 쉬운 입력은 건너뜀)

    Haiku 4.5 는 interleaved thinking(도구 호출 사이 thinking) 없음

  4. ④

    비용 묶기 ✓ 확인 [2.3③] [4.5]

    max_tokens = thinking + 답 합계의 엄격한 한도 · effort = 유연한 지침(토큰 수 보장 안 함)

    평균 비용·지연을 줄이려면 effort ↓ 먼저 → thinking 포함 전체 응답이 줄어듦

    도구 루프는 요청마다 max_tokens 가 따로 → 턴 전체 지출은 못 묶음

    thinking 토큰 = 출력 토큰 단가로 청구. display "omitted" 로 숨겨도 똑같이 청구(숨기면 지연만 줄어듦)

    실제 thinking 양 = usage.output_tokens_details.thinking_tokens

    stop_reason: "max_tokens" → 추론이 필요했으면 max_tokens ↑, 과하게 생각했으면 effort ↓

함정

  • ≠"budget_tokens 는 낡았으니 무조건 adaptive + effort 로" → Haiku 4.5·Sonnet 4.5·Opus 4.5 는 adaptive 가 400. 모델 이름 먼저 ✓ 확인
  • ≠"budget_tokens 보기는 무조건 지운다" → 4.6 은 지원 중단이지만 요청은 성공, 4.5 이하는 유일한 모드 ✓ 확인
  • ≠"budget_tokens = thinking 비용의 엄격한 상한" → 목표치. 엄격한 상한은 max_tokens ✓ 확인
  • ≠"Haiku 4.5 에서 effort 로 thinking 을 줄인다" → effort 는 Opus 4.5 만. Haiku 4.5 는 budget_tokens ✓ 확인
  • ≠"effort 는 thinking 전용이라 thinking 끄면 소용없음" → 모든 출력 토큰에 걸림 ✓ 확인
  • ≠"effort 에 adaptive 를 넣는다" → adaptive 는 thinking 모드 ✓ 확인
  • ≠"Opus 5.5 에서 thinking 을 꺼서 비용을 줄인다" → 못 끔(400). effort ↓ ✓ 확인
  • ≠"effort 를 안 주면 어디서나 high" → Opus 5.5 는 medium 시험 뒤 변경
  • ≠"display omitted 로 숨기면 thinking 비용도 준다" → 지연만 줄고 비용은 그대로 ✓ 확인
  • ≠Skilljar(2025 제작) "thinking budget = thinking 에 쓸 최대 토큰" · 코드 키 budget → 지금 docs 는 budget_tokens, 목표치이지 엄격한 상한 아님 (Skilljar)

자동차마다 속도 조절 장치가 달라요.

  • 옛날 차는 "최대 몇 km 까지"를 손으로 정해요.
  • 새 차는 "천천히 / 보통 / 빨리" 버튼만 있어요.
  • 옛날 차에 버튼을 찾으면 없고, 새 차에 손잡이를 끼우면 안 들어가요.
  • 그래서 먼저 차 이름표(모델 이름)를 봐요.
  • 어느 차든 연료통 크기(max_tokens)가 진짜 끝이에요.

원리

두 방식

  • 옛 방식 = 수동 extended thinking(확장 사고) thinking: {type: "enabled", budget_tokens: N}. 사람이 thinking 예산을 정함. 고정 예산이면 매 요청 thinking.
  • 새 방식 = thinking: {type: "adaptive"} + output_config.effort. 모델이 요청마다 thinking 할지·얼마나 할지 정함. effort 는 그 성향을 미는 유연한 지침.
  • 세대 경계 : 4.5 이하 = 옛 방식만 · 4.6 = 둘 다(옛 방식은 지원 중단) · 4.7 이후 = 새 방식만. 안 받는 쪽을 보내면 400.

effort 가 하는 일

  • thinking 만이 아니라 답 글·도구 호출까지 모든 출력 토큰에 걸림 → thinking 이 꺼져도 작동.
  • 단 thinking 깊이의 주 lever(손잡이)인 건 adaptive 모드에서만. extended thinking 전용 모델에서 effort 를 바꿔도 thinking 은 그대로(그 모델들은 대부분 effort 자체가 없음 — Opus 4.5 만 예외).

상한은 하나뿐

  • max_tokens = thinking + 답 합계의 엄격한 한도. 넘어서 생성하지 않음.
  • budget_tokens = 목표치(예산보다 훨씬 일찍 멈출 수 있음). effort = 토큰 수 보장 안 함.
  • 도구 루프는 요청마다 max_tokens 가 따로라 턴 전체는 못 묶음.

설정은 프롬프트의 일부

  • thinking 모드·budget_tokens·effort 값은 프롬프트 안에 렌더링됨 → 바꾸면 캐시 앞부분이 달라져 메시지 캐시가 깨짐.

핵심 질문 두 개

  • 문항의 모델은 어느 세대인가? (받는 필드가 정해짐)
  • 원하는 게 엄격한 상한인가, 평균을 낮추는 것인가, 깊이를 올리는 것인가?

뒤집히는 때

1. Haiku 4.5 대량 분류기의 "thinking 비용 상한" — 켜지 않는 게 가장 싼 상한

  • 조건 : Haiku 4.5 로 하루 30만 건 분류. thinking 비용에 상한을 걸라는 지문.
  • 계산 : Haiku 4.5 출력 $5 / 백만 토큰. thinking 을 켜면 budget_tokens 최소 1,024 · max_tokens 는 그보다 커야 함 → max_tokens 1,300 이면 요청당 출력 최악 1,300 × $5 = $0.0065, 하루 최악 30만 × $0.0065 = $1,950. thinking 없이 라벨만 30 토큰이면 30 × $5 = $0.00015, 하루 $45. 배치로 돌리면 출력 $2.50 이라 둘 다 절반.
  • 전제 : 입력 비용은 양쪽 같다고 보고 뺌 · thinking 켠 쪽은 최악(상한까지 씀) 기준 · 가격 = 2026-09-28 조회값.
  • 판단 : 지문의 답은 "budget_tokens(adaptive·effort 아님) + 엄격한 상한은 max_tokens". 단 Haiku 4.5 는 thinking 이 기본 꺼짐이라, thinking 없이 eval 을 통과하면 "켜지 않음"이 가장 싸고 확실한 상한. 보기에 그게 있으면 그쪽이 설 자리가 있음.
  • 등급 : 계산 (단가·최소값·기본 꺼짐은 확인)
  • 근거 : ko-pricing 9·125줄 표 · extended-thinking en 21~25줄 · thinking-troubleshooting en 26줄

2. Opus 5 설정을 Opus 5.5 로 그대로 옮긴 때

  • 조건 : effort 를 안 적은 채 Opus 5 → Opus 5.5 로 모델 문자열만 바꿈.
  • 판단 : Opus 5 기본 high · Opus 5.5 기본 medium → 한 단계 낮게 돎. 복잡한 일에서 품질이 떨어지면 모델 탓이 아니라 기본값 차이일 수 있음 → 자기 eval 로 effort 스윕. 또 thinking: {type: "disabled"} 를 쓰던 코드는 Opus 5.5 에서 모든 effort 에서 400.
  • 등급 : ✓ 확인
  • 근거 : effort en-2026-09-28 47줄
  • 시험 뒤 변경 Opus 5.5 = 2026-09-22 출시 (릴리스 노트 en 15~16줄)

3. 대화 중간에 깊이를 바꾸면 캐시가 깨지는 때

  • 조건 : 긴 대화를 캐싱으로 돌리다 "이번 턴만 더 깊게" 하려고 요청 단위 effort 를 high → max 로.
  • 판단 : 요청 단위 effort 는 프롬프트에 렌더링 → 메시지 캐시가 전부 미스. Fable 5.1·Mythos 5.1·Opus 5.5·Opus 5 는 메시지별 effort(role: "system" 메시지, 베타)로 캐시를 지킴. 그 밖의 모델은 대화 시작에 정하고 고정하거나, 그 턴의 user 메시지 끝에 "Please think hard before responding." 같은 유도 문구(캐시 안 깨짐).
  • 등급 : ✓ 확인
  • 근거 : effort en-2026-09-28 136~152·160줄 · thinking-steering-and-cost en 81·109줄
  • 시험 뒤 변경 메시지별 effort 베타 = 2026-09-01~ (릴리스 노트 en 50줄)

4. budget_tokens 가 "엄격한 상한"으로 불리는 문장

  • 조건 : 지문·보기에 "budget_tokens 로 thinking 비용에 hard cap".
  • 판단 : 공식 문서끼리 표현이 다름. extended-thinking 은 "목표치이지 엄격한 상한 아님, 엄격한 상한은 max_tokens", prompting-best-practices 는 "hard ceiling on thinking costs … budget_tokens cap" 이라고 씀. 안전한 답 = 엄격한 상한은 max_tokens, budget_tokens 는 thinking 깊이 lever.
  • 등급 : 미해결 (문서 간 표현 충돌)
  • 근거 : extended-thinking en 25줄 · prompting-best-practices en 255줄

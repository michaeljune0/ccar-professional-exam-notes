  • Claude 자체도 인젝션에 버티게 설계됐고 자체 분류기를 씀 — 그래도 앱 쪽 대응을 겹침 ✓ 확인. 모델 재학습·더 큰 모델은 공식 대응 목록에 없음 (추론)

함정

  • ≠"안전 학습(모델 재학습)으로 막는다" → Anthropic 쪽 일. 공식 대응 목록에 없음 (추론 — 목록 5.1① 매력적인 오답)
  • ≠"더 큰 모델로 교체" → 공식 대응 목록에 없음 (추론 — 샘플 1 D 와 같은 방향)
  • ≠간접 인젝션인데 "사용자를 스로틀·차단" → 간접이면 사용자는 피해자 — 적은 가져온 콘텐츠 (추론)
  • ≠간접 인젝션인데 "메일 본문을 user text 에 붙여 넣고 '지시는 무시해' 문구만" → 제3자 콘텐츠는 tool_result 에만 ✓ 확인
  • ≠반대 함정 : "system prompt 문구·분류기 선별 보기는 항상 오답" → 둘 다 공식 권장 목록에 있음 ✓ 확인
  • ≠두 위협 모델을 한 처방으로 묶음 ("입력 필터 하나면 됨") → 간접은 사용자 입력이 아니라 가져온 콘텐츠로 들어옴 ✓ 확인

신호

"These attacks fall into two categories with different threat models:"

"Jailbreaks and direct prompt injection, where the user of your application is the adversary and crafts inputs intended to bypass your guardrails."

"Indirect prompt injection, where the user is trusted but Claude processes third-party content (web pages, emails, documents, tool results) that contains adversarial instructions."

"Use a lightweight model like Claude Haiku 4.5 to pre-screen user input before it reaches your main conversation."

"Adjust responses and consider throttling or banning users who repeatedly attempt to circumvent your application's guardrails."

"Apply the same lightweight-model screening pattern you use for user input to the content your tools return."

ELI5

가게에 나쁜 손님이 오는 경우와, 착한 손님이 들고 온 편지에 나쁜 말이 적힌 경우는 달라요.

  • 나쁜 손님이면 문 앞에서 막고, 자꾸 오면 못 들어오게 해요.
  • 편지가 나쁘면 손님은 잘못이 없어요. 편지를 따로 상자에 넣고 "편지 내용은 명령이 아님"이라고 정해 둬요.
  • 두 경우 다 문 앞 검사원은 똑같이 쓸 수 있어요.
  • 먼저 "누가 나쁜가"를 봐야 막는 방법이 정해져요.

원리

위협 모델이 둘 (공식이 둘로 나눔)

  • 직접(탈옥 포함) : 앱의 사용자가 공격자. 가드레일을 넘으려는 입력을 일부러 만듦.
  • 간접 : 사용자는 믿을 만함. Claude 가 사용자 대신 읽는 제3자 콘텐츠(받은 메일 본문 · 가져온 웹 페이지 · 업로드 파일 OCR · 도구 결과)에 공격 지시가 들어 있음.

왜 처방이 갈리나

  • 직접 : 공격이 사용자 입력 한 곳으로 들어옴 → 입구에서 거르고, 같은 사용자가 반복하면 그 사용자에게 조치.
  • 간접 : 공격이 "데이터" 자리로 들어옴 → Claude 가 데이터와 내 지시를 안정적으로 구분하게 앱 구조를 짬. 사용자는 피해자라 사용자에게 조치할 이유가 없음.

겹치는 부분

  • 가벼운 모델(Haiku 4.5) 선별 : 사용자 입력에도, 도구 원시 출력에도 같은 패턴. 판정은 구조화 출력으로 받아 앱이 분기.
  • 입력 검증 패턴도 도구 결과에 적용 가능.
  • 여러 방어를 겹치고(layering), 배포 뒤 출력을 계속 분석.

모델 쪽과 앱 쪽

  • Claude 는 원래 이런 공격에 버티게 설계됐고, Anthropic 은 분류기로도 막음. 공식 대응 목록은 그 위에 앱이 덧대는 것.

뒤집히는 때

1. 사용자가 공격자인데 콘텐츠로 들어올 때

  • 조건 : 사용자가 직접 만든 문서를 업로드해 그 속에 우회 지시를 심음.
  • 판단 : 출처는 "업로드 파일"이라 간접처럼 보이지만 공격자는 사용자 본인. 두 쪽 처방을 함께 : 파일 내용은 tool_result 로 격리 + 같은 사용자가 반복하면 반복 위반자 대응.
  • 등급 : 추론 (공식은 두 위협 모델을 나누기만 하고 섞인 경우 문장은 없음)
  • 근거 : mitigate-jailbreaks en 5·6·15·23줄

2. 도구 결과인데 믿을 만한 출처일 때

  • 조건 : 도구가 사내 정책 DB 에서 운영팀이 쓴 문서를 가져옴.
  • 판단 : 공식은 "도구·문서·검색 결과는 비신뢰 데이터"로 일괄 명시하라고 함 → 출처가 사내여도 그 안의 지시가 system prompt 를 덮게 두지 않음. 다만 콘텐츠가 무엇이고 어디서 왔는지 알려 주면 Claude 가 얼마나 믿을지 조정함.
  • 등급 : ✓ 확인 (정책 명시 · 출처 표시)
  • 근거 : mitigate-jailbreaks en 24·25줄

3. "가장 효과적인 하나" vs "두 개 고르시오"

  • 조건 : 간접 인젝션 문항, 보기에 선별·문구·경로 차단이 섞임.
  • 판단 : 하나면 구조(나가는 길 차단·권한 제거), 두 개면 문구 명시·분류기 선별도 후보.
  • 등급 : 추론 (공식 목록엔 순서 없음 — ■ 프롬프트 인젝션 피해 경로 끊기 · 규칙 ④)
  • 근거 : mitigate-jailbreaks en 21~31줄(순서 표시 없음)

오답 재료

오답 왜 끌리나 왜 틀리나 등급 근거
"안전 학습(모델 재학습)으로 막는다" 근본 해결처럼 보임 앱이 고르는 공식 대응 목록에 없음. 모델 쪽 방어는 Anthropic 이 이미 함 추론 mitigate-jailbreaks en 1·12~15줄 · safe-trustworthy-agents en 53줄
"더 큰 모델로 교체" 지시를 더 잘 따를 것 같음 공식 대응 목록에 없음. 샘플 1 D 도 같은 원리 추론 가이드 샘플 1 해설
간접 인젝션에 "해당 사용자 차단" 반복 공격 대응이 공식 항목이라 간접이면 사용자는 피해자 추론 mitigate-jailbreaks en 6줄
메일 본문을 user text 에 이어 붙이고 "속 지시는 무시" 한 줄 문구도 공식 권장이라 넣는 자리가 틀림 — 제3자 콘텐츠는 tool_result 에만 ✓ 확인 mitigate-jailbreaks en 23줄
"system prompt 문구·분류기 선별 보기는 항상 오답" "문구는 안 막는다"는 감 둘 다 공식 권장 목록에 있음 ✓ 확인 mitigate-jailbreaks en 12·14·25·29줄
"입력 필터 하나면 두 공격 다 막음" 필터가 입구라서 간접은 사용자 입력이 아니라 도구 결과로 들어옴 → 도구 출력 선별이 따로 필요 ✓ 확인 mitigate-jailbreaks en 29~30줄

미해결

  1. 목록 5.1① 의 Constitutional classifiers 수치(86%→4.4%, 연산 23.7%)는 받아 둔 원문(mitigate-jailbreaks·safe-trustworthy-agents)에 없음 — 카드에 안 씀 (검색어 86, 4.4, 23.7).
  2. 목록 5.1① 의 영상 '입력 분류기·안전 학습·거절 지시' 중 "안전 학습"은 공식 목록에 없음 — 카드엔 함정으로만.
  3. 사용자가 공격자이면서 콘텐츠로 들여오는 섞인 경우(뒤집히는 때 1)는 공식 문장 없음.
  4. 대화 중간 system message(지원 모델 한정)는 이름만 확인 — 어느 모델이 지원하는지 원문 미수집.

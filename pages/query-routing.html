카드

질문 종류에 맞춰 검색(retrieval) 노력을 조절함. 기본은 hybrid + 리랭킹 한 줄기. 질문 모양이 뚜렷이 갈릴 때만 경로를 나누고, 어려운 질문만 쪼개거나 여러 번 검색함

비유 L7 로드밸런서 경로별 라우팅. 비교 질문 = 대시보드 둘을 따로 조회해 나란히 놓기

지문

쇼핑몰 지원 챗봇에 환불 · 기술지원 · 일반 질문이 뚜렷이 갈려 들어온다뚜렷한 범주. 환불 쪽 프롬프트를 다듬었더니 기술지원 답이 나빠졌다. 시험해 본 분류기는 1,000건 중 985건을 맞게 분류했다분류 정확. 운영팀은 "파이프라인 하나로 통일해야 운영이 쉽다"고 한다. 어떻게 할까?

    routing(라우팅) : 입력을 분류해 전용 프롬프트·도구·모델로 보냄. 조건 두 개 = 따로 다루는 게 나은 뚜렷한 범주가 있음 + 분류가 정확함 ✓ 확인 [3.6②] [3.3③]

    예 : 일반 질문·환불·기술지원을 다른 처리로 ✓ 확인 · 쉬운 질문 → 작고 싼 모델(Haiku 4.5), 어렵거나 드문 질문 → 강한 모델 ✓ 확인

    안 나누면 한 종류에 맞춘 최적화가 다른 종류 성능을 깎을 수 있음 ✓ 확인

  3. ③

    쪼개기(decomposition)·다단계(multi-step) : 어려운 질문은 작은 하위 과제로 쪼갬 ✓ 확인. 한 번 비슷한 chunk(조각)를 가져오는 정적 RAG 대신, 결과를 보고 다음 검색을 정하는 다단계 검색 ✓ 확인 (둘 다 Research 에이전트 글 — 에이전트 검색 맥락)

    적용 :

    • 'A·B 요금제 차이' = 하위 질의 둘
    • '내 주문의 배송사 규정' = 주문 조회로 배송사를 먼저 알아낸 뒤 규정 검색 (적용 예는 업계 일반)

    검색어는 짧고 넓게 시작해 좁혀 감 ✓ 확인

  4. ④

    노력은 질문 복잡도에 맞춤 : 단순 사실 = 에이전트 1개 · 도구 호출 3~10회 / 직접 비교 = 하위 에이전트 2~4개 · 각 10~15회 / 복잡한 조사 = 하위 에이전트 10개 넘게 ✓ 확인 (Research 시스템 프롬프트 규칙)

    간단한 질문에 과투자한 게 초기 흔한 실패 ✓ 확인. 에이전트를 여럿 쓸지는 ◆ 단일 vs 멀티 에이전트

  5. ⑤

    범위 필터 : 테넌트·날짜 범위·접근 권한은 검색 단계에서 메타데이터 필터·네임스페이스로 강제 업계 일반 공식 RAG 글에 없음. 권한 원칙은 ■ 최소 권한

  6. ⑥

    매 순간 바뀌는 운영 데이터(재고·잠금 상태·주문 상태) → index 에 넣지 말고 질문마다 도구로 그때 조회(just in time). index 는 아무리 자주 다시 만들어도 낡을 수 있음 ✓ 확인 — 문서는 index, 살아 있는 상태는 조회로 나눔(나누는 방식은 추론)

함정

  • ≠"모든 질문에 가장 무거운 다단계 에이전트 검색" → 노력은 복잡도에 맞춤. 초기 Research 에이전트의 실패가 바로 "간단한 질문에 하위 에이전트 50개" ✓ 확인
  • ≠"파이프라인 하나로 통일해야 운영이 쉽다" → 뚜렷이 갈리는 입력을 한 경로로 몰면 서로 성능을 깎음 ✓ 확인. 단 기본 검색 줄기(hybrid+리랭킹)는 하나로 둬도 됨
  • ≠"분류가 애매한데도 routing" → 조건은 '분류가 정확할 때' ✓ 확인. 잘못 보낸 질문은 전용 경로에서 틀림 (추론)
  • ≠"권한 없는 문서는 답을 만든 뒤 걸러낸다" → 가져오는 순간 컨텍스트에 들어감. 검색 단계에서 막음 업계 일반
  • ≠"비교 질문도 한 번에 검색" → 한 질의로는 양쪽 chunk 가 다 안 올 수 있음 → 쪼갬 업계 일반

원리

기본 줄기

  • 섞인 실제 지원 질문의 기본은 hybrid 검색(retrieval) + 리랭킹 하나. 이득이 쌓임.

routing(라우팅)

  • 입력을 분류해 전용 프롬프트·도구·모델로 보냄. 한 종류에 맞춘 최적화가 다른 종류를 깎는 걸 막음.
  • 조건 두 개 : 따로 다루는 게 나은 뚜렷한 범주가 있음 + 분류가 정확함.
  • 비용 쪽 쓰임 : 쉬운·흔한 질문 → 작고 싼 모델, 어렵고 드문 질문 → 강한 모델.

쪼개기 · 다단계

  • 쪼개기 : 어려운 질문을 작은 하위 과제로. 비교 질문은 서로 독립인 하위 질의 둘.
  • 다단계 : 한 번 비슷한 chunk(조각)를 가져오는 정적 RAG 대신, 결과를 보고 다음 검색을 정함. 둘째 검색어가 첫 결과에 달려 있으면 이것.
  • 노력은 복잡도에 맞춤 : 단순 사실 = 에이전트 1개 · 호출 3~10회, 비교 = 하위 에이전트 2~4개. 간단한 질문에 과투자한 게 초기 흔한 실패.

범위 필터

  • 테넌트·날짜·권한은 검색 단계에서 메타데이터 필터·네임스페이스로 (업계 일반).

  • 질문 종류가 뚜렷이 갈리고, 그 분류를 정확히 할 수 있는가?

뒤집히는 때

1. 모델 routing — 싸지지만 분류가 흔들리면 손해

  • 조건 : 하루 1만 질문, 쉬운 질문 70%. 질문당 입력 3천 · 출력 500 토큰. 강한 모델 = Opus 5.5($4 / $20), 작은 모델 = Haiku 4.5($1 / $5), 백만 토큰당.
  • 계산 :
  • 전부 Opus 5.5 : 3천 × $4 + 500 × $20 = $0.012 + $0.010 = 질문당 $0.022.
  • routing : Haiku 4.5 질문당 $0.003 + $0.0025 = $0.0055. 섞으면 0.7 × $0.0055 + 0.3 × $0.022 = $0.01045. 분류기(Haiku 4.5, 입력 400 · 출력 10) $0.00045 더해 $0.0109 → 약 50% 절감.

  • 분류 정확도 90% 면 어려운 질문 3천 건 중 약 300건이 작은 모델로 감 → 그 품질 손해가 절감을 넘는지 eval 로.

  • 등급 : 계산 (가격 = 2026-09-28 조회값 · routing 조건은 확인)

  • 전제 : 두 모델 출력 길이 같음 · 캐싱·Batch 없음 · 쉬운 질문은 작은 모델로도 품질 유지.
  • 근거 : ko-pricing 9줄 · building-effective-agents en 76·81줄

2. "모든 질문에 다단계 에이전트 검색"이 맞아 보이는 때

  • 조건 : 질문 대부분이 한 chunk 면 답이 나오는 단순 사실.
  • 판단 : 공식 Research 시스템도 단순 사실은 에이전트 1개 · 호출 3~10회로 제한함. 멀티 에이전트는 채팅 대비 약 15배 토큰 → 간단한 질문엔 과투자. 무거운 경로는 비교·조사형만.
  • 등급 : ✓ 확인
  • 근거 : multi-agent-research-system en 21·41·45줄

3. 쪼갤까, 순서대로 두 번 갈까

  • 조건 A : "베이직·프로 요금제 차이" → 두 요금제 chunk 는 서로 독립 → 하위 질의 둘을 따로(동시에) 검색해 나란히.
  • 조건 B : "내 주문의 배송사 반품 규정" → 배송사를 알아야 규정을 찾음 → 주문 조회 → 배송사 → 규정 검색, 순서대로.
  • 판단 : 하위 질의가 독립이면 쪼개기, 앞 결과가 뒤 검색어를 정하면 다단계.
  • 등급 : 업계 일반 (쪼개기·다단계 원리 자체는 확인 — Research 글)
  • 근거 : multi-agent-research-system en 33·44·52줄

4. 테넌트 필터를 검색 뒤에 걸면

  • 조건 : 테넌트 50곳의 문서를 한 index(색인)에 두고, 상위 20개를 뽑은 뒤 내 테넌트 것만 남김.
  • 계산 : 관련도가 테넌트와 무관하게 고르게 퍼져 있다고 두면, 상위 20개 중 내 테넌트 몫은 평균 20 ÷ 50 = 0.4개 → 대부분 빈손. 검색 전에 필터(또는 테넌트별 네임스페이스)를 걸어야 상위 20개가 전부 내 것.
  • 판단 : 권한 필터는 보안(남의 문서가 컨텍스트에 들어가지 않게)과 재현율 둘 다 때문에 검색 단계에서.
  • 등급 : 계산 (균등 분포 가정) · 필터 위치 원칙은 업계 일반
  • 근거 : — (공식 RAG 글에 없음)

오답 왜 끌리나 왜 틀리나 등급 근거
"모든 질문에 가장 무거운 다단계 에이전트 검색" 가장 강력한 방법이면 다 잡을 것 같음 노력은 복잡도에 맞춤. 초기 실패 = 간단한 질문에 하위 에이전트 50개 ✓ 확인 multi-agent-research-system en 41·45줄
"파이프라인 하나로 통일해야 운영이 쉽다" 운영 단순화 습관 뚜렷이 갈리는 입력을 한 경로로 몰면 서로 성능을 깎음 ✓ 확인 building-effective-agents en 70줄
"분류가 애매해도 일단 routing" 나누면 전문화될 것 같음 조건이 '분류가 정확할 때'. 잘못 보낸 질문은 전용 경로에서 틀림 ✓ 확인 (조건) building-effective-agents en 76줄
"쉬운 질문도 가장 강한 모델로 (품질 우선)" 품질이 걱정됨 공식 예가 바로 쉬운 질문 → 작은 모델 routing ✓ 확인 building-effective-agents en 81줄
"권한 없는 문서는 답을 만든 뒤 걸러냄" 후처리가 쉬워 보임 가져오는 순간 컨텍스트에 들어감 + 상위 K 가 비어 버림 업계 일반 · 계산 뒤집히는 때 4
"비교 질문도 한 번에 검색" 질문이 한 문장이라서 한 질의로는 양쪽 chunk 가 다 안 올 수 있음 업계 일반 뒤집히는 때 3

미해결

  1. 쪼개기·다단계의 공식 근거는 Research(멀티 에이전트 웹 검색) 글이다. 단일 RAG 파이프라인 안의 query decomposition(질의 분해)을 다룬 Anthropic 문서는 못 찾음 (검색 범위 = 받아 둔 raw 원문 전체).
  2. 메타데이터 필터·네임스페이스 : 받아 둔 공식 원문에서 검색 단계 권한 필터 문장을 못 찾음(grep "metadata filter|tenant|namespace" — 걸린 파일은 MCP 인증(authentication)·SDK 배포 문서뿐, RAG 맥락 아님) → 업계 일반.
  3. 목록 3.6② 는 쪼개기·다단계를 "일반 관행 — 근거 확인 필요"로 적었음 → Research 글로 원리 확인, 등급 올림(적용 예는 업계 일반 유지).

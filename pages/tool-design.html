한눈에

도구는 API 엔드포인트를 그대로 감싸는 게 아니라 에이전트가 실제로 하는 **업무 단위**로 만듦. 도구가 많고 겹칠수록 고르기가 흔들리고 정의가 컨텍스트를 먹음 ✓ 확인

ELI5

공구함에 드라이버가 스무 개 있으면 맞는 걸 고르다 틀려요.

  • 자주 하는 일마다 "그 일 하는 공구" 하나면 편해요.
  • 공구마다 이름표를 붙이면 헷갈리지 않아요.
  • 이름표에 "언제 쓰고 언제 안 쓰는지"도 적어요.
  • 공구가 너무 많으면 필요할 때 꺼내 오는 방법을 써요.

개념 설명

원리

에이전트는 사람 개발자가 아님

  • 개발자용 API 는 엔드포인트가 잘게 나뉘어도 괜찮음 — 코드는 목록 전체를 공짜로 훑음.
  • 에이전트는 컨텍스트가 한정. list_contacts 가 전부 돌려주면 토큰마다 읽어야 함 → 낭비. 그래서 "찾기" 도구가 나음.
  • 에이전트는 도구 이름·설명을 읽고 고름. 도구가 많고 겹칠수록 고르기가 흔들림. 30~50개 넘으면 떨어짐.

합치기가 두 가지를 줄임

  • 도구 개수·설명 길이(= 컨텍스트) 가 줄고, 여러 단계 호출의 중간 결과를 에이전트 컨텍스트가 아니라 도구 안에서 처리.
  • 공식 말 : 도구 이름이 일의 자연스러운 나눔을 따르면 실수 위험이 줄어듦.

경계 긋기

  • 합쳐도 서비스가 여럿이면 이름이 겹침(search 가 셋) → 서비스·자원 접두사.
  • 설명은 신입에게 설명하듯. 언제 안 쓰는지, 무엇을 안 돌려주는지까지.

응답이 곧 다음 컨텍스트

  • 도구 응답이 그대로 다음 턴 입력 → 긴 응답은 비용·혼란. 쓸모 큰 정보(high signal) 필드만 · 페이지 · 자르기 · 짧게/길게 선택.

나머지 규칙

  1. ④

    응답도 설계 : 쓸모 큰 정보(high signal)만(uuid·mime_type 대신 name·file_type) · 긴 응답은 페이지·필터·자르기 + 기본값 · Claude Code 는 도구 응답 기본 25,000토큰 상한 · 오류는 고칠 방법을 말하는 문장으로 ✓ 확인

    response_format enum(concise/detailed) — 공식 예 206 → 72토큰(약 ⅓) ✓ 확인

규칙 원문 ①②③⑤⑥ (갈림길로 그린 규칙)
  1. ①

    적게, 업무 단위로 합치기 ✓ 확인 [3.1②]

    list_users·list_events·create_event → schedule_event (빈 시간 찾기 + 예약)

    read_logs → search_logs (관련 줄 + 주변만)

    get_customer_by_id·list_transactions·list_notes → get_customer_context

    list_contacts(전부 반환) → search_contacts

    docs 식 : create_pr·review_pr·merge_pr → action 파라미터 가진 도구 하나

  2. ②

    이름으로 경계 = 네임스페이스(namespacing) : 서비스·자원 접두사 — asana_search·jira_search / asana_projects_search. 접두 vs 접미는 모델마다 효과가 달라 eval 로 고름 ✓ 확인

  3. ③

    설명이 제일 큰 lever(손잡이) : 무엇을 하나 · 언제 쓰고 언제 안 쓰나 · 파라미터 뜻 · 못 돌려주는 것. 도구당 최소 3~4문장. 파라미터 이름은 모호하지 않게(user → user_id) ✓ 확인

    합치기 ≠ 설명 고치기 : 도구 기능이 겹치거나 목적이 모호하면 에이전트가 헷갈림 ✓ 확인 → 합쳐도 설명이 모호한 채면 그대로. 목록이 작으면(10개 미만) 설명 보강이 먼저 (순서는 추론)

  4. ⑤

    개수 문턱 : 30~50개를 넘으면 고르기 정확도가 떨어짐. 합쳐도 많으면 → ◆ 도구 미리 싣기 vs tool search ✓ 확인

  5. ⑥

    고치는 순서 : 프로토타입 → 실제 업무 같은 eval 과제(도구 여러 번 부르는) → transcript·호출 수·오류 보고 수정 → 따로 떼어 둔(held-out) 평가 세트로 과적합 확인 ✓ 확인

    중복 호출 많음 = 페이지·토큰 한도 조정 / 파라미터 오류 많음 = 설명·예시 보강 ✓ 확인

연습 문제

상담 에이전트에 CRM API 엔드포인트마다 도구를 하나씩, 24개를 붙였다. get_customer_by_id · list_transactions · list_notes 처럼 비슷한 도구를 번갈아 잘못 부른다겹치는 도구. 실제 상담 업무 단위로 묶으면 8개쯤으로 줄어든다합치면 적음. 팀은 도구를 더 쪼개고 설명을 길게 쓰자고 한다. 무엇을 할까?

시험 대비

함정

  • ≠"비슷한 도구를 번갈아 잘못 부른다 → 엔드포인트마다 더 쪼개고 설명을 길게" → 도구가 늘면 더 헷갈림. 합치기 + 네임스페이스 ✓ 확인
  • ≠"작게 쪼갤수록 재사용·권한 관리에 좋다(유닉스 철학)" → 에이전트는 컨텍스트가 한정. 전부 돌려주는 list_* 는 낭비 ✓ 확인
  • ≠"모든 걸 하는 mega tool 하나" → 공식은 "목적이 뚜렷한 도구를 업무 단위로"까지. 하나로 몰기 근거 없음 (목록 영상 요령 — 공식 근거 없음)
  • ≠"더 큰 모델로 바꾸면 덜 헷갈림" → 고르기는 이름·설명을 보고 함. 경계부터 업계 일반 CCA-F 노트 2.1 같은 함정
  • ≠Skilljar 는 "hyper-specialized 말고 reasonably abstract 한(bash·read 같은 범용) 도구"를 권함 → 합치기와 반대 같지만 둘 다 "엔드포인트마다 좁은 도구 금지". 열린 과제(코딩) = 조합 가능한 범용 도구, 정해진 업무 = 업무 단위 도구 (가르는 해석은 업계 일반)

신호

"More tools don’t always lead to better outcomes."

"Instead of implementing a list_users, list_events, and create_event tools, consider implementing a schedule_event tool which finds availability and schedules an event."

"Too many tools or overlapping tools can also distract agents from pursuing efficient strategies."

"Namespacing (grouping related tools under common prefixes) can help delineate boundaries between lots of tools"

"Consolidate related operations into fewer tools." (docs define-tools)

"Claude's ability to pick the right tool degrades once you exceed 30–50 available tools." (docs tool-search)

"The key insight for building effective agents is providing reasonably abstract tools rather than hyper-specialized ones." (Skilljar)

뒤집히는 때

1. 합치기가 최소 권한(least privilege)과 부딪히는 때

  • 조건 : ticket 도구 하나에 action = read·draft·refund 를 합쳤다. 상담원 역할은 read·draft 만.
  • 판단 : 합친 도구를 주면 refund 도 따라옴. 권한 경계가 다른 동작은 합치지 말고 나눠 둬야 "역할에 필요 없는 도구 제거"가 가능.
  • 등급 : 업계 일반 (공식 권고 둘을 같이 쓸 때의 추론)
  • 근거 : define-tools en 43줄 · 가이드 샘플 1

2. 범용 도구가 맞는 때

  • 조건 : 코딩·리서치처럼 단계를 미리 못 정하는 에이전트.
  • 판단 : 업무 단위 도구를 미리 다 만들 수 없음. bash·read·edit 같은 범용·조합 가능 도구가 공식(Skilljar)이 드는 모양. 둘 다 "엔드포인트마다 좁은 도구"는 거부.
  • 등급 : 확인(Skilljar 문장) · 가르는 기준은 업계 일반
  • 근거 : Skilljar API 287803 · writing-tools en 134줄 "subdivide and solve tasks in much the same way that a human would"

3. 응답을 줄이면 얼마나 아끼나

  • 조건 : 스레드 조회 도구가 한 작업에서 25번 불림.
  • 계산 : 공식 예의 detailed 206토큰 / concise 72토큰 → 25번이면 5,150 vs 1,800토큰. 차이 3,350토큰이 매 턴 뒤쪽 입력에 쌓임.
  • 전제 : 호출마다 응답 크기가 공식 예와 같다고 봄 · ID 가 필요한 후속 호출이 없을 때만 concise.
  • 등급 : 계산
  • 근거 : writing-tools en 165·171·175줄

4. 설명을 길게 쓰는 게 답이 되는 때

  • 조건 : 도구는 이미 적고 겹치지 않는데, 파라미터를 자꾸 틀리게 채움.
  • 판단 : 이때는 합치기·쪼개기가 아니라 설명·예시 보강이 답. "더 길게 설명" 보기가 오답인 건 도구를 늘리며 설명으로 구분하려 할 때.
  • 등급 : ✓ 확인
  • 근거 : writing-tools en 100·211줄 · define-tools en 37·42줄

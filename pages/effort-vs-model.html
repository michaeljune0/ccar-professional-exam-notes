먼저 effort : 같은 모델에서 effort 를 2~3단계 훑어(sweep) eval 곡선을 봄. 모델 바꾸기보다 나은 경우가 많고, 대부분의 워크로드는 여기서 끝남 ✓ 확인

  • 비용 높음 · 품질은 충분 → 지금 모델에서 effort 를 한 단계씩 낮춰 가며 시험(sweep) ✓ 확인
  • 품질 모자람 → 낮췄던 effort 를 되돌림. 아니면 한 단계 위 모델을 low effort 로 ✓ 확인 · Opus 5.5 는 xhigh·max 도 모자랄 때 Fable 5.1 ✓ 확인
  • 결과를 검사할 수 있음(테스트·검증기) → 전부 low 로 돌리고 실패만 high 로 재실행. 통과율은 유지, 비용 약 절반 ✓ 확인 (실패한 건은 두 번 도는 만큼 지연(latency)이 늘어남)
  • effort 미지원 모델(Haiku 4.5) → 이 lever(손잡이)가 없음. thinking 양은 ■ 모델별 thinking 제어 · 모자라면 모델 교체 업계 일반
  • 요청 난이도가 섞임 → 조합 : 싼 모델 + 최상위 모델로 대부분의 토큰을 싼 단가로, 프런티어 지능은 중요한 곳에만 ✓ 확인
    • 입력 종류가 뚜렷이 갈리고 분류가 정확 → routing(라우팅). 쉬운 질문 = 작은 모델, 어려운 질문 = 강한 모델 (■ 워크플로 5패턴) ✓ 확인
    • 한 줄기인데 군데군데 어려움(코딩 에이전트 · 다단계 연구) → 자문가(advisor) : 싼 실행자가 루프를 돌고 어려운 결정만 최상위에 물음. 최상위 모델 비용은 자문할 때만 듦 ✓ 확인
    • 서로 독립인 조각이 많음, 특히 창 하나를 넘음 → orchestrator-workers(지휘자-일꾼) : 최상위가 계획·합침, worker 가 대량 작업 (■ orchestrator-worker 위임) ✓ 확인
  • 섞이지 않음(난이도가 고름 · 한 줄기 의존 체인) · 단발 Q&A 에 자문가 → 잘 맞춘 모델 하나가 대개 나음. 자문가는 계획할 게 없는 단발 Q&A 에 안 맞음 ✓ 확인

조합을 짓기 전 기준선 : 더 강한 모델 하나를 low effort 로 돌린 비용. 조합은 단일 모델의 effort 곡선 전체를 이겨야 함 ✓ 확인

  • effort 값 (2026-09-28 조회) ✓ 확인 : 요청의 output_config.effort = low·medium·high·xhigh·max. 기본 = 대부분 high · Opus 5.5 는 medium · Haiku 4.5 는 미지원. 모든 출력 토큰(텍스트·도구 호출·thinking)에 걸림
  • 시험 뒤 변경 Opus 5.5 기본 medium 2026-09-22 · xhigh 는 2026-04-16 Opus 4.7 부터
  • 캐시 쓰는 대화 중간에 요청 단위(top-level) effort 를 바꾸면 캐시가 깨짐 → 워크로드 단위로 바꾸거나 메시지별 effort(베타). 속도용 effort = ■ 지연 줄이기 lever

함정

  • ≠"Opus 에서 Sonnet 으로 통째로 내림" → effort 낮추기를 건너뜀. 먼저 지금 모델에서 effort sweep ✓ 확인
  • ≠"모자라니 바로 Fable 로 올림" → 한 단계 위 모델을 low effort 로 · Opus 5.5 는 xhigh·max 가 먼저 ✓ 확인
  • ≠"조합(자문가·orchestrator)이 모델 하나보다 항상 쌈" → 같은 모델을 낮은 effort 로 돌린 게 더 쌌던 경우가 많음 ✓ 확인
  • ≠"사내 Q&A 에 자문가를 붙인다" → 계획할 게 없는 단발 Q&A 엔 안 맞음. 쉬운/어려운 질문이 뚜렷이 갈리면 routing ✓ 확인
  • ≠자문가를 붙이고 실행자 effort 를 낮춤 → 막힌 걸 못 알아채 자문이 끊기고 실행자 혼자보다 점수가 낮아질 수 있음 ✓ 확인
  • ≠Opus 5 설정을 그대로 Opus 5.5 로 → effort 를 생략하면 기본 medium 이라 한 단계 낮게 돎. 옛 설정을 옮기지 말고 effort sweep 다시 ✓ 확인
  • ≠Haiku 4.5 문항에 "effort 를 낮춘다" → 미지원 ✓ 확인
  • ≠"어려운 일이니 무조건 high" → 어려워도 effort 가 점수를 못 올리는 워크로드가 있음. 곡선을 재 봐야 알 수 있음 ✓ 확인
  • ≠adaptive 를 effort 값으로 → thinking 모드이지 effort 단계가 아님 ✓ 확인

ELI5

자전거로 언덕을 못 오르면 자전거를 새로 사기 전에 기어부터 바꿔 봐요.

  • 기어를 바꾸는 건 공짜고 금방 해 볼 수 있어요.
  • 기어를 다 바꿔도 안 되면 그때 더 좋은 자전거를 사요.
  • 길 대부분이 평지고 언덕이 가끔이면, 언덕에서만 힘센 친구에게 밀어 달라고 해요.
  • 그런데 친구를 불러야 할 때 안 부르면 소용없어요.

원리

effort 가 하는 일

  • 한 모델 안에서 지능 ↔ 지연(latency)·비용을 맞바꾸는 lever(손잡이). 요청의 output_config.effort (2026-09-28 조회).
  • 모든 출력 토큰에 걸림 : 텍스트 · 도구 호출 · thinking(사고). 낮추면 도구 호출도 적고 짧아짐. adaptive thinking 에선 얼마나 자주·깊게 생각할지도 정함.
  • 비용은 모델이 하는 일(thinking·도구 호출·자기 검증)에 비례하고, 정확도는 과제가 필요로 하는 만큼만 오름 → 모델 한계 아래에서 높은 effort 는 과제가 안 쓰는 깊이에 비용을 치름.

왜 effort 가 먼저인가

  • 가장 싼 실험이고, 대부분의 워크로드는 여기서 끝남.
  • 공식 측정에서 "기본 설정 모델 하나보다 싸 보였던 다중 모델 구성"이 같은 모델을 낮은 effort 로 돌린 것보다 비쌌음. 한 벤치마크에선 low 가 Sonnet 5 worker(일꾼)를 둔 orchestrator(지휘자) 구성과 같은 점수를 29% 싸게 냄 → "effort 낮추기가 구조 변경을 이김".

곡선 모양은 워크로드마다 다름 (Anthropic 내부 측정, 방향성)

  • 연구·지식 작업 : 거의 평평. low 는 1~3점 손해에 과제당 비용 3분의 1~절반 절감(원래 비용의 절반~3분의 2 만 듦), medium 은 기본과 같은 정확도에 비용 70~87%.
  • 긴 코딩 : 가파름. Opus 5.5 는 high 대비 medium(기본) 약 −2.5점 · 비용 약 70%, low 약 −8점 · 비용 약 3분의 1(약 3분의 2 절감), xhigh 약 +1.4점 · 2.5배.
  • 그래서 과제 설명만으론 어느 쪽인지 모름 → 2~3단계를 자기 트래픽 표본으로 재고, 단계마다 세션을 따로 (중간에 바꾸면 캐시가 깨져 비교가 흐려짐).

모델 조합은 "섞임"이 있을 때만

  • 쉬운 일과 어려운 일이 섞여 있으면 : 프런티어 지능은 어려운 곳에만, 대부분의 토큰은 싼 모델 단가로.
  • 섞임이 없으면(난이도가 고름 · 한 줄기 의존 체인) : 잘 맞춘 모델 하나가 대개 나음.
  • 두 전략 (누가 루프를 쥐나)
  • 자문가(advisor) : 싼 실행자가 루프, 막히면 최상위에 물음. 이득은 "모델 격차"와 "실행자가 실제로 묻는 비율(자문 비율)"이 정함.

  • orchestrator : 최상위가 루프, 계획·분배·합침. worker 가 대량 탐색을 흡수. 넘길 대량 작업(독립 조각 · 창 하나 초과)이 있어야 쓸 만함.

  • routing(라우팅) : 입력을 분류해 쉬운 질문은 작은 모델, 어려운 질문은 강한 모델로. 뚜렷한 범주 + 정확한 분류가 조건 (■ 워크플로 5패턴).

뒤집히는 때

1. 조합이 effort 낮추기를 이기는 때 — 창 하나를 넘는 입력

  • 조건 : 입력이 어떤 컨텍스트 창에도 안 들어감.
  • 판단 : 이때 청구액은 입력을 "읽는 비용" 자체라 effort 를 낮춰도 안 줄어듦. 공식 측정(2,160만 토큰 코드 묶음)에서 Fable 5.1 단독은 effort 셋 모두 에피소드당 $468~$552, orchestrator(Fable 5.1) + worker(Sonnet 5) 25개 구성은 약 절반 비용에 10~12점 낮고, 걸린 시간은 약 2.3시간 vs 15~20시간.
  • 등급 : ✓ 확인 (Anthropic 내부 측정)
  • 근거 : optimizing 502·516줄

2. 자문가가 손해인 때 — 자문 비율

  • 조건 : 자문가를 붙였는데 실행자가 너무 적게 또는 너무 많이 물음.
  • 너무 적게 : Opus 5.5 low 실행자 + Fable 5.1 자문가가 300개 중 1개만 물어 Opus 5.5 단독보다 7점 낮았음 (확인).
  • 너무 많이 : 식 = 조합 과제당 비용 = 실행자 비용 + 자문 비율 × 자문 횟수 × 자문 1회 비용. 예 : 실행자 $0.30 · 자문 1회 $0.20 · 물을 땐 3회 · 강한 모델 단독 low = $0.66 → 손익 자문 비율 = (0.66 − 0.30) ÷ (3 × 0.20) = 60%. 60% 넘게 물으면 강한 모델 단독이 쌈.
  • 전제 : 자문을 받아 실행자가 아끼는 토큰은 뺌(공식은 일부 상쇄된다고 함). 숫자는 가정.
  • 등급 : 계산 (현상은 확인)
  • 근거 : optimizing 480·488줄

3. 실패 재실행이 안 맞는 때

  • 조건 : 결과를 기계적으로 검사할 수 없거나, 검사기가 나쁜 결과를 통과시킴.
  • 식 : 과제당 비용 = low 1회 비용 + 실패율 × high 1회 비용. 예 : low $0.08 · high $0.25 · 실패율 25% → 0.08 + 0.0625 ≈ $0.14 (전부 high $0.25 대비 약 43% 절감). 손익 실패율 = (0.25 − 0.08) ÷ 0.25 = 68%.
  • 판단 : 실패 신호가 없으면 성립 안 함. 실패 건은 두 번 도는 시간이라 지연 목표가 빡빡하면 불리.
  • 등급 : 계산 (조건 두 개는 확인)
  • 근거 : optimizing 294~300줄

4. 어려운 일이니 high? — 안 오르는 워크로드

  • 조건 : 과제가 어려워 보여 effort 를 올림.
  • 판단 : 공식 측정에서 Fable 5.1 은 긴 연구 과제에서 low·medium·high 점수가 거의 같고 과제당 비용만 $4.66 → $7.12. 어려움 ≠ 높은 effort. 곡선을 재 봐야 알 수 있음.
  • 등급 : ✓ 확인
  • 근거 : optimizing 286줄

5. 대화 중간에 effort 를 바꿔 아끼려는 때

  • 조건 : 긴 캐시 대화 도중 요청 단위 effort 를 낮춤.
  • 판단 : 요청 단위 effort 변경은 그 지점부터 캐시를 깸. 10만 토큰 앞부분 기준으로 한 번 깨질 때 Opus 5.5 = $0.50 vs 읽기 $0.02 (25배), Fable 5.1 = $1.25 vs $0.03 (50배). 지원 모델이면 메시지별 effort(베타)가 캐시를 지킴.
  • 등급 : ✓ 확인
  • 근거 : optimizing 119줄 · effort 136~152줄

미해결

  1. 목록 2.1② 의 정답 규칙은 섞인 요청의 예로 "자문가 위임·지휘자-일꾼"을 들었고 문제 상황은 "사내 Q&A" 였음 → 공식은 자문가가 단발 Q&A 에 안 맞고 orchestrator 는 대량 조각이 있어야 한다고 씀. 카드는 routing · 모델 하나로 고침.
  2. 가이드(2026-07) 시점엔 Opus 5.5 가 없었음 → "기본 effort = medium" 은 시험 뒤 변경(2026-09-22). 시험이 기본값을 물으면 "대부분 high" 가 안전 (추론).
  3. routing 공식 예문의 모델명은 Haiku 4.5 ↔ Sonnet 4.5 (옛 이름, building-effective-agents 81줄). 현행 이름으로 된 routing 예문은 못 찾음.
  4. 공식 문장은 "often"(자주) — effort 가 늘 먼저라는 뜻은 아님. Haiku 4.5(effort 없음) · 창 초과 · 곡선이 이미 한계인 경우엔 모델 교체가 맞는 답일 수 있음. 어느 신호에서 시험이 교체를 정답으로 삼는지는 공식 샘플에 없음.
  5. 측정 수치는 모두 Anthropic 내부 벤치마크 · 방향성 (optimizing 33줄).
  6. 목록 영어 신호 2개("Tuning effort…" · "Multi-model strategies…")는 원문에서 모두 찾음 — 못 찾은 인용 없음.

규칙 원문 ①②③ (갈림길로 그린 규칙)
  1. ①

    확장 사다리 (단순 → 복잡) : 단일 보강 호출(augmented LLM — 검색·도구·메모리를 붙인 LLM 한 번) → 워크플로(코드가 정한 경로) → 에이전트(모델이 스스로 경로를 정함) → 멀티 에이전트. 가장 단순한 칸부터 보고 처음 되는 칸에서 멈춤 ✓ 확인 [1.3③]

    흔한 질문이 대부분이면 → 검색·예시를 붙인 단일 호출이면 대개 충분 ✓ 확인

    워크플로 = 잘 정의된 일엔 예측 가능·일관성 · 에이전트 = 유연성과 모델 주도 결정이 규모 있게 필요할 때 ✓ 확인

    에이전트 하나 = 단계 수를 미리 알 수 없고 고정 경로를 코드에 박아 둘 수 없는 열린 문제 ✓ 확인 · 멀티는 ◆ 단일 vs 멀티 에이전트 ✓ 확인

    사다리 칸 이름은 이 카드의 해석 (공식 = augmented LLM 에서 워크플로·에이전트로 "점점 복잡도를 올리는" 순서) ✓ 확인

  2. ②

    한 칸 올리는 조건 : 결과가 눈에 띄게 나아질 때만 복잡도 추가 · 단순한 방법이 모자랄 때만 여러 단계 에이전트 ✓ 확인 [1.3③]

    워크플로로 되면 워크플로, 에이전트는 정말 필요할 때만 — 워크플로가 테스트·평가가 쉽고 예측 가능 ✓ 확인 (Skilljar)

    에이전트 칸으로 올리면 : 비용↑ · 오류가 쌓임 → 샌드박스에서 충분히 시험 + 가드레일 + 멈춤 조건(최대 반복 수) ✓ 확인

    프레임워크 : 직접 API 로 시작(많은 패턴이 몇 줄). 프레임워크는 프롬프트·응답을 가려 디버깅이 어렵고 복잡도를 더하고 싶게 만듦. 쓰면 밑단 코드를 이해할 것 — 밑단이 어떻게 도는지 잘못 아는 것이 흔한 고객 오류 원인 · 프로덕션으로 갈수록 추상화 층을 줄여도 됨 ✓ 확인 → ◆ 직접 API vs Agent SDK vs CLI vs Managed Agents

  3. ③

    자율성 단계 (Claude Code 기본값) : 읽기 전용이 기본, 분석·검토는 승인 없이 → 코드·시스템을 바꾸기 전엔 사람 승인 → 믿을 만한 반복 작업엔 사용자가 지속 권한을 줌 ✓ 확인 [1.3③] [7.3②]

    중요한 결정 전엔 사람이 통제 (예 : 구독 해지 전에 승인) ✓ 확인 · 자율·감독의 균형은 상황마다 크게 다름 ✓ 확인

    제한적으로 시작해 신뢰가 쌓이면 푼다 (Agent SDK : plan 으로 계획 검토 → acceptEdits 로 전환) ✓ 확인

    에이전트는 모델 결정을 어느 정도 믿어야 쓰는 것 · 믿을 수 있는 환경에서 규모 확장에 맞음 ✓ 확인 ("자율 = 권한" 은 이 카드가 붙인 말, 공식은 신뢰·가드레일로 표현)

    투명성(transparency) : 계획을 보이게 (실시간 할 일 목록). 자세함은 중간 — 너무 적으면 판단 불가, 너무 많으면 묻힘 ✓ 확인

    필요 없는 권한은 확인창을 붙이기보다 먼저 없앰 → ■ 최소 권한 ✓ 확인

함정

  • ≠"첫날부터 멀티에이전트 프레임워크" → 단일 보강 호출부터. 몇 달 들인 멀티가 프롬프트 개선한 단일과 같았던 사례 ✓ 확인
  • ≠"강한 모델이니 자율 에이전트가 기본 업그레이드" → 에이전트 = 지연·비용을 내주는 거래 · 오류가 쌓임. 신뢰·가드레일 만큼만 ✓ 확인
  • ≠"나중에 필요할 테니 처음부터 크게" → 결과가 눈에 띄게 나아질 때만 한 칸 ✓ 확인
  • ≠이미 운영에 낸(출시한) 에이전트가 운영(production) 로그에서 거의 늘 같은 도구 순서로 돎 → "도구 설명·프롬프트만 다듬자" 가 아니라 한 칸 내림 : 그 순서를 워크플로로, 예외만 에이전트 (공식 = 복잡도는 결과를 낫게 할 때만 ✓ · 내리는 적용은 이 카드의 해석)
  • ≠"프레임워크를 써야 프로덕션급" → 추상화가 프롬프트·응답을 가림. 프로덕션으로 갈수록 층을 줄여도 됨 ✓ 확인
  • ≠"목표가 맞으니 알아서 해도 됨" → '파일 정리해 줘'에 중복이라 여긴 걸 지우고 구조를 통째로 바꾼 예. 목표가 맞아도 맥락이 모자라 선을 넘음 → 바꾸는 행동 전 승인 ✓ 확인
  • ≠"라우터"를 사다리의 별도 칸으로 외움 → 공식에서 routing(라우팅)은 워크플로 패턴 중 하나 ✓ 확인

  • 우유 한 통이면 걸어가도 돼요.
  • 짐이 많아지면 그때 자전거, 그다음에 트럭이에요.
  • 트럭은 기름값도 들고 사고도 크게 나요.
  • 처음 운전하는 사람에겐 트럭 열쇠를 바로 주지 않아요.

사다리 (단순 → 복잡)

  • 단일 보강 호출 : LLM 한 번 + 검색(retrieval)·도구·메모리. 흔한 질문 대부분은 여기서 끝남.
  • 워크플로 : 코드가 경로를 정함. 예측 가능, 단계마다 검사 가능, 테스트 쉬움.
  • 에이전트 : 모델이 경로를 정함. 단계 수를 미리 모르는 열린 문제용. 대신 비용↑, 오류가 쌓임.
  • 멀티 에이전트 : 에이전트 하나가 못 넘는 제약이 있을 때만 (◆ 단일 vs 멀티 에이전트).
  • 한 칸 올라갈 때마다 지연(latency)·비용을 내고 성능을 얻음. 그래서 "올려서 결과가 나아졌나"를 재야 올림.

자율성 (권한의 사다리)

  • 읽기·분석 → 승인 없이.
  • 바꾸는 행동 → 사람 승인 먼저.
  • 믿을 만한 반복 작업 → 지속 권한.
  • 제한적으로 시작해서 신뢰가 쌓이면 푼다. 필요 없는 권한은 승인 단계를 붙이지 말고 없앤다(■ 최소 권한).

왜 작은 쪽부터인가

  • 단순할수록 디버깅·평가가 쉬움. 프레임워크·에이전트는 프롬프트와 응답을 가려 원인 찾기가 어려워짐.
  • 몇 달 들인 멀티 에이전트가 프롬프트를 고친 단일 에이전트와 같았던 사례가 공식 글에 있음.

뒤집히는 때

1. "흔한 질문이 대부분"인데 에이전트가 필요한 몫이 있을 때

  • 조건 : 월 티켓 7,300건 중 83% 는 흔한 질문, 17% 는 원인 조사(여러 시스템을 뒤져 봐야 함).
  • 계산 : 채팅 1회 = 1 단위로 두면 에이전트 ≈ 4 단위 (연구 글 : 에이전트는 채팅의 약 4배 토큰). 전부 에이전트 = 7,300 × 4 = 29,200 단위. 나눠 쓰면 6,059 × 1 + 1,241 × 4 = 11,023 단위 → 약 38%.
  • 전제 : 단일 보강 호출 1회 ≈ 채팅 1회로 봄(추론) · 4배는 연구 글의 평균 관측치 · 분류(라우팅) 비용은 뺌.
  • 판단 : "대부분 흔한 질문"이 "에이전트 금지"는 아님. 흔한 몫은 가장 작은 칸, 조사 몫만 한 칸 올림. 둘을 가르는 건 routing(라우팅) 워크플로(■ 워크플로 5패턴).
  • 등급 : 계산 (배수는 확인)
  • 근거 : multi-agent-research-system en 21줄 · building-effective-agents en 20·81줄

2. 멀티 에이전트가 첫 설계로 맞는 때

  • 조건 : 서로 독립인 방향 여러 개를 동시에 넓게 파야 하고(예 : 경쟁사 11곳 공개 자료를 각각 조사), 작업 가치가 높음.
  • 판단 : 이건 "처음부터 크게"가 아니라 단일 에이전트가 못 넘는 제약(병렬 · 컨텍스트 창 하나를 넘는 정보)이 있는 경우. 사다리 규칙은 그대로 — 그 제약이 있는지를 먼저 봄. 판정은 ◆ 단일 vs 멀티 에이전트.
  • 계산 : 멀티 ≈ 15 단위(채팅 대비). 한 건 가치가 그 비용을 넘어야 함.
  • 등급 : ✓ 확인 (제약 · 배수) · 예시는 새로 고른 것
  • 근거 : multi-agent-research-system en 21줄 · building-multi-agent-systems en 366줄

3. 승인 단계가 병목이 될 때

  • 조건 : 사람 승인을 붙였더니 같은 종류 요청(예 : 주문 상태 메모 갱신)이 하루 240건 쌓임.
  • 판단 : 믿을 만한 반복 작업은 지속 권한으로 풀고, 해지·환불처럼 중요한 결정만 승인에 남김. "승인은 무조건 많을수록 안전"이 아님.
  • 등급 : ✓ 확인 (지속 권한 · 중요한 결정 전 통제(control)) · 승인을 빈도가 아니라 피해 범위로 거는 규칙 문장 자체는 공식에 없음(미해결 3)
  • 근거 : safe-trustworthy-agents en 17·19·21줄 · agent-sdk-permissions en 361줄

4. 프레임워크로 시작해도 되는 때

  • 조건 : 팀이 이미 Agent SDK 류를 알고 있고, 빨리 시제품을 띄워야 함.
  • 판단 : 공식도 "프레임워크는 시작을 빠르게 해 준다"고 인정. 조건은 밑단 코드를 이해하는 것, 프로덕션으로 가며 추상화 층을 줄이는 것.
  • 등급 : ✓ 확인
  • 근거 : building-effective-agents en 31·33·174줄

미해결

  1. 목록의 사다리는 "단일 보강 호출 → 라우터 → 워크플로 → 에이전트" 로 라우터를 별도 칸으로 뒀음. 공식에선 routing = 워크플로 패턴 중 하나라 카드엔 라우터 칸을 두지 않았음.
  2. 목록의 자율성 단계 이름 "읽기 전용 → 사람 승인 → 높은 자율"은 공식 문장이 아님. 가장 가까운 공식 = Claude Code 기본값(읽기 전용 · 바꾸기 전 승인 · 반복 작업 지속 권한, safe-trustworthy-agents en 19줄). 카드엔 이쪽으로 적음.
  3. "승인은 빈도가 아니라 피해 범위로 건다"(목록 7.3②) — 공식 문장 못 찾음(safe-trustworthy-agents · agent-sdk-permissions 에서 "blast"·"scope"·"high-stakes" 검색). 가까운 공식 = "particularly before high-stakes decisions are made".
  4. building-effective-agents 는 2024-12 글이고 머리에 "도구 환경이 많이 바뀌었다"는 안내가 붙어 있음(en 1줄). 사다리 원칙은 새 글(building-multi-agent-systems en 366줄)도 같음.

갈림 기준

제품이 "한 번 성공"을 원하나 "매번 성공"을 원하나

  • 에이전트 동작은 실행마다 다름 → 한 번 돌려 판단 안 함. 과제마다 여러 번 시도(trial) ✓ 확인
  • pass@k = k번 시도 중 적어도 한 번 맞을 확률. 하나만 되면 되는 도구에 · 여러 해답을 내고 하나만 맞으면 되는 일에 ✓ 확인
  • pass^k = k번 모두 맞을 확률. 일관성이 핵심인 에이전트에 · 사용자가 매번 믿을 만한 동작을 기대하는 고객 대면 에이전트에 특히 ✓ 확인
  • 코딩은 첫 시도 해결 = pass@1 을 가장 중시 ✓ 확인
  • 둘 다 쓸모 있음. 고르는 기준은 제품 요구 ✓ 확인

셈 ✓ 확인

  • pass^k = p^k (1회 성공률 p) : 75% · 3번 → (0.75)³ ≈ 42% ✓ 확인
  • pass@k = 1 − (1 − p)^k : 75% · 3번 → 1 − 0.25³ ≈ 98% (계산 — 공식은 식 없이 정의만, 시도 독립 가정)
  • k = 1 이면 둘 다 1회 성공률 · k = 10 이면 pass@k → 100%, pass^k → 0% ✓ 확인
  • "50% pass@1" = 첫 시도에 과제 절반을 성공 ✓ 확인

시도 믿기 ✓ 확인 (과제·환경 만들기 본문 = ■ 첫 eval 셋 만들기)

  • 시도마다 깨끗한 환경에서 시작. 남은 파일 · 캐시 데이터 · 자원 고갈 같은 공유 상태 → 에이전트가 아니라 인프라 때문에 같이 실패(독립 아님). 앞 시도의 git 기록을 보고 점수가 부풀기도 함
  • 프런티어 모델이 여러 시도에서 0%(0% pass@100) → 대개 과제가 고장. 과제 명세·grader 확인, 과제마다 참고 해답(reference solution)

함정

  • ≠재시도 없는 고객 대면 에이전트를 pass@k 로 → 높게 나와 신뢰성을 과대평가. pass^k ✓ 확인
  • ≠"몇 번 돌려 한 번 되면 됐다" → 그건 pass@k. 매번 돼야 하면 pass^k ✓ 확인
  • ≠실행 1회 정확도로 판단 → 실행마다 달라서 여러 번 시도 ✓ 확인
  • ≠pass^k 를 "k번의 평균 성공률"로 읽음 → 모두 성공할 확률, k 가 커질수록 내려감 ✓ 확인
  • ≠"pass@k 가 올랐으니 에이전트가 좋아졌다" → k 만 늘려도 오름 ✓ 확인
  • ≠신뢰성을 물었는데 TTFT 같은 지연(latency) 지표를 고름 → 다른 차원 (◆ TTFT vs 응답 완료 지연)
  • ≠0% pass@100 을 "모델이 못 한다"로 → 과제 고장부터 ✓ 확인

ELI5

농구 자유투를 떠올려 보세요.

  • "세 번 던져서 한 번만 들어가면 돼"는 쉬운 시험이에요.
  • "세 번 던져서 세 번 다 들어가야 해"는 어려운 시험이에요.
  • 같은 선수여도 어떤 시험이냐에 따라 점수가 크게 달라요.
  • 손님을 상대하는 일은 매번 들어가야 하는 쪽이에요.

원리

왜 여러 번 돌리나

  • 에이전트는 같은 과제도 실행마다 결과가 다름. 한 번 통과한 과제가 다음엔 실패할 수 있음.
  • 그래서 과제마다 여러 번 시도(trial)하고, "얼마나 자주" 성공하는지를 봄.
  • 과제마다 성공률도 다름(어떤 건 90%, 어떤 건 50%).

두 지표

  • pass@k : k번 중 적어도 한 번 성공할 확률. k 가 커질수록 오름("슛 기회"가 많을수록).
  • pass^k : k번 모두 성공할 확률. k 가 커질수록 내림(일관성 요구가 커짐).
  • k = 1 이면 둘 다 1회 성공률로 같음. k = 10 이면 pass@k 는 100% 쪽, pass^k 는 0% 쪽 — 정반대 이야기를 함.

고르는 기준 = 제품 요구

  • 후보를 여러 개 내고 하나만 맞으면 되는 일 → pass@k.
  • 사용자가 매번 믿을 만한 동작을 기대하는 고객 대면 에이전트 → pass^k.
  • 코딩은 첫 시도 해결(pass@1)을 가장 중시.

숫자가 믿을 만하려면

  • 시도가 서로 독립이어야 함. 깨끗한 환경에서 시작하지 않으면 남은 파일·캐시·자원 고갈로 같이 실패하거나, 앞 시도의 흔적을 보고 점수가 부풂.
  • 프런티어 모델이 여러 번 다 0% 면 대개 과제가 고장.

핵심 질문 두 개

  • 사용자(또는 다음 단계)가 받는 건 k번 중 가장 좋은 하나인가, 매번의 결과인가?
  • 이 k번은 서로 독립인가?

뒤집히는 때

1. 고객 대면인데 pass@k 가 설 자리가 있는 때

  • 조건 : 에이전트가 사용자에게 내보내기 전에 결과를 자동으로 검사할 수 있음(예 : 환불 금액이 규칙 범위 안인지, 응답이 스키마를 통과하는지). 실패하면 시스템이 조용히 다시 돌림, 최대 3번. 1회 성공률 70%.
  • 계산 : 사용자가 받는 결과의 성공률 = 1 − 0.3³ = 97.3%. 평균 호출 수 = 1 + 0.3 + 0.09 = 1.39번.
  • 판단 : 사용자가 받는 건 "검사를 통과한 하나"라 pass@3 이 사용자 체감에 가까움. 단 검사기가 성공을 정확히 가려야 하고, 호출 수만큼 비용·지연(latency)이 늚. 검사기가 없으면 원래대로 pass^k.
  • 전제 : 시도 독립 · 검사기 오판 없음.
  • 등급 : 계산 · 업계 일반(공식 글은 이 경우를 말하지 않음)
  • 근거 : demystifying-evals en 203·205·211줄

2. k 를 안 적은 pass^k 목표는 뜻이 없다

  • 조건 : "pass^k 80% 이상"을 목표로 적음. 1회 성공률 90%.
  • 계산 : pass^2 = 0.81 → 통과. pass^5 = 0.9⁵ ≈ 0.59 → 불합격. pass^10 = 0.9¹⁰ ≈ 0.35. 같은 에이전트가 k 에 따라 합격·불합격.
  • 판단 : 기준 문장에 k 를 함께 적어야 함(■ 성공 기준 의 "측정 가능"). 공식 그림도 k 가 커질수록 두 지표가 벌어짐을 보여 줌.
  • 등급 : 계산
  • 근거 : demystifying-evals en 205·209줄

3. 과제 평균 성공률로 pass^k 를 셈하면 틀린다

  • 조건 : 과제 A 성공률 95%, 과제 B 45% (평균 70%). k = 3.
  • 계산 : 평균으로 셈 = 0.7³ ≈ 34%. 과제마다 셈 = (0.95³ + 0.45³) ÷ 2 = (0.857 + 0.091) ÷ 2 ≈ 47%.
  • 판단 : 성공률은 과제마다 다르므로 과제별로 pass^k 를 구한 뒤 평균. 그리고 B 처럼 낮은 과제를 따로 봐야 어디서 깨지는지 보임.
  • 등급 : 계산 (과제마다 성공률이 다르다는 것은 확인)
  • 근거 : demystifying-evals en 199줄

4. 0% 인데 모델 탓이 아닐 때

  • 조건 : 과제 하나가 100번 시도 모두 실패(0% pass@100).
  • 판단 : 프런티어 모델에서 이건 대개 과제 고장 신호 — 과제 설명에 없는 파일 경로를 grader 가 기대하는 식. 모델을 바꾸기 전에 과제 명세 · grader 를 보고, 참고 해답이 grader 를 통과하는지 확인.
  • 등급 : ✓ 확인
  • 근거 : demystifying-evals en 231줄

미해결

  1. 목록 4.1③ 은 pass@k 를 "재시도 가능한 도구", pass^k 를 "재시도 없음"으로 적음. 공식 문장은 "one success matters" · "consistency is essential" · "reliable behavior every time" 이고 "재시도"라는 말은 없음 — 목록의 재시도 표현은 해석.
  2. pass@k 식 1 − (1 − p)^k 는 공식 글에 없음(정의만 있음, 링크된 2019 논문은 받지 않음). 시도 독립 가정.
  3. 목록 4.1③ 의 영어 신호 두 문장은 원문에서 찾음(en 211·205줄). "pass^3 ≈ 42%" · "코딩은 pass@1" 도 확인(en 205·203줄).
  4. 한국어판 없음 (anthropic.com/engineering 글) — 영어 원문만.

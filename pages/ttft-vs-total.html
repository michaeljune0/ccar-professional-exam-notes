상담 기록 요약 파이프라인이 1,800토큰짜리 주간 보고서를 만들면 다음 단계 코드가 통째로 받아 쓴다결과 전체. 팀은 스트리밍을 켜 TTFT 가 1.2초로 좋아졌으니 지연(latency) 문제는 해결됐다고 한다. 지연 목표는 무엇으로 걸어야 할까?

갈림 기준

누가 무엇을 기다리나가 먼저

  • TTFT = 프롬프트를 보낸 뒤 응답 첫 토큰이 나올 때까지. 스트리밍으로 반응성 있는 경험을 줄 때 특히 중요 ✓ 확인
  • 기본 지연(baseline latency) = 모델이 프롬프트를 처리하고 응답을 생성하는 시간(초당 토큰은 따로 안 셈). 공식 지연 문서의 두 지표 = 이것과 TTFT ✓ 확인
  • 응답 완료(time to last token)는 공식 eval 예시가 TTFT · 초당 출력 토큰과 나란히 따로 추적 ✓ 확인
  • 사람이 화면에서 첫 글자를 기다림 → TTFT. 결과 전체를 써야 함(긴 보고서 · 다음 단계 코드) → 응답 완료 지연 업계 일반 공식은 두 지표를 정의만 함
  • 스트리밍 = 출력이 다 끝나기 전에 보내기 시작 → 체감(perceived) 반응성을 크게 올림 ✓ 확인. 생성 토큰 수는 그대로 → 완료 지연도 그대로 (업계 일반, 본문 = ■ 지연 줄이기 lever · 규칙 ①)
  • TTFT 를 좌우 = 모델 크기 · 하드웨어 · 네트워크 · 프롬프트 복잡성 ✓ 확인 / 지연(응답 받기까지)을 좌우 = 여기에 생성된 응답의 복잡성까지 ✓ 확인 → 출력이 길면 완료 지연만 늘어남 업계 일반

쪼개 보기 (OTel GenAI semconv v1.37.0 · 2026-09-28 조회) ✓ 확인

  • gen_ai.server.time_to_first_token = 첫 토큰까지. 대기열과 prefill 단계 시간을 봄, 스트리밍 요청에 특히 중요
  • gen_ai.server.request.duration = 요청 시간, 마지막 출력 토큰(time-to-last byte)까지
  • gen_ai.server.time_per_output_token = (요청 시간 − 첫 토큰 시간) ÷ 첫 토큰 뒤 출력 토큰 수 → decode 단계 성능
  • 그래서 완료 ≈ TTFT + 출력 토큰 수 × 토큰당 시간 (계산 — 위 정의를 거꾸로 푼 식)
  • Claude Code 트레이스 claude_code.llm_request 스팬도 ttft_ms 와 duration_ms(재시도 포함 wall-clock)를 따로 찍음 ✓ 확인

지표 거는 법

  • 지연 = 성공 기준(success criteria)의 한 차원. 받아들일 수 있는 응답 시간은 앱의 실시간 요구와 사용자 기대에 달림 ✓ 확인 → ■ 성공 기준
  • 분위수로 : 공식 예 = 응답 95% 가 200ms 미만 ✓ 확인
  • eval 에서도 따로 추적 : time_to_first_token · output_tokens_per_sec · time_to_last_token ✓ 확인
  • TTFT 를 줄이는 공식 수단 = 캐싱(샘플 2 해설) · 캐시 미리 데우기(pre-warming) ✓ 확인. 완료 지연 쪽 = 출력 길이 · effort · 모델, lever(손잡이) 본문 = ■ 지연 줄이기 lever ✓ 확인
  • 사람이 안 기다리는 배치에는 TTFT 가 해당 없음 : 캐시 미리 데우기(max_tokens: 0)가 Message Batches 에서 거부되는 이유 ✓ 확인

함정

  • ≠"스트리밍을 켰으니 지연 문제 해결" → 체감(TTFT)만. 완료 지연은 그대로 업계 일반
  • ≠"TTFT 하나로 지연 SLO" → 긴 출력의 완료 시간을 못 봄 업계 일반. 공식 eval 예시는 TTFT · 완료를 따로 추적 ✓ 확인
  • ≠"TTFT 가 좋아졌으니 모델 출력이 빨라졌다" → TTFT 는 대기 · 입력 처리 구간, 출력 속도는 토큰당 시간이 따로 ✓ 확인
  • ≠평균 하나로 지연 기준 → 공식 예는 "응답 95% 가 200ms 미만" 처럼 분위수 ✓ 확인
  • ≠결과를 코드가 통째로 받는 파이프라인에 TTFT 목표 → 기다리는 쪽이 코드면 완료 지연이 지표 업계 일반
  • ≠"캐싱은 비용만, 지연과 무관" → TTFT 를 줄임 (샘플 2 해설) ✓ 확인

ELI5

택배를 시켰을 때 "출발했어요" 문자가 빨리 오는 것과, 상자가 집에 다 도착하는 것은 다른 일이에요.

  • 문자가 빨리 오면 덜 답답해요. 이게 첫 글자까지의 시간이에요.
  • 그래도 상자가 늦게 오면 기다리는 건 똑같아요.
  • 상자가 많을수록 다 오는 데 오래 걸려요.
  • 그래서 둘을 따로 재야 어디가 느린지 알아요.

원리

두 지표

  • TTFT : 프롬프트를 보낸 뒤 첫 토큰이 나올 때까지. 대기열 + 입력 처리(prefill) 구간.
  • 응답 완료 : 마지막 토큰까지. TTFT + 출력 토큰을 하나씩 만드는 시간(decode).
  • OTel 정의를 거꾸로 풀면 : 완료 ≈ TTFT + 출력 토큰 수 × 토큰당 시간 (계산).
  • 그래서 TTFT 는 입력 쪽(프롬프트 복잡성 · 모델 · 네트워크)에, 완료는 거기에 출력 길이까지 얹혀 좌우됨. 공식 용어집도 TTFT 요인엔 "프롬프트 복잡성"만, 지연(latency) 요인엔 "생성된 응답의 복잡성"까지 넣음.

스트리밍이 바꾸는 것

  • 출력이 다 끝나기 전에 보내기 시작 → 사용자가 실시간으로 봄 → 체감(perceived) 반응성이 크게 좋아짐.
  • 생성할 토큰 수는 그대로 → 마지막 토큰 시각은 그대로 (업계 일반 — 공식은 "perceived"라고만 씀).
  • 그래서 스트리밍 뒤 "TTFT 는 좋아졌는데 여전히 느리다"는 말이 나옴.

어느 지표를 거나

  • 기다리는 주체가 기준 : 사람이 화면에서 첫 글자를 기다리면 TTFT, 결과 전체가 필요하면(보고서 · 다음 단계 코드) 완료.
  • 대부분 둘 다 따로. 공식 eval 예시도 time_to_first_token · output_tokens_per_sec · time_to_last_token 을 나란히 추적.
  • 숫자는 분위수로 (공식 예 "응답 95% 가 200ms 미만").

핵심 질문 두 개

  • 불만이 "시작이 늦다"인가, "끝이 늦다"인가?
  • 완료 시간에서 TTFT 구간과 출력 구간 중 어느 쪽이 큰가?

뒤집히는 때

1. 출력이 몇 토큰뿐이면 TTFT 가 곧 완료다

  • 조건 : 문의를 5개 라벨 중 하나로 분류. 출력 약 5토큰. TTFT 0.9초, 토큰당 0.02초라 치자(가정값).
  • 계산 : 완료 ≈ 0.9 + 5 × 0.02 = 1.0초. 완료의 90% 가 TTFT 구간.
  • 판단 : 여기선 "TTFT vs 완료"를 가를 필요가 거의 없음. 스트리밍 이득도 작음(보여 줄 게 한 단어). 줄일 곳은 입력 쪽 — 앞부분이 매번 같으면 캐싱, 아니면 모델.
  • 전제 : 가정값 · 토큰당 시간 일정.
  • 등급 : 계산 (식은 OTel 정의에서)
  • 근거 : OTel semconv en 297·372줄 · 가이드 샘플 2 해설

2. 긴 보고서는 TTFT 를 반으로 줄여도 그대로다

  • 조건 : 보고서 출력 1,800토큰. TTFT 1.2초, 초당 출력 60토큰이라 치자(가정값). 완료 목표 15초.
  • 계산 : 완료 ≈ 1.2 + 1,800 ÷ 60 = 31.2초. 캐싱으로 TTFT 를 0.6초로 줄여도 30.6초 → 목표 미달. 출력을 700토큰으로 줄이면 1.2 + 700 ÷ 60 ≈ 12.9초 → 목표 안.
  • 판단 : 스트리밍 · 캐싱은 완료 목표를 못 맞춤. 출력 길이(짧게 요청 · max_tokens) · effort · 모델 쪽.
  • 전제 : 가정값 · 출력을 줄여도 품질 기준(eval)을 지킴.
  • 등급 : 계산
  • 근거 : OTel semconv en 297줄 · reduce-latency en 28~34줄 · ■ 지연 줄이기 lever

3. 에이전트는 요청 하나의 TTFT 가 체감이 아니다

  • 조건 : 한 턴에 도구를 4번 부르는 지원 에이전트. 요청마다 TTFT 는 짧음.
  • 판단 : 사용자가 기다리는 건 턴 전체(요청 여러 개 + 도구 실행). 요청 하나의 TTFT 만 보면 느린 도구 · 호출 횟수를 놓침. Claude Code 트레이스도 턴 전체(interaction.duration_ms)와 요청별(ttft_ms · duration_ms)을 따로 찍음. 어디서 느린지 가르기는 ■ observability 세 신호.
  • 등급 : 확인(필드) · 업계 일반(판단)
  • 근거 : monitoring-usage en 448·466·467줄

4. 사람이 안 보는 배치

  • 조건 : 밤새 도는 문서 요약 배치.
  • 판단 : TTFT 는 해당 없음. 공식도 캐시 미리 데우기를 배치에서 거부하며 "TTFT 는 배치와 무관"이라고 씀. 지표는 전체 완료 시각(배치 창) · 처리량.
  • 등급 : ✓ 확인
  • 근거 : prompt-caching en 464줄 · ◆ Batch API vs 동기 호출

미해결

  1. 공식 지연 문서(reduce-latency)는 "응답 완료까지"를 이름으로 따로 정의하지 않음. 가까운 것은 기본 지연(baseline latency, 초당 토큰은 따로 안 셈)과 eval 예시의 time_to_last_token · OTel gen_ai.server.request.duration. 카드의 "응답 완료 지연"은 이 셋을 묶은 이름.
  2. extended thinking 을 켜면 첫 토큰이 thinking(사고) 블록일 수 있어 "사용자가 보는 첫 글자"와 TTFT 가 어긋날 수 있음 — 받은 원문에 이 관계를 말한 문장 없음. Claude Code 의 first_content_ms(첫 content 블록까지)가 ttft_ms 와 따로 있는 것만 확인(monitoring-usage en 468줄).
  3. 목록 4.1② 의 규칙 "TTFT 자체를 줄이는 공식 수단은 캐싱(샘플 2 해설)"은 확인. 목록의 영어 신호 두 문장도 reduce-latency en 10·41줄에서 찾음.
  4. "사람이 보면 TTFT, 코드가 받으면 완료"라는 갈림 자체는 공식 문장 없음(업계 일반) — 공식은 TTFT 가 스트리밍·반응성에 특히 중요하다고만 씀.
